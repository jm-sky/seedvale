## Confirmed current state

**Generation pipeline** (`settlement/settlementGenerator.ts`): `generateSettlementCore()` runs one deterministic pass per grid cell — `resolveSettlementContext()` (resource scan + provisional size roll from terrain) → `chooseSettlementSite()` (`findSettlementSite.ts`, hard-rejects river-channel overlap and wet/uneven terrain) → `resolveVillageIdentity()` (terrain/resource-driven name, food-source type, optional Resource Outpost override) → `generateFamilies()` (`families.ts`) → `planVillageLayout()` (`villagePlanner.ts`, produces the authoritative `VillagePlan`: boundary/center/pattern/zones/plots/buildings/landmarks/paths/entrances). `SettlementDef` (`settlementDefFromPlan()`) is an explicit **thin compatibility projection** over `VillagePlan` — the plan, not the def, is authoritative (plan 047). `settlementPlanCache.ts` memoizes defs per cell so repeated resolution (streaming, road midpoints, debug tools) doesn't regenerate.

**Streaming** (`SettlementsManager.ts`): grid cells within `loadRadius`/`unloadRadius` of the player are streamed via `ensureLoaded()`/`unload()`; the home cell `(0,0)` is always loaded and its 2 nearest neighbors are eagerly pre-streamed. `createSettlement.ts` builds the runtime `Settlement` (props/houses/roads meshes, `NpcAgent`s, livestock, economy, households) from a `SettlementDef` plus five long-lived registries owned by `SettlementsManager` itself, not by any individual `Settlement`: `EconomyRegistry`, `HouseholdRegistry`, `NpcStateRegistry`, `NpcRelationships`, `LivestockRegistry`. All five survive a settlement's unload/reload cycle (registries persist while the `Settlement` object is disposed and rebuilt) and an in-session `WorldBundle` rebuild via a consistent `initial*` (constructor param) / `snapshot*` (serialize) idiom.

**Settlement economy** (`economy/settlementEconomy.ts`): `SettlementEconomy` holds bulk `EconomicStock` (`wood`/`iron`/`coal`/`gold`) plus a separate concrete-item `Inventory` for `food` (since plan settlements-npcs-008 — `add`/`remove('food', …)` are literal no-ops, food only moves through `depositFood`/`withdrawFood`). Demand-driven `shortage`/`surplus` compare live stock against a fixed per-`EconomicKind` target; `reserve`/`consumeReservation`/`releaseReservation` back `development.ts`'s settlement upgrades. `economy/registry.ts`'s `EconomyRegistry` is the per-manager map; `economy/localExchange.ts`'s `claimHouseholdSurplus`/`claimEconomySurplus` are small, atomic, live-revalidated claim primitives shared by every transfer direction (village↔household, household↔household, Trader work) instead of a `TradeManager`.

**Households** (`household.ts`): one household per family (`householdIdFor(settlementId, familyIndex)`), living on `HouseholdRegistry` (mirrors `EconomyRegistry`'s lifetime contract exactly). A household owns `stock` (wood only — `EconomicStock`), `water` (a separate `WaterReserve`, deliberately not an `EconomicKind`), and `items` (a generic unbounded `Inventory` — the sole authoritative store for concrete food items plus meat/hide/arrows/bandages/hay). `HOUSEHOLD_POLICY`/`WATER_POLICY` are small fixed minimum/target/capacity constants, not an economic planner.

**Land ownership/purchase** (`landOwnership.ts`, `landPurchase.ts`): a sparse `Set<"settlementId:plotId">` (`LandOwnershipRegistry`), persisted directly as a top-level `SaveData.ownedLandPlots: string[]` — a structurally different, simpler persistence path than the registry `initial*`/`snapshot*` idiom used everywhere else in this domain. `purchaseLandPlot()` is a pure, fully-validated transaction (plot exists → not already owned → positive price → affordable) against a narrow `LandPurchaseTarget` structural type, not the whole `Settlement`.

**Lodging** (`lodging.ts`, `lodgingResolver.ts`): a `LodgingOption` contract (`bed`/`friend`/`paid`/`hay`) and a pure preference resolver (`resolveBestLodging`). Physically lives in `src/settlement/` but is self-tagged `@domain ui-input` in its own JSDoc and is documented in `docs/state/player-systems.md`, not `settlements.md` — a deliberate cross-domain split (settlement data, player-facing feature), consistent with the file's own domain tag.

**Storage** (`storageDestinations.ts`, `storageVisuals.ts`): `storageDestinations.ts` is the single "WHERE does a resource physically go" resolver — wood always to `landmarks.stockpile`, food to a household's own home or (at settlement scope) `landmarks.settlementStorage`. `storageVisuals.ts` (tagged `@domain settlements-npcs`) is presentation-only; the quantity itself always lives in `Household`/`SettlementEconomy`.

**Places** (`places.ts`): a small `Place` abstraction (`home`/`workplace`/`food`/`social`) with an optional `isAvailable()` gate, shared by NPC scheduling, the settlement campfire Social Place, and (via `homeIndexFromPlaceId`) the lodging resolver's house lookup.

**Fauna/economy seam inside `settlement/`**: `rats.ts` is explicitly self-tagged `@domain fauna` (`settlement-rats` system) despite living in `src/settlement/` — `ratPopulationTarget()` is a pure function of `Household.foodCount()` summed across a settlement plus `SettlementEconomy.query('food')` and alive dog count; rats drain real food from those same stores. `livestock.ts` gives owned animals `ownerHouseId`, consumed by `fauna/AnimalAgent`'s water/diet-target resolution (owner's `Household.water`/`items` preferred before falling back to wild forage/shore, per `docs/state/settlements.md`'s own accurate description).

**Terrain-facing site/road logic**: `findSettlementSite.ts` and `villagePlanner.ts`'s per-plot placement (`pushOutOfRiver`, `footprintOverlapsRiver` calls) both hard-reject candidates whose footprint overlaps a live river channel (`terrain/riverNetwork.ts`), using `RiverChannelSegment` data resolved once per settlement generation pass. `settlement/roadNetwork.ts` computes route/corridor waypoints (`RoadCorridorSegment`) between settlements; the actual terrain carving — including blending in ford geometry at a river crossing — happens in `terrain/chunkHeightmap.ts` (a world/terrain-owned module) via `terrain/riverFord.ts`'s `fordBedHeight`/`fordStrength`. The settlement domain determines *where* roads/sites avoid or cross rivers; the physical terrain deformation, including fords, is entirely a `terrain/`-owned concern.

## State ownership

- **Deterministic, non-authoritative layer**: `VillagePlan`/`SettlementDef` are pure functions of `(seed, cell, terrain samplers, region params)` — regenerated on demand via `settlementPlanCache`, never itself mutated. This is *not* authoritative runtime state; it's closer to procedural worldgen output (same category as terrain chunk generation).
- **Authoritative mutable state** lives in the five `SettlementsManager`-owned registries (`EconomyRegistry`, `HouseholdRegistry`, `NpcStateRegistry`, `NpcRelationships`, `LivestockRegistry`) plus the standalone `LandOwnershipRegistry` (owned further up, at the `app/` composition level per `saveState.ts`/`createApp.ts`/`interactables.ts` usage). The runtime `Settlement` object (props meshes, `NpcAgent` instances) is a rebuildable projection over `SettlementDef` + these registries — the same "authoritative state not duplicated into Three.js/runtime objects" invariant `ARCHITECTURE.md` states for `WorldBundle` is replicated one level down inside `SettlementsManager` itself. Presentation-only containers (`WaterBarrel`/`AnimalTrough`/`storageVisuals.ts` crates) are explicitly documented in code comments as non-authoritative — the quantity is always `Household`/`SettlementEconomy`.
- **Persistence status — a significant, previously-undetected staleness**: `persistence/saveData.ts` shows `npcStates?`, `households?`, `npcRelationships?`, and `livestock?` are all now **optional, sparse `SaveData` fields**, added by plan `persistence-001` (full-simulation persistence). This directly contradicts `docs/state/settlements.md`'s Standing Decision **S7** ("Runtime NPC (needs, AI, vigor) nie jest w save. Continue nie przywraca pełnej symulacji.") and its §Gospodarstwa closing bullet ("`Household`/`household.water` w `SaveData`" listed under "świadomie nie ma"), and its §NPC section's claim that `npcRelationships` "nie jest jeszcze w `SaveData`". The code itself is aware of this drift — `settlement/npcState.ts`'s own doc comment explicitly flags that its "not part of SaveData" per-field comments are stale, and `docs/plans/LOOSE-ENDS.md` already has a 2026-09-06 entry about `npcState.ts`'s internal comments — but that awareness has not propagated to `settlements.md`, which still states the old (pre-persistence-001) picture as current fact in three separate places. This is the single most consequential documentation-accuracy finding in this audit.
- **`WorldBundle`-rebuild carry** (in-session, distinct from `SaveData`): all five registries use the same `initial*` constructor param / `snapshot*`-called-from-`worldBundle.ts` idiom, confirmed directly in `SettlementsManager.ts`'s constructor signature and doc comments (`initialEconomies`/`initialHouseholds`/`initialNpcStates`/`initialNpcRelationships`/`initialLivestock`+`initialRemovedLivestockIds`). `settlements.md` documents this carry mechanism correctly for economy/household/NPC state (plan 197/151 references check out); it just conflates "not carried across `WorldBundle` rebuild" (which used to be true and now isn't, for household) with "not in `SaveData`" (which used to be true for all of these and now isn't either).
- **Land ownership uses a different persistence idiom**: `ownedLandPlots` is a flat top-level `SaveData` field, not routed through a registry `initial*`/`snapshot*` pair the way the other four are — worth noting as an inconsistency (not a bug) if a future architectural pass wants one uniform persistence pattern for settlement-adjacent state.
- **NPC-state ownership-boundary oddity** (reconfirmed from Stage 1): `settlement/npcState.ts`, `npcRelationships.ts`, `npcPhysicalProfile.ts` are physically under `src/settlement/` but are constructed and threaded opaquely by `SettlementsManager`/`createSettlement.ts` into `src/ai/`'s `NpcAgent`, which is their near-exclusive consumer and mutator. This is not an isolated case: the codebase already has a lightweight `@domain`/`@system` JSDoc convention (feeding `CODE_INDEX.md`'s generated navigation section) that several other `src/settlement/` files use to declare a *different* logical domain than their physical directory — `rats.ts` (`@domain fauna`) and `lodging.ts` (`@domain ui-input`) both do this explicitly, while `npcState.ts`/`npcRelationships.ts`/`npcPhysicalProfile.ts` carry no such tag at all despite arguably needing one (`@domain npc-ai` or similar) more than any other file in the directory.

## Important runtime flows

1. **Generation → streaming → build.** `worldToCell(playerPos)` → `SettlementsManager.recheck()` → `defFor(cell)` (cached `generateSettlementCore()` via `settlementPlanCache`) → within `loadRadius`, `ensureLoaded()` → `waitForChunks()` (terrain must exist first) → `createSettlement(def, economyFor(def), settlementDeps)` builds houses/roads/props (`houseBuilder.ts`/`props.ts`/`roadNetwork.ts`), resolves/creates this settlement's households from `HouseholdRegistry` (reused if this cell was visited before this session) and NPCs from `NpcStateRegistry` (same reuse), and spawns livestock via `livestock.ts` seeded from `LivestockRegistry`. Beyond `unloadRadius`, `unload()` captures livestock state into the registry and disposes the `Settlement`'s meshes/agents — the registries, not the disposed objects, are what survives.

2. **Resource → NPC work → household storage → settlement economy** (wood path, the cleanest example): a woodcutter NPC's `chop → deposit` action (built in `ai/` via the profession-work planners) calls `Household.deposit('wood', amount, economy, simTime)` — this caps at the household's own capacity and only routes the *overflow* into `SettlementEconomy.add('wood', overflow)`. The mirrored ore/mining path is asymmetric by design: mined ore skips `Household` entirely and goes straight from the NPC's own carried `Inventory` into `SettlementEconomy` as `iron`/`coal`/`gold` — confirmed in both `household.ts`'s doc comments and `settlements.md`'s §Ekonomia description, and consistent with `EconomicStock`'s kind set never including a household-storable raw-ore category.

3. **Local resource exchange (shortage pull).** When a household is short on `wood`/`food`, an NPC's strategy list (`ai/npcLogistics.ts`, outside this domain's scope but the consumer of it) resolves a claim through `economy/localExchange.ts`'s `claimHouseholdSurplus`/`claimEconomySurplus` — both **re-read live `surplus()`** at claim time rather than trusting an earlier decision-time snapshot (explicit design intent in the file's own header comment, guarding against a stale "available" read after another NPC/the player already consumed the source). `storageDestinations.ts` then resolves the physical destination, and `Household.depositFood`/`deposit` performs the final capacity-capped write. Household↔household lookups are settlement-bounded (`householdExchange.ts`'s `HouseholdExchangeHooks`, nearest-first, no world-wide scan).

4. **Settlement placement vs. terrain/hydrology.** `settlementGenerator.ts` resolves a per-cell resource/terrain context, then `findSettlementSite.ts` and `villagePlanner.ts`'s per-plot placement both hard-reject any candidate whose footprint overlaps a live river channel (`terrain/riverNetwork.ts`'s `footprintOverlapsRiver`, using `RiverChannelSegment`s resolved once per generation pass and reused by both). Once a site and plan exist, `settlement/roadNetwork.ts` computes the route/corridor waypoints connecting settlements; the actual terrain deformation for that corridor — including ford geometry where a road crosses a river — is carved entirely inside `terrain/chunkHeightmap.ts` (a `terrain/`-owned module, consuming `terrain/riverFord.ts`). The settlement domain never itself models a ford; it only supplies corridor waypoints and (for site/plot selection) a hard river-avoidance gate.

5. **Land purchase.** A player interacting with a `SettlementLandPlot` landmark triggers `purchaseLandPlot()` (validated: plot exists, not owned, positive price, affordable) → `Inventory.remove('coin', price)` + `LandOwnershipRegistry.setOwned()` → persisted directly to top-level `SaveData.ownedLandPlots` (via `app/saveState.ts`, confirmed as a consumer). This flow is entirely undocumented in any `docs/state/*.md` file today (see Documentation discrepancies #3).

## Shared mechanisms

- **`economy/localExchange.ts`'s atomic claim seam** (`claimHouseholdSurplus`/`claimEconomySurplus`) — owned by this domain, consumed by `ai/npcLogistics.ts` and the profession-work planners. A good candidate to promote from "`STATE.md` prose only" to an actual `settlements.md` entry point, since it's genuinely settlement/economy-domain code, not NPC-AI code, despite being driven by NPC decisions.
- **`storageDestinations.ts`'s WHERE resolver** — one small pure module used by every wood/food delivery leg (chop→deposit, catch→deposit, exchange, economy-withdraw) instead of each call site hard-coding a destination.
- **`Place` abstraction** (`places.ts`) — shared by NPC scheduling, the Social Place (campfire) system, and the lodging resolver's house lookup (`homeIndexFromPlaceId`). A genuinely cross-cutting settlement-owned primitive.
- **Registry `initial*`/`snapshot*` idiom** — the same shape (`getOrCreate`/`get`/`clear`/`serialize`) is independently implemented for economy, household, NPC state, NPC relationships, and livestock. Not abstracted into a shared generic (each has different construction/hydration needs), but consistent enough that documenting the *pattern* once (rather than per-registry) would reduce `settlements.md`'s repetition.
- **`terrain/riverNetwork.ts`'s `footprintOverlapsRiver`** — owned by terrain, consumed by both settlement site-selection and plot-placement; this domain is a major consumer but not the owner.

## Recommended documentation changes

1. **Fix the three stale SaveData claims** in `settlements.md` (S7, §Gospodarstwa closing bullet, §Social's `npcRelationships` line) to reflect plan persistence-001: `npcStates`/`households`/`npcRelationships`/`livestock` are now optional, sparse `SaveData` fields. This is the highest-value, lowest-risk fix identified in this audit — it's a factual correction, not a scope change.
2. **Narrow `settlements.md`'s stated scope.** Its header claims to be the source of truth for "generacji osad i życia NPC" — recommend narrowing to something like "settlement generation, households, and settlement/household economy" and adding an explicit forward pointer to the future NPC-AI state doc for decision-making/needs/strategies content, rather than implying `settlements.md` covers NPC behaviour it doesn't actually document in depth.
3. **Add a short land-ownership/purchase section** to `settlements.md` (plan 129: `landOwnership.ts`/`landPurchase.ts`, `SaveData.ownedLandPlots`) — currently undocumented anywhere.
4. **Add one-line cross-references** from `settlements.md` to: (a) `player-systems.md`'s lodging section (so a reader discovers that settlement-hosted lodging data is documented there), (b) `settlement/rats.ts`'s fauna-domain consumption of household/economy food state (even a single sentence, since it's a real, if small, integration seam touching this domain's own authoritative state), and (c) `water.md`'s "Integracja rzek z resztą worldgenu" section, which already documents the river-overlap rejection at settlement site/plot placement in detail — `settlements.md` currently has no pointer to it at all (confirmed during reconciliation with the parallel world/terrain/water audit).
5. **Move `economy/localExchange.ts`'s claim-seam description** from `STATE.md`'s prose into `settlements.md` proper — it's settlement/economy-owned code and belongs in the domain doc rather than only in the higher-level snapshot.
6. **Trim `STATE.md`'s "Settlements / NPCs" section.** Once a dedicated NPC-AI audit/doc exists, split this section: keep a short paragraph on settlement generation/streaming/economy/household ownership (pointing to `settlements.md`), and move the NPC decision-architecture prose (needs arbitration, weather/healing pressure, work contracts, the NpcAgent refactor) to wherever the NPC-AI current-state doc ends up. Do not apply this now — it depends on the NPC-AI audit's outcome — but the audit matrix should record it as a concrete Stage 4 action item.
7. **Language consistency (open question, not a strong recommendation):** `settlements.md` is Polish while `combat.md`/`player-systems.md`/`terrain-and-world-generation.md` are English. Given the document is dense and technically precise as-is, a Polish→English conversion is a nontrivial rewrite risk for a purely cosmetic consistency gain — flagging as a question for the reconciliation stage rather than recommending it outright.
8. **Document the `@domain`/`@system` JSDoc convention itself**, if it isn't already documented somewhere (not found in this pass) — it's the actual mechanism that resolves "which directory is this file in" vs. "which domain does it belong to" for `rats.ts`, `lodging.ts`, and (recommended, see below) the NPC-state files, and future audits/agents would benefit from knowing it exists and is authoritative over physical directory placement.
9. **Add `@domain`/`@system` tags to `settlement/npcState.ts`, `npcRelationships.ts`, `npcPhysicalProfile.ts`** (e.g. `@domain npc-ai`) — not a documentation-file change but a low-risk source comment addition that would make the existing ownership-boundary oddity self-evident to both humans and the `CODE_INDEX.md` generator, the same way `rats.ts`/`lodging.ts` already do for their own cross-directory ownership.
