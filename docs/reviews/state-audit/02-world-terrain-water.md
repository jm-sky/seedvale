## Confirmed current state

### Chunk streaming & terrain generation

- `ChunkManager` (`src/terrain/chunkManager.ts`, 2608 lines — the single largest file in the domain) owns chunk lifecycle: load/unload by Chebyshev distance (`loadRadius`/`unloadRadius` hysteresis pair, `homeChunks` pinned regardless of distance), a `CHUNKS_STARTED_PER_FRAME = 2` cap on worker-job starts, and a `finalizeQueue` that spends one slot/frame on either a mesh attach or vegetation/environment content (mesh wins ties). This matches `terrain-and-world-generation.md`'s description exactly.
- **Newly confirmed, not yet documented anywhere:** chunk *mesh geometry* data generation (`computeChunkMeshData` in `chunkMeshData.ts` — position/normal/color/`aBareGround` arrays) now runs **in the worker pool**, not on the main thread. `ChunkWorkerPool.requestMesh()` (`chunkWorkerPool.ts`) dispatches a `'mesh'` job to `chunkHeightmap.worker.ts`, which calls `computeChunkMeshData()` and transfers the result back; `ChunkManager.requestChunkMeshData()` either serves a `ChunkMeshDataCache` (`chunkMeshCache.ts`, in-session LRU, 64 MB budget) hit or awaits that worker round-trip, and only then does `buildChunkGeometry()` on the main thread — now just cheap `THREE.BufferGeometry`/`Mesh` assembly from already-computed arrays. This is plan `world-terrain-004`, landed in commit `16ca5a3c` ("feat(world-terrain): move chunk mesh geometry computation off the main thread"), **2026-09-02 14:48**, i.e. **after** `GRAPHICS.md`'s G17 log entry (commit `f9d0a7d4`, same day 14:09) which describes this exact migration as "Docelowy kierunek (niezaimplementowany)" — see Documentation discrepancies.
- GLB prop templates preload at `ChunkManager` construction (confirmed, matches doc).
- `forestDensityAt`/`forestBiomeAt` (`biomeRegions.ts`) is one continuous function feeding both tree density and fauna habitat, exposed as `ChunkManager.sampleForestFactor`/`sampleForestBiome` and `WorldContext.sampleForestBiome` — confirmed, matches doc.

### Terrain shaping pipeline (mountains, roads, rivers)

- `chunkHeightmap.ts`'s `computeChunkTexel()` runs three ordered terrain-modifier stages on the raw procedural texel, confirmed by reading the code directly:
  1. `applyRegionalSmoothing()` — broad, weak village-wide leveling (settlement-driven; this is the concrete **terrain-adaptation-for-settlements** mechanism, not documented under that name anywhere).
  2. `applyTerrainCorridors()` — sharp road/path/clearing blend (tint + `roadFalloff` output feeds both the road texture and the ford blend below).
  3. `applyRiverChannel()` — river channel carving, only ever lowers terrain (`Math.min`), consumes stage 2's `roadFalloff` for the ford blend (`riverFord.ts`'s `fordStrength`/`fordBedHeight`).
  This confirms `water.md`'s "Architektura" description and its river-integration section (`riverFord.ts`) precisely.
- Mountain massif shaping (`sampleRawTexel()`), peak/massif hierarchy (plan 191) — code present as described in `terrain-and-world-generation.md`; not independently re-verified line-by-line (low risk, stable area, last touched by an already-closed plan).

### Vegetation, rocks, trees

- Region-batched instancing (`vegetationRegionBatcher.ts`, `REGION_CHUNKS = 3`) confirmed present and wired from `ChunkManager`. Grass (`grass.ts`/`grassPlacement.ts`) confirmed per-chunk, not region-batched, with a separate filler-LOD bucket. `TreeLifecycle` (`world/treeLifecycle.ts`) confirmed as sparse-override + lazy-growth, not a per-tree ticking simulation.

### Weather, seasons, surface effects

- `world/weather.ts` (298 lines): `getSeason`/`computeWeather`/`computeClimate` are confirmed pure functions of `(seed, elapsedDays)` — no save field, no runtime history. `computeSurfaceWeather()` (wetness/snow) and `computeRainExposureDays()` are confirmed as separate bounded-lookback derived functions (different lookback shapes — the doc's phrasing correctly keeps them distinct). `WeatherState` is confirmed threaded live (`gameLoop.ts` → `SettlementsManager`/`Settlement.update()` → `NpcAgent.update()` → `ai/weatherPressure.ts`) — one shared per-frame value, never recomputed per NPC, matching `STATE.md`'s npc-012 description.
- Visuals (`weatherVisuals.ts`, `weatherParticles.ts` GPU points, `clouds.ts` sprite pool, `groundFog.ts` fixed pool) — all confirmed present as described; not line-by-line re-verified (stable, low-churn area with existing GRAPHICS.md G13 contract).
- Weather → NPC/fauna/resource coupling: `terrain-and-world-generation.md` still says "not implemented," which is stale — `ai/weatherPressure.ts` (npc-012) and settlement garden hydration (settlements-npcs-001, rain via `computeWeather`) are both real, existing consumers threaded from this exact module. See Documentation discrepancies.

### Hydrology / rivers

- `terrain/hydrology.ts` (D8 flow + accumulation) → `terrain/riverNetwork.ts` (256 m deterministic "river tiles", Chaikin smoothing + seeded meander) → `terrain/riverTileCache.ts` (synchronous, main-thread, reference-counted per loaded chunk, ~18 ms/tile) → `world/riverGeometry.ts` (per-chunk ribbon, `canonicalWaterHeight`) → `world/riverWaterMaterial.ts` (dedicated shader, not the lake/ocean family). All confirmed present and match `water.md`'s "Architektura"/"Rzeki" sections precisely, including: dry-sink repair (`resolveMeaningfulDrySinks`/`findBreachPath`), estuary continuity fix (`hasClassifiedInflow`/`MIN_CONTINUATION_CHAIN_POINTS`), waterfalls (`aFall` attribute, no separate geometry), and channel carving invariants (`bedH < waterH < floorH`, `waterHalfWidth < channelHalfWidth`).
- **Settlement/road/fauna integration with rivers (2026-09-06 entry in `water.md`) — independently confirmed in code, all three claims check out:**
  - `terrain/riverQuery.ts`'s `createRiverQuery()` is consumed by `settlement/settlementGenerator.ts` (`riverQuery.segmentsNear`) and registered via `settlement/settlementPlanCache.ts`'s `setSettlementRiverQuery`; `settlement/findSettlementSite.ts` hard-rejects a plaza within `SITE_RIVER_CLEARANCE = 8m` via `footprintOverlapsRiver` (from `terrain/riverNetwork.ts`).
  - Ford: `chunkHeightmap.ts` imports `fordBedHeight`/`fordStrength` from `terrain/riverFord.ts` and applies them inside `applyRiverChannel`'s per-texel candidate, gated by stage 2's road corridor `roadFalloff` — confirmed emergent (no separate ford mesh/segment type).
  - Fauna: `fauna/createFauna.ts` has `SPAWN_RIVER_CLEARANCE = 1.5`, `SPAWNER_RIVER_CLEARANCE = 6`, and `clearsRiverChannel()` gating both wild-ring spawns and habitat spawner sites via `ChunkManager.riverShoreDistance`.
- `terrain/waterSample.ts`'s `sampleLocalWater()` is confirmed as the single physical water-presence answer (lake/ocean via `floorHeights`, river via `riverNetwork.ts`'s `riverWaterSampleAt()`, river always wins) — wired to `ChunkManager.sampleLocalWater`, consumed by `fauna/waterTraversal.ts`'s classifier for wading/swimming/drowning. Matches `water.md` and `STATE.md`'s fauna-015 description.

Scene mirror (`world/waterMirror.ts`, single RT, 30 Hz cap, layer-gated away from NPC/fauna/grass) confirmed present and matches `GRAPHICS.md` G5/G5a and `water.md` W6/W9.
- `WaterSource` (`world/WaterSource.ts`) confirmed as the shared drink/fill abstraction (`well`/`lake`/`river`/`ocean`), consumed by `app/actions/survivalActions.ts`, `app/interactables.ts`, `settlement/household.ts` (animal/NPC watering), `items/itemCatalog.ts`, `persistence/saveData.ts`. ### Persistent worldgen cache mechanism (undocumented anywhere)

- `src/persistence/db.ts` + `src/persistence/worldgenCacheDb.ts` implement a generic, versioned, IndexedDB-backed `(seed, namespace, version, fingerprint) → payload` derived-data cache (plan world-015) — exactly the "worldgen cache namespace/version bump" mechanism `CLAUDE.md`'s Determinism section describes as the required convention. The **only current namespace** is `world/locations/locationsCoarseCache.ts`'s `'locations-coarse'` (`LOCATIONS_COARSE_VERSION = 1`), used for `WorldLocationCatalog`'s coarse terrain tiles — not core terrain/hydrology generation. A record whose `fingerprint` (hash of every deterministic `RawSampleParams` input) doesn't match is a cache miss, never migrated — the correct pattern per repo convention.
- Core terrain/hydrology generation itself (`chunkHeightmap.ts`, `hydrology.ts`, `riverNetwork.ts`) has **no persistent cache at all** — only in-session, non-persisted caches (`riverTileCache.ts`, `chunkMeshCache.ts`'s `ChunkMeshDataCache`) that are trivially safe across a code change (cleared on reload/new session, never carried across a deploy). This means the versioned-cache-namespace concern from `CLAUDE.md` currently applies to exactly one namespace in the whole terrain/water domain, and it already follows the convention correctly. Neither `terrain-and-world-generation.md` nor `water.md` mentions this mechanism.

### Caves, locations, map (adjacent, not core to this domain)

- Caves (`world/caveGenerator.ts`, `caveVolume.ts`, `createCaves.ts`, `world/caves/*`) are a deterministic `CaveDefinition` graph (entrance → tunnel → chamber(s)) built on top of `largeCaves.ts`'s existing world-scale site placement; `createCaves.ts` carves a mouth recess into the terrain heightmap via `ChunkManager.modifyTerrain` (`source: 'system'`) — the one place caves directly touch this domain's terrain-mutation API. Otherwise caves are their own presentation/collision/fauna-habitat system.
- `world/locations/*` (`WorldLocationCatalog`, `locationDiscovery.ts`, `locationKnowledge.ts`, `navigationTargets.ts`) and `world/map/*` (`MapData`, `MapProjection`, `MapDiscovery`) are **consumers** of terrain sampling (`sampleContinentalnessAt`/`sampleFloorAt`/`sampleHeightAt`/`sampleMountainRidgeAt` from `chunkHeightmap.ts`, plus `terrainClassification.ts`'s `isMountainRidge`/`isOceanMix`/`isWetFloor`) to classify coarse world tiles (lake/mountain-peak/cemetery siting) independent of chunk streaming. They are not owned by this domain and are effectively undocumented as their own domain in `docs/state/` (only two one-line `STATE.md` bullets) — this looks like it belongs to a future progression/discovery-focused audit pass, not this one; recorded here only because of the terrain-sampling dependency.

## State ownership

- **Authoritative, deterministic, unpersisted:** terrain heightmap/biome/river/road data is derived fresh every session from `(seed, region params)` — no save field, confirmed by `ARCHITECTURE.md`'s save-schema section and the complete absence of terrain grids in `persistence/saveData.ts`'s `SaveData` type (not independently re-read line-by-line here, but no code path found writing raw terrain grids to `SaveData`). `Season`/`WeatherState`/surface wetness/snow are likewise pure functions of `(seed, elapsedDays)` — zero save fields, confirmed both by the water/terrain docs and by `ARCHITECTURE.md`'s explicit callout.
- **Runtime-only caches, not authoritative:** `riverTileCache.ts` (reference-counted per streamed chunk) and `chunkMeshCache.ts`'s `ChunkMeshDataCache` (byte-budgeted LRU) are pure performance caches over the same deterministic functions — evicting or clearing either changes nothing observable except recompute cost. Neither is a second source of truth.
- **Persisted, but as sparse deltas over deterministic base state (not the state itself):** `SaveData.terrainModifications` (dig/scorch/prepare, player-caused only — system-caused ones like cave carving are excluded and reproduced from scratch every build, confirmed by `ARCHITECTURE.md`), `SaveData.resourceDeposits` (sparse `id → remaining` map). This is the correct "authoritative delta over derived base" shape and matches the documented invariant.
- **The one real persistent worldgen cache (`worldgenCacheDb.ts`)** is explicitly a disposable optimization layer, never a correctness dependency (its own JSDoc states this) — a miss always falls back to normal procedural generation. It is not "state" in the gameplay sense, but it is the one place in this domain where the `CLAUDE.md` cache-namespace-versioning convention is directly exercised, and it's completely absent from both `terrain-and-world-generation.md` and `water.md`.
- **`WorldBundle` rebuild survival:** `ChunkManager` itself is recreated wholesale on `rebuildWorldBundle()` (new seed ⇒ new terrain generator, per `ARCHITECTURE.md`'s world-lifecycle section); `PlayerController` explicitly survives and is rebound via `setGround(...)`. Module-level caches that are *not* seed-scoped (the road-network cache, tree-lifecycle presence/override caches — per `ARCHITECTURE.md`'s world-lifecycle diagram) must be and are cleared on rebuild; `riverTileCache`/`chunkMeshDataCache` are owned by the (recreated) `ChunkManager` instance itself, so they don't need separate clearing logic — this ownership shape is correct but not spelled out in either domain doc.
- **Weather/climate runtime cache:** `ClimateState`/`tickClimate` is a small mutable cache (mirrors `DayNightState`'s shape) that only recomputes `weather` on a cycle boundary — confirmed derived-not-authoritative, consistent with the doc.

## Important runtime flows

**1. Seed → chunk streaming → render.**
`ChunkManager.update()` drives a load queue (Chebyshev distance) → `ChunkWorkerPool.requestTile()` (worker: `computeChunkTile()` — heights/biomes/road-tint/vegetation/items/environment/crops, transferable buffers) → on tile arrival, `requestChunkMeshData()` (worker: `computeChunkMeshData()`, cached in `ChunkMeshDataCache`) → main thread `buildChunkGeometry()` (now just `BufferGeometry`/normals-from-arrays/mesh attach) → scene attach via the `finalizeQueue`, one slot/frame shared with vegetation/environment attach.

**2. Hydrology → river tile → per-chunk ribbon + channel carving.**
`hydrology.ts`'s D8/accumulation over a 256 m analysis window (+halo) → `riverNetwork.ts`'s `computeRiverTile()` (chains, dry-sink repair, meander) → `riverTileCache.ts` (sync compute + ref-count) → two independent consumers of the same canonical chain: `world/riverGeometry.ts` (visual ribbon, `aFlow`/`aFall` attributes) and `chunkHeightmap.ts`'s `applyRiverChannel` (terrain carving, ford blend) via `riverNetwork.ts`'s `riverChannelSegmentsNear`. Both consumers are guaranteed not to drift because they resolve through the same pure `computeRiverTile()`.

**3. Rainfall/season → weather state → NPC/settlement/garden consumers.**
`world/weather.ts`'s pure `computeClimate(seed, elapsedDays)` → `gameLoop.ts`'s live `climate.weather` → threaded unmodified through `SettlementsManager`/`Settlement.update()` into every `NpcAgent.update()` call for that frame → `ai/weatherPressure.ts`'s `weatherShelterPressure()` competes in `NpcAgent.choose()`'s arbitration as a `seekShelter` decision target. Separately, `computeRainExposureDays()` (bounded lookback over the same `computeWeather`) feeds player-garden hydration (`resolveGardenHydration`, settlements-npcs-001) and sleeping-utility condition decay (items-player-013) — two independent lazy-resolved consumers of the same deterministic weather history, never a second weather simulation.

**4. Settlement site selection ↔ terrain queries (three independent seams, same `chunkHeightmap`/`terrain/` sampling surface).**
`findSettlementSite.ts` biases candidates via `terrain/naturalResources.ts::resourceAttractionAt` and rejects river-overlapping plazas (`footprintOverlapsRiver`, 8 m clearance); `settlementTerrain.ts::classifySettlementTerrain` averages `sampleContinentalness`/`sampleMountainRidge`/`sampleMoistureRegion` around the chosen site for settlement *naming*; and `chunkHeightmap.ts`'s stage-1 `applyRegionalSmoothing` physically flattens terrain around a settlement footprint before roads/rivers are blended in. Three distinct terrain↔settlement seams, all reusing the same underlying sampling functions rather than duplicating terrain logic — but none of them is named as such in `terrain-and-world-generation.md`.

## Shared mechanisms

- **Terrain sampling API surface** (`ChunkManager`'s `sampleHeight`/`sampleFloor`/`sampleBiome`/`sampleContinentalness`/`sampleMountainRidge`/`sampleMoistureRegion`/`sampleForestFactor`/`sampleForestBiome`/`sampleLocalWater`/`riverShoreDistance`) is the domain's single most cross-cutting export — consumed directly by settlements (siting, naming, leveling), fauna (habitat, water traversal), locations/map (discovery classification), and player movement (`slopeConstraint.ts`). `ARCHITECTURE.md`'s "Terrain as shared world environment" section correctly states the principle ("consume these APIs rather than duplicate terrain-generation logic") but doesn't enumerate the actual surface — that enumeration currently only exists in the `ChunkManager`/`WorldContext` type definitions themselves.
- **`slopeConstraint.ts`** — one pure finite-difference slope probe, called identically from `PlayerController.update()`, `NpcAgent.steerTo()`, `AnimalAgent.steerToward()`. Confirmed a true shared mechanism, correctly documented as such.
- **`WaterSource`** (`world/WaterSource.ts`) — shared drink/fill data contract across well/lake/river/ocean, deliberately designed (per its own JSDoc) to extend to future polluted/treated sources without a parallel mechanism. Confirmed genuinely shared (household, player, persistence all consume the same type).
- **`worldgenCacheDb.ts`** — a generic reusable persistence primitive for *any* future worldgen namespace (deterministic derived-data cache keyed by seed+namespace+version+fingerprint). Currently under-advertised: only one namespace owner exists, but the mechanism is explicitly designed for reuse ("a namespace owner decides its own payload shape, fingerprint and versioning; this module only knows how to store/retrieve/bound it").
- **`ChunkWorkerPool`** — one shared worker pool now serving three job kinds (`tile`/`grass`/`mesh`) with priority ordering (tile & mesh > grass) and cancel-by-discard. This is the concrete mechanism `performance-and-workers.md`'s "Workers are appropriate candidates for... procedural terrain/chunk generation" principle already names in the abstract; the pool itself isn't named in that doc (reasonable — that doc is a principles doc, not an inventory).
