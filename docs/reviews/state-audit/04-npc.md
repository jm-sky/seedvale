## Confirmed current state

### `src/ai/` is the NPC decision/behaviour core, but not the whole NPC system

`NpcAgent.ts` (4,654 lines, by far the largest file in the domain) is the coordination point: FSM (`Phase`), `choose()` sequencing, movement execution, combat entry, social/contract drive, time-skip, and the public inspection API (`createInspectionSnapshot()`/`why()`). Its own class-header JSDoc self-tags `@domain settlements-npcs @system npc-agent`, not `@domain npc` — the one file most central to this audit is tagged with the *other* domain's name, which is itself a documentation-boundary artifact worth noting (see Documentation discrepancies).

The class delegates domain logic to 27 other non-test modules in `src/ai/` (confirmed via full listing: `Needs.ts`, `characters.ts`, `decisionModifiers.ts`, `dialogue.ts`, `dialogueTemplates.ts`, `healingPressure.ts`, `helperAssignment.ts`, `nameCultures.ts`, `npcAction.ts`, `npcAnimalThreat.ts`, `npcAssistance.ts`, `npcColliderRim.ts`, `npcCombat.ts`, `npcCrowd.ts`, `npcDecision.ts`, `npcLoadout.ts`, `npcLogistics.ts`, `npcMovementWatchdog.ts`, `npcPlan.ts`, `npcProfessionWork.ts`, `npcStrategies.ts`, `npcVigor.ts`, `npcVoiceLines.ts`, `npcWorkContract.ts`, `reactionChance.ts`, `schedule.ts`, `socialBehaviour.ts`, `weatherPressure.ts`), documented by `docs/reviews/2026-09-03--NpcAgent-refactor-review.md` as the outcome of a 2026-09-03/04 refactor that shrank the class from 5,179 to ~4,315 lines (it has grown again since, to 4,654, from later plans — npc-002/npc-012/npc-018 work landed after that review).

NPC *state* extends outside `src/ai/` entirely: `src/settlement/npcState.ts`, `npcRelationships.ts`, `npcPhysicalProfile.ts` hold authoritative NPC entity state and are consumed almost exclusively by `ai/`'s `NpcAgent` — confirmed exactly as `01-inventory.md`/`03-settlements-economy.md` found. None of the three carry an `@domain`/`@system` JSDoc tag (unlike `settlement/rats.ts`'s `@domain fauna` or `settlement/lodging.ts`'s `@domain ui-input`), despite `NpcAgent.ts` itself importing directly from all three and owning nothing else that touches them.

`src/settlement/families.ts` is a fourth NPC-adjacent file physically under `settlement/`: it generates `FamilyDef`/`FamilyMember` (name, lastName, relation, `CharacterDef`, scale, age) deterministically from a settlement seed, and is the sole producer of the identity data `ai/characters.ts` (role/traits/personality) and `ai/nameCultures.ts` (names) get folded into before `NpcAgent` construction. It is correctly `settlement`-owned (family/household composition is a settlement-generation concern), but its output (`FamilyMember.character: CharacterDef`) is entirely NPC identity data with no other consumer.

### NPC state ownership

**Identity / physical profile (deterministic, not persisted, regenerated every session):**
- `ai/characters.ts::CharacterDef` — name, lastName, gender, `Role` (8 values: woodcutter/farmer/miner/fisher/hunter/trader/guard/blacksmith), `BigFivePersonality` (OCEAN, continuous 0-1 each; the older discrete `Personality` enum — cheerful/calm/grumpy/curious — is now derived from it via `nearestArchetype()` purely to pick a dialogue-line bucket), `readonly Trait[]` (curious/energetic/fast_worker/night_owl/sociable). 4 names (Anna, Piotr, Kasia, Marek) are `RESERVED_CHARACTERS` — hardcoded because `quests/quests.ts` matches quest givers/targets by first name only; everyone else is `characterForSeed()`-generated.
- `settlement/npcPhysicalProfile.ts::generatePhysicalProfile(seed, sex, age)` — pure, deterministic max HP/stamina/vigor from sex + a 9-stage `LifeStage` age curve (infant→veryElderly) + ±10% per-capacity variation. Neither `strength`/`agility`/build/appearance exist yet (explicitly out of scope per the file's own doc comment, pointing at `docs/vision/npc-physical-state.md`).
- `settlement/families.ts::FamilyMember.age` — a real integer age in `[0,100]`, generated from a dedicated `familyAgeSeed` stream isolated from role/trait/name RNG, constrained so a child's age leaves ≥18 years below its younger parent.

**Authoritative runtime entity state — `settlement/npcState.ts::NpcAuthoritativeState`, keyed by stable `npc.id`, owned by a `NpcStateRegistry` living on `SettlementsManager` (mirrors `EconomyRegistry`/`HouseholdRegistry`):**
- `health: HealthState`, `stamina: StaminaState`, `vigor: VigorState`, `needs: NeedState` (thirst/woodDuty/waterDuty/hunger).
- `physicalInjury: number` (plan npc-002) — outstanding healable HP loss, deliberately *not* derived from `maxHp - currentHp` so it never conflates with a future non-physical (starvation/dehydration) damage type.
- `helperAssignment: HelperAssignment | null` (plan 167) — `{ targetContainerId, resourceKind: 'food', enabled }`.
- `activePlan: NpcPlan | null` (plan ai-004) — `{ goal: NpcGoalId, strategy: NpcStrategyId | null, state: NpcPlanState, progress: { amount }, currentStep }`.

`NpcAgent` holds **direct references** into these objects (no copy step); dispose/recreate of the `NpcAgent` instance (settlement unload/reload, in-session `WorldBundle` rebuild) re-hydrates from the same object. Deliberately excluded from this authoritative state (owned by `NpcAgent` itself, reset on reconstruction): `phase`, `pendingAction`, pathfinding/watchdog state, `combatIntent`, the carried `Inventory` (`carried`, ore/hunt-yield/exchange cargo).

**Persistence status — confirmed, resolving the open question `03-settlements-economy.md` flagged from the settlement side.** `persistence/saveData.ts`'s `isNpcStateSnapshot()` (line ~1219) validates `health`/`stamina`/`vigor`/`needs`/`physicalInjury`/`helperAssignment`/`activePlan` as part of `SaveData.npcStates?: Record<NpcId, NpcStateSnapshot>` (plan persistence-001). **All seven fields are persisted today**, not only the four (`health`/`needs`/`stamina`/`vigor`) `03-settlements-economy.md` confirmed from the settlement side — `helperAssignment` and `activePlan` round-trip through `SaveData` too. **Explicitly not persisted (confirmed from the NPC side):** `phase`/`pendingAction`/pathfinding/watchdog/`combatIntent`/`carried` inventory (all reset fresh on reconstruction, by design — transient presentation/execution state, not entity identity); NPC **death has no disposal path** — a dead NPC stays in `settlement.npcs` permanently as a "corpse in place" (excluded from the O(n²) separation loop and from dialogue targeting, but never removed), unlike fauna's `fresh→rotting→bones→removed` lifecycle (confirmed via `docs/plans/LOOSE-ENDS.md`'s 2026-08-22 entry, plan `197`).

**Relationships — two entirely separate stores, easy to conflate:**
- `settlement/npcRelationships.ts::NpcRelationships` — symmetric NPC↔NPC pair store (`get(a,b)`/`adjust(a,b,delta)`), one instance per `SettlementsManager`, threaded into `createSettlement` the same way `households`/`economies` are. Persisted since plan persistence-001 (the file's own doc comment states this plainly, unlike `npcState.ts`'s stale per-field comments below) — confirmed against `saveData.ts`. Consumed today only by `ai/socialBehaviour.ts`'s conversation-outcome relationship delta.
- `quests/QuestManager.ts::relations: Map<string, number>` — player↔NPC relation, keyed by `npcName` (not npc id), used for quest availability gates (`RELATION_LEVEL_THRESHOLDS`), `ai/reactionChance.ts`'s reaction-chance bonus, and `ai/npcAssistance.ts`'s willingness-to-help formula. A structurally unrelated model (single scalar per name vs. symmetric pair store) that happens to share the vocabulary "relation" — worth naming explicitly as two different mechanisms so a future reader doesn't assume one derives from the other.

**Work contracts** — `world/workContract.ts::WorkContractRecord` is the sole authority for an NPC's hired-labour commitment (`accepted`/`travelling`/`working`/`payment_due`/`completed`, plus `cancelled`/`invalidated`); `NpcAgent` never keeps a second copy, resolving its own commitment via `workContracts.findByWorker(this.id)` every decision cycle. `ai/npcWorkContract.ts::scoreWorkContractOpportunity`/`selectBestWorkContract` are pure, NpcAgent-free evaluators (`reward + roleSuitability − travelCost − workDurationCost − scheduleConflictPenalty`, compared against zero). This is genuinely NPC-side decision logic over settlement/world-owned state — the record lives in `world/`, the evaluation lives in `ai/`.

**Dialogue-related state** is split three ways with no single owner file:
- `ai/dialogue.ts::BigFivePersonality`/`PausePersonalityParams`/`pickDialogueLine` — need-flavor lines (Polish, personality/need-keyed) and the player-approach pause reaction (trigger distance/look duration/cooldown, all derived continuously from raw OCEAN dimensions).
- `ai/dialogueTemplates.ts` — the v2 dialogue-menu topic generator (role/family/village-flavor sentences), deliberately free of `NpcAgent`/`QuestManager` side effects — callers (the Vue menu) own fetching data and side effects.
- `quests/QuestManager.ts::onInteract()` — quest-driven dialogue overrides (offer/reminder/report lines), which take priority over the flavor dialogue above when a quest is relevant to the interaction.

### The decision pipeline — reconstructed from `NpcAgent.update()`'s `choose` case (`NpcAgent.ts:2312-2393`)

The brief's hypothesized `pressure → decision → strategy/action → world interaction → state change` shape is **confirmed accurate**, with one important nuance the brief didn't anticipate: there are **three independent, structurally identical pressure producers** feeding one arbitration, not one.

```
1. PRESSURE GENERATION (three independent producers, same [0,1]-ish scoring domain)
   a. Needs.ts::generateNeedPressures(needs, options) → NpcPressure[]
      (water/wood/waterDuty/food/idle — physiological + duty meters,
       biased by settlement/household shortage flags passed in via PickNeedOptions)
   b. decisionModifiers.ts::scoreNeedCandidates(pressures, {personality, role})
      → re-scores (a)'s output with small personality/role modifiers
        (conscientiousness biases duty targets; woodcutter/hunter role bonuses).
        Cannot add or remove a candidate, only re-rank an already-active one.
   c. weatherPressure.ts::weatherShelterPressure(currentWeather) → single scalar,
      competes as a 'seekShelter' NpcDecisionTarget
   d. healingPressure.ts::healingPressure(physicalInjury, maxHp, hasHealthConsumable)
      → single scalar, competes as a 'heal' NpcDecisionTarget

2. ARBITRATION (NpcAgent.ts, inline in `choose`)
   pickActionKind<NpcDecisionTarget>([...b, seekShelter: c, heal: d], fallback: 'idle')
   → one winner: a real NeedId | 'seekShelter' | 'heal' | 'idle'

3. TOP-LEVEL SEQUENCING (npcDecision.ts::decideNpcAction, pure/tested separately)
   Fixed priority table (NPC_DECISION_PRIORITY, gaps of 10 for future inserts):
     collapseSleep(100) > seekShelter(90) > need/heal(80, mutually exclusive
     by construction) > scheduledSleep(70) > idle(60)
   → one NpcDecisionKind: collapseSleep | seekShelter | heal | need | scheduledSleep | idle

4. DISPATCH (NpcAgent.ts, per NpcDecisionKind)
   seekShelter → beginSeekShelter()      (activeNeed stays 'idle' — pressure, not a Need)
   heal        → beginHeal()             (activeNeed stays 'idle' — pressure, not a Need)
   need        → ensurePlanForNeed(need) → beginNeed(need)
   scheduledSleep → beginGoSleep()
   idle        → beginIdle(resolveIdleActivity(scheduledActivity, timeOfDay))

5. STRATEGY SELECTION (only for `need`; npcStrategies.ts::selectStrategy, "first
   available candidate wins" — deliberately not a scoring engine)
   e.g. food: playerStorageDelivery → householdFood → economyWithdraw →
        householdExchange → hunt (hunters only) → nearbyFoodSource → gardenGather
   e.g. wood: economyWithdraw → householdExchange → chopDeposit
   e.g. water: householdWater → well
   e.g. waterDuty: fetchDeposit (only one strategy exists)

6. ACTION CONSTRUCTION (NpcAgent.beginNeed()'s per-strategy branches, or
   npcLogistics.ts/npcProfessionWork.ts's pure planners for the shared
   claim→carry→deposit / profession-work shapes) → NpcPlannedAction
   (adapts shared simulation/PlannedAction: destination + durationSec +
   onComplete, optional `next` chain, optional `queueId`)

7. EXECUTION (NpcAgent's own goTo/execute FSM phases drive movement + wait,
   then invoke onComplete — the actual world/household/item mutation)

8. STATE CHANGE (onComplete callbacks: relieveNeed(), Household.deposit()/
   depositFood()/water.add(), SettlementEconomy.add()/depositFood(),
   Inventory add/remove on `carried`, progressActivePlan())
```

**Persistent Plan layer (plan ai-004) sits alongside, not inside, this pipeline.** `NpcAgent.ensurePlanForNeed()`/`reevaluatePlanCompletion()` (checked against the *same* fresh pressures step 1 just computed, before dispatch) track a `NpcPlan{goal, strategy, state, progress, currentStep}` per active `NeedId`-derived `NpcGoalId` (`secureFood`/`secureWater`/`obtainWood`/`fulfilWorkDuty`). It is explicitly "what I want and where I am", never a queued action list — `beginNeed()`'s branches remain the only place that resolves a concrete next `PlannedAction`. A Plan transitions `active ↔ partially_completed ↔ blocked ↔ interrupted → completed | obsolete` and survives interruption (a critical-need/vigor-collapse pre-empt marks it `interrupted`, not cleared — resumed once `choose()` re-derives the same need).

**Interrupt/revalidation semantics are a *separate*, deliberately different precedence from step 3 above** (`npcDecision.ts`'s own doc comment is explicit about this: "the two precedences stay exactly as different as they were... they are not meant to agree"). `NpcAgent.tickCriticalInterrupt()` (throttled to once/second via `CRITICAL_INTERRUPT_CHECK_INTERVAL_SEC`, only while `goTo`/`execute` is in flight) calls `npcDecision.ts::shouldInterruptAction({collapsing, activeNeed, criticalNeed, weatherPressure})`: vigor collapse always interrupts; otherwise **only when `activeNeed === 'idle'`** (a genuinely need-driven action, once started, is never pre-empted by a *different* need or by weather) does a stricter `pickNeed({critical: true})` threshold or `weatherPressure >= WEATHER_SEVERE_SHELTER_THRESHOLD` (0.65) interrupt. An ordinary schedule/hour change never interrupts (unchanged since plan 060). `interruptCurrentAction()` cancels the in-flight `NpcPlannedAction`, marks any active Plan `interrupted` (never cleared), and returns to `phase: 'choose'` for full re-arbitration — there is no separate "resume exactly where I left off" fast path; the next `choose()` tick re-derives everything from scratch.

**Which actions mutate world state vs. only local NPC state:** every `onComplete` callback in `beginNeed()`/`npcLogistics.ts`/`npcProfessionWork.ts` either (a) mutates shared authoritative state reached through injected hooks (`Household.deposit`/`depositFood`/`takeFood`/`water.add`, `SettlementEconomy.add`/`depositFood`/`withdrawFood`, `economy/localExchange.ts`'s atomic claims, `TerrainPreparations.contributeWork`, `PlayerWells.addWork`, `ResourceDeposits.mine`, `foodSources.harvest`/`plant`, `sharpenWeapon`) or (b) mutates only this NPC's own local state (`relieveNeed`, `carried` Inventory, `progressActivePlan`). No action mutates another NPC's `NpcAuthoritativeState` directly — cross-NPC effects only ever happen through a shared intermediate (Household/Economy/`NpcRelationships`/a combat target), never a direct object reference into another `NpcAgent`.

### Work and economy — the NPC-side seam onto `03-settlements-economy.md`'s ownership

Confirms `03`'s wood/ore asymmetry from the NPC side: `npcLogistics.ts::depositWoodHarvest()` routes chop yield through `Household.deposit('wood', ...)` (capacity-capped, overflow to `SettlementEconomy`, gated on real harvest success via `harvestWorldTreeFully`'s outcome — a failed harvest mints nothing); `npcProfessionWork.ts::planOreGathering()` skips `Household` entirely, carrying ore in the NPC's own `carried` Inventory straight to `SettlementEconomy.add(oreEconomicKind(...))` at the stockpile.

**Local resource exchange (plan settlements-npcs-005/014)** is the NPC-side consumer `03` flagged as "outside settlement audit's scope": `npcLogistics.ts::planEconomyWithdraw`/`planHouseholdExchange` both build the identical `goTo(pickup) → execute → next: deposit` two-leg `NpcPlannedAction` via `buildTransferAction()`, differing only in their source (`economy/localExchange.ts`'s `claimEconomySurplus`/`claimHouseholdSurplus`, or `items/foodItems.ts`'s `claimFoodItems` for the food-as-concrete-items case) — both **re-validate live at claim time** (`onPickup`), never trusting the availability check made at decision time (`canWithdrawFromEconomy`/`canExchangeWithHousehold`, both read-only). The claimed goods are carried through the NPC's own `carried` Inventory between the two legs (plan settlements-npcs-014's fix for the earlier closure-variable "lost claim on interruption" risk) — an interrupted trip after claim genuinely loses the goods (accepted tradeoff, same as the ore mine→deposit chain), but no longer silently duplicates or drops them via a dangling closure.

**Profession work** (`npcProfessionWork.ts::planProfessionWork`, dispatched by `Role`) is a pure-function-per-profession dispatch table: miner (`planOreGathering`), hunter (`planArrowCrafting` — arrow *production* during `work`, distinct from the hunt expedition itself which is `NpcAgent`'s own `beginHuntExpedition`, pressure-driven off `food`), farmer (`planFarmWork` — harvest before plant, plant only from a real household-held seed), fisher (`planFishingWork` — real dock, same deterministic `(spot,attempt)` catch rule as the player), guard (`planGuardPatrol` — 3-point deterministic patrol, always succeeds), trader (`planTraderWork` — own-household surplus→economy first, falls back to `planTraderCollection` — a physical pickup from *another* household, plan settlements-npcs-014's new capability), blacksmith (`planBlacksmithWork` — gated on a household-held `whetstone`, confirmed currently dormant since nothing supplies one to a household). `null` from any planner falls back to `commitRoleWork`'s generic idle-at-workplace stand — "profession is a preference, not the only way to act," confirmed unchanged.

**Helper resource delivery (plan 167)** is a fifth, player-configured logistics flow: `helperAssignment.ts::HelperAssignment{targetContainerId, resourceKind: 'food', enabled}` is set externally (Villagers screen), read by `npcLogistics.ts::canDeliverToPlayerStorage`/`planPlayerStorageDelivery` as the `food` need's **highest-priority** strategy candidate when active — gated so the NPC's own real hunger (`FOOD_THRESHOLD_NORMAL`) always wins over delivering surplus away. This is the one strategy list where NPC self-need is explicitly checked as a precondition for a *duty*-shaped candidate rather than the other way around.

### Relationships / social / dialogue / quests — actual ownership

**Social (plan 151)** is entirely `ai/socialBehaviour.ts` + `NpcAgent`'s own `social`/`conversation` FSM glue, over the settlement's own campfire as a shared `Place` (`settlement/places.ts::socialPlaceFor`). Partner selection is deliberately unranked ("same Social Place + available + not self", deterministic lowest-id tie-break — `findConversationPartner`); `extraversion` only changes retry frequency (`conversationAttemptCooldownSec`), never candidate choice. `advanceSocialPairing()` is the one non-pure entry point, called once per settlement per `Settlement.update()` tick (not a global registry) — it atomically reserves both participants, generates one shared duration and one shared outcome closure (`applyOutcomeOnce`, safe against double-invocation) before either side's `beginConversation()` runs, so a third NPC can never be offered either mid-pairing. `conversationOutcome()` is a small deterministic-given-`rng` roll (combined agreeableness + existing `NpcRelationships` value nudges the odds) that adjusts the symmetric `NpcRelationships` store by ±1 — the same order of magnitude as `QuestManager`'s own `QUEST_RELATION_REWARD`.

**Dialogue** has no single file; see State ownership above. `ai/dialogue.ts` (need-flavor + pause reaction) and `ai/dialogueTemplates.ts` (v2 topic menu) both live in `ai/` despite the domain split `01-inventory.md` already flagged (`quests/dialogue*.ts` naming mismatch) — confirmed: there is no `quests/dialogue*.ts` at all; both dialogue modules are physically and correctly in `ai/`, and `01`'s note was about the *quests* domain's own file being small (4 files), not a misplacement of dialogue itself.

**Quests** (`src/quests/`, 4 files: `quests.ts`, `QuestManager.ts` + their `.test.ts`) confirm `01-inventory.md`'s "too small for its own pass" call. `QuestManager` is genuinely quest-agnostic of NPC internals — it never imports `NpcAgent` for state, only `genderForName()` (a pure lookup) and `NPC_QUEST_COMPLETE_SOUND_URLS`; world bindings (fauna kill/find targets, landmarks) are resolved through injected resolver functions (`AnimalTargetResolver`, `LandmarkResolver`), never direct imports — confirmed clean dependency direction (quests depends on ai/fauna/world only through narrow injected function types, never the reverse). `QuestManager.relations` (player↔NPC, by name) is the fourth relationship-shaped store in the domain, entirely separate from `NpcRelationships` (NPC↔NPC, by id pair) — see State ownership.

`ai/reactionChance.ts` and `ai/npcAssistance.ts` are two more small, independent "player interacts with an NPC" decision resolvers that read `QuestManager`'s relation level but don't touch quests otherwise: `computeReactionChance()` (ambient "does this NPC even notice the Hero" roll, gated by trigger distance, group-suppressed by nearby-NPC count) and `computeAssistanceWillingness()`/`resolveNpcAssistance()` (synchronous "will you give me food/water" dialogue-action resolver, explicitly documented as a *different* model from the ambient reaction chance). Neither is routed through `generateNeedPressures()`/`pickNeed()`/`selectStrategy()` — both are one-shot social decisions triggered by player action, structurally parallel to but never touching the pressure/strategy pipeline above.

### Cross-domain seams confirmed from the NPC side

- **NPC↔weather:** confirmed exactly as `02-world-terrain-water.md` found — `WeatherState` threaded live, unmodified, from `gameLoop.ts` through `SettlementsManager`/`Settlement.update()` into every `NpcAgent.update()` call for the frame (never recomputed per-NPC), consumed by `ai/weatherPressure.ts::weatherShelterPressure()` as the `'seekShelter'` arbitration candidate.
- **NPC↔water:** confirmed indirect only — NPCs never call `terrain/waterSample.ts::sampleLocalWater()` directly (that's fauna-side, per `02`); NPC water need is entirely mediated through `Household.water`/the village well `Place`, a settlement/world-object abstraction, not a raw terrain query.
- **NPC↔fauna (combat/hunting/threat):** `ai/npcAnimalThreat.ts` (immediate-threat perception + defend/flee scoring, personality-biased by neuroticism) and `ai/npcCombat.ts` (NPC's own carried-weapon resolution feeding the shared `combat/` resolvers) are the two seams; `SettlementHuntingHooks.queryTarget`/`SettlementFoodSourceHooks` are the injected hooks a hunter's `food`-need branch and a farmer's `work`-block planner read, never a direct `fauna/`/`AnimalAgent` import from `ai/`.
- **NPC↔items/inventory:** `Inventory` is confirmed as the same generic class for both player and NPC carry (`NpcAgent.carried`, `NPC_CARRY_MAX_WEIGHT = 5`); `items/foodItems.ts`'s claim/carry/deliver helpers and `items/weaponMaintenance.ts::sharpenWeapon()` are shared, unmodified for the NPC caller.
- **NPC↔work-contracts:** confirmed above — `world/workContract.ts` owns the record, `ai/npcWorkContract.ts` owns pure evaluation, `NpcAgent` drives the state machine and never duplicates the record.
- **NPC↔persistence:** confirmed above — `SaveData.npcStates`/`SaveData.npcRelationships` (both plan persistence-001) are the two NPC-owned save fields; `SaveData.households` is settlement-owned but consumed identically by NPC logistics.
- **NPC↔quests/dialogue/relationships:** confirmed above — three independent mechanisms (`NpcRelationships`, `QuestManager.relations`, dialogue's flavor-line bank) that share vocabulary but not implementation.
- **NPC↔shared simulation contracts:** `simulation/types.ts::PlannedAction`/`DecisionContext`/`ActionLifecycle`, `simulation/scoreActions.ts::pickActionKind`/`pickHighestScore`/`ScoredAction` are used throughout `ai/` (`npcAction.ts::NpcPlannedAction` extends `PlannedAction<ActionId>`; `NpcAgent`'s own `actionLifecycle` field is a raw `ActionLifecycle`; `npcDecision.ts`/`npcAnimalThreat.ts` both use `ScoredAction`/`pickHighestScore` for their debug-inspectable priority tables, mirroring `fauna/faunaDecision.ts`'s identical shape). Confirmed genuinely domain-agnostic (`@domain shared`, Three.js-free) and consumed identically by `ai/`/`fauna/`/`settlement/`.
- **NPC↔player:** confirmed narrow and one-directional in most cases — `PlayerSocialLookup` (relation/standing by name, threaded from `QuestManager` down through `worldBundle.ts`/`SettlementsManager.ts`/`createSettlement.ts`, kept `NpcAgent` quest-agnostic) is the only injected player-state read; the reverse (`QuestManager.onInteract`/`onInteractObjective`) is driven by player action, not polled by NPCs.

## Shared mechanisms / invariants

- **The pressure/arbitration seam (`NpcDecisionTarget = NeedId | 'seekShelter' | 'heal'`)** is the domain's central extensibility point: three independently-implemented, independently-tested pressure producers (`Needs.ts`, `weatherPressure.ts`, `healingPressure.ts`) compete in one `pickActionKind` call without any of them knowing about the others. Adding a fourth pressure source (the module headers explicitly invite this — `weatherPressure.ts`'s own comment: "this type is the shared decision-target union, not weather-specific") requires no change to the other two producers or to the arbitration call site itself, only a new candidate pushed into the same array. This is the single most important shared mechanism in the domain and is currently undocumented as a *pattern* anywhere (each producer's own file documents itself, but no doc names the pattern or its extension contract).
- **"First-available-wins" strategy selection (`npcStrategies.ts::selectStrategy`)** is deliberately not a scoring engine — order encodes priority. This is a different (simpler) mechanism from the pressure arbitration above and from fauna's `pickHighestScore`-based behaviour scan; documenting it as a genuinely distinct, deliberate choice (not an omission) would help a future agent avoid "fixing" it into a scoring engine.
- **The persistent-Plan layer (`npcPlan.ts`)** sits structurally *beside* the strategy/action pipeline, not inside it — a Plan records intent and progress, `beginNeed()` alone resolves concrete actions. This separation (Goal/Plan vs. Strategy vs. Action, three distinct types: `NpcGoalId`/`NpcPlan` — `NpcStrategyId` — `NpcPlannedAction`) is easy to collapse mentally into "the decision system" as one thing; it is actually three composable layers with three different lifecycles (Plan persists across interruption and reconstruction; Strategy is re-selected every `beginNeed()` call; Action is single-use).
- **The claim→carry→deposit two-leg pattern (`npcLogistics.ts::buildTransferAction`)** is the one generic mechanism behind every economy/exchange/delivery flow (economy withdraw, household exchange, player-storage delivery, trader collection) — composing `economy/localExchange.ts`, `items/foodItems.ts`, `settlement/storageDestinations.ts` rather than reimplementing claims per flow. All five flows share the same live-revalidation-at-claim-time invariant (never trust a decision-time availability read).
- **`ScoredAction<TKind>`/`pickHighestScore`/`pickActionKind` (`simulation/scoreActions.ts`)** is reused identically by `ai/npcDecision.ts`, `ai/npcAnimalThreat.ts`, and (per `STATE.md`) `fauna/faunaDecision.ts` — the same debug-inspectable priority-table shape across NPC top-level decisions, NPC animal-threat response, and fauna behaviour arbitration. Confirmed as a genuinely cross-domain shared mechanism, currently a two-line `STATE.md` bullet with no worked example from any domain.
- **Interrupt semantics are intentionally asymmetric to arbitration semantics** — `shouldInterruptAction`'s own doc comment states this is by design, not an oversight. This is exactly the kind of invariant a state doc should preserve explicitly, since it is easy for a future change to "fix" the apparent inconsistency without realizing it's deliberate.
- **NPC death has no disposal/removal path** (confirmed via `LOOSE-ENDS.md`) — a standing invariant gap (not a bug) that any future NPC-facing feature (loot, funerals, population effects, quest "kill an NPC" objectives) needs to know about before assuming NPCs behave like fauna corpses.

## Recommended documentation changes

1. **Create `docs/state/npc.md`.** The evidence strongly supports this (Stage 1's own guess is confirmed): 57 files in `src/ai/` plus 3-4 NPC-state files physically in `src/settlement/`, zero current-state documentation today, and the domain's own decision-pipeline/state-ownership shape (three independent pressure producers, three composable Goal/Strategy/Action layers, five registries' worth of authoritative state) is genuinely architecturally distinct from settlement generation/household/economy — this is not a case of "small domain, fold it into a sibling doc." Recommended scope: NPC identity/physical profile, authoritative runtime state ownership (and its persistence status, kept current — this domain has already drifted stale twice in the same file), the full decision pipeline (pressures → arbitration → sequencing → strategy → action → execution, including the interrupt-semantics asymmetry), profession work dispatch, work-contract evaluation, combat/animal-threat glue, social/conversation, and a short "dialogue/quests: see elsewhere" pointer (item 3). Explicitly do **not** duplicate settlement generation, household mechanics, or `SettlementEconomy` internals — cross-reference `settlements.md` for those (mirroring how `settlements.md` should cross-reference this new doc for NPC decision content, per `03-settlements-economy.md`'s own recommendation #2/#6).

2. **`docs/state/settlements.md`'s scope should narrow correspondingly** — confirms and extends `03`'s recommendation #2: once `npc.md` exists, remove `settlements.md`'s §NPC section's decision/schedule/dialogue-entry-point content (keep only what's genuinely settlement-owned: NPC↔household/economy resource ownership already covered in §Gospodarstwa, and a one-line pointer "NPC decision-making, needs, strategies, work, combat, social: see `npc.md`"). §Social (conversation/relationships) should move to `npc.md` wholesale — it is NPC-behaviour content (`ai/socialBehaviour.ts`) documented today only because it happened to land in the settlements doc when written, not because settlements own it.

3. **Quests/dialogue/relationships: fold into `npc.md` as a clearly-scoped section, not a separate doc — confirms `01-inventory.md`'s Stage 1 recommendation.** `src/quests/` (4 files) is genuinely too small for its own `docs/state/*.md`; dialogue (`ai/dialogue.ts`/`dialogueTemplates.ts`) is physically and correctly in `ai/`. Recommend one `npc.md` section titled "Dialogue, quests, and relationships" covering: the three-way dialogue-content split (flavor lines / topic menu / quest overrides, and their priority order), the two-relationship-store distinction (`NpcRelationships` vs. `QuestManager.relations` — this audit found this is currently undocumented as a distinction anywhere), and a short quest-mechanics summary pointing at `QuestManager.ts`/`quests.ts` directly for detail (quest content itself — the `QUESTS` array — is data, not architecture, and doesn't belong in a state doc).

4. **Shared simulation contracts (`PlannedAction`/`ActionLifecycle`/`DecisionContext`/`ScoreAction`) do not need their own `docs/state/*.md`** — they are small (11 files, ~250 lines total), stable, and genuinely just a shared vocabulary rather than an owned system with its own runtime behaviour or invariants beyond "here is the shape." Recommend describing them as a shared mechanism once, with a real worked example (this audit's decision-pipeline diagram above is a ready-made one), in whichever domain doc most needs the illustration — `npc.md` is the natural home given the domain has by far the most consumers and the richest example (three independent pressure producers), with a one-line cross-reference from a future `fauna.md`.

5. **Add `@domain npc` (or equivalent) JSDoc tags** to `settlement/npcState.ts`, `npcRelationships.ts`, `npcPhysicalProfile.ts` — reconfirms `03-settlements-economy.md`'s recommendation #9 from the NPC side; these three files are the clearest candidates in the whole codebase for the existing `@domain`/`@system` convention (`rats.ts`, `lodging.ts` already use it for the identical "physical directory ≠ logical domain" situation) and currently carry no tag at all. This is a source-comment change for the reconciliation/implementation stage to apply, not something this audit itself changed.
6. **Consider whether `NpcAgent.ts`'s own `@domain settlements-npcs` tag should become `@domain npc`** (or the combined tag should be reserved for genuinely cross-cutting content) — flagged as a judgment call for Stage 4 rather than a recommendation, since `settlements-npcs` also appears as an established plan-ID prefix and changing the file tag alone without a broader convention decision could create a new inconsistency rather than resolve one.
7. **Fix `settlements.md` S7 and §Social's stale `SaveData` claims** (items #1/#2 in Documentation discrepancies above) — already recommended by `03-settlements-economy.md`; this audit adds that `helperAssignment`/`activePlan` specifically should be named alongside health/needs/stamina/vigor when the fix lands, and that a parallel pass through `npcState.ts`'s own two remaining stale per-field comments (`docs/plans/LOOSE-ENDS.md`'s existing entry) should happen at the same time so the source comments and the state doc don't drift apart again.
8. **`docs/CODE_INDEX.md`'s "NPC AI internals" section** should be expanded (or regenerated, per `CLAUDE.md`'s "fix the generator rather than manually correcting its output" rule if this section is meant to be auto-generated — verify before hand-editing) to list the remaining load-bearing delegate modules named in Documentation discrepancy #5, particularly `Needs.ts`/`npcPlan.ts`/`decisionModifiers.ts` given how central they are to the pipeline this audit reconstructed.
9. **Trim `STATE.md`'s "Settlements / NPCs" section** once `npc.md` exists — confirms `03-settlements-economy.md`'s recommendation #6 with this audit's domain-level view that the overwhelming majority of that section's ~5,000 words is NPC-AI decision-architecture implementation history that belongs in `npc.md` (current-state facts only, no plan-ID narrative) or nowhere in current-state docs at all (pure history → plans/reviews).
