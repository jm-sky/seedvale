## Confirmed current state

### `src/fauna/` is a monolithic-class domain, unlike `ai/`'s 27-module delegation

Where `src/ai/` (per `04-npc.md`) is `NpcAgent.ts` coordinating 27 delegate modules, `src/fauna/` is structured differently: **`AnimalAgent.ts` (4,861 lines) is not just the coordination point but the actual owner of most species data, decision glue, corpse/rabies/harvest lifecycle, and movement** — confirmed by the fact that 9 of the domain's 22 test files (`corpseDecay`, `rabies`, `trapLure`, `frenzyWolf`, `animalRoamingTrips`, `villageAvoidance`, `mountedSpeed`, plus `createFauna.test.ts`'s `measureSlope`/`spawnerLabels`) import their subject symbols directly from `AnimalAgent.ts`/`createFauna.ts`, not from a dedicated pure module. The genuinely extracted pure modules (`faunaDecision.ts`, `faunaCombat.ts`, `waterTraversal.ts`, `predatorHumanDecision.ts`, `dogGuard.ts`, `preyAlertPerception.ts`, `herdCohesion.ts`, `AnimalLife.ts`, `AnimalSpawner.ts`, `huntingHooks.ts`, `animalHarvest.ts`, `animalMeat.ts`, `livestockProduction.ts`) are each small (23-353 lines), Three.js-free, and unit-tested independently — `AnimalAgent.ts` imports and composes all of them, the same "pure logic module + one big stateful class" split `ai/NpcAgent.ts` uses, just with far fewer extracted modules relative to the coordinator's size (13 pure modules vs. `ai/`'s 27).

### State ownership

**Species definitions (deterministic, shared across every individual):** `AnimalKind` (`AnimalAgent.ts:767`, 16 values: wolf/fox/deer/stag/rabbit/duck/boar/bear/horse/donkey/cow/sheep/chicken/rooster/dog/rat) and `ANIMAL_DEFS: Record<AnimalKind, AnimalDef>` (`AnimalAgent.ts:1087`) are the single per-species data table — role (`AnimalRole = 'predator' | 'prey' | 'livestock'`, `AnimalAgent.ts:756`), sociability (`'wild' | 'domestic'`, `:760`), speeds, detect/flee/notice/panic ranges, and capability blocks that follow a consistent "presence of the field IS the capability, no separate boolean" convention: `mount?: MountPointConfig` (riding), `production?: LivestockProductionConfig` (egg/milk), `scavenging?: ScavengingConfig` (rotting/bones food value), `diet?: AnimalDietConfig` (grass/item herbivore or meat diet), `water?: AnimalWaterCapability` (swim capability), `roaming?: [min,max]` (species wander band), `trips?: { water?: WaterTripConfig }` (periodic long-range water trips, deer/stag only). `dog` is `role: 'livestock'` with a `MEAT_DIET` — "eats meat but doesn't hunt" is expressed purely by `role !== 'predator'` gating `findFoodTarget()`'s carcass-seeking branch, not a dog-specific flag.

**Individual runtime state — one `AnimalAgent` instance per animal**, holding directly (not through a separate authoritative-state object the way NPC does via `NpcAuthoritativeState`): `health: HealthState` (shared primitive, see Shared mechanisms), `life: AnimalLifeState` (`hunger`/`thirst`/`stamina`, from `AnimalLife.ts`), `productionReadyAtDays`/`eggPending` (livestock only), `timeSinceDeath`/`meatHarvested`/`corpseHeld` (corpse lifecycle), `frenzied`/`rabid` (two independent disease/quest-state booleans — see Behaviour pipeline), `npcTarget`/`preyTarget` (live combat commitments), `spawnPointId?` (habitat-spawner provenance, metadata only), `ownerHouseId?`/`household?` (livestock ownership, `undefined` for wild fauna — `AnimalAgent.ts:1515-1522`). **There is no `AnimalStateRegistry` analogous to `NpcStateRegistry`** — an `AnimalAgent`'s state lives and dies with the JS object itself; see Persistence below for what actually survives a reload.

**Population/spawner state — `fauna/AnimalSpawner.ts`'s `PreySpawner`** (habitat sites: cave/thicket/grove/wolfDen), a small explicit state machine (`SpawnPointState = 'active' | 'depleted' | 'disabled' | 'recovering'`) independent of any individual `AnimalAgent`: `updateSpawners()` ticks respawn timers in game-days and calls back into the caller to actually construct a new agent; `shouldDeplete()`/`depletionThreshold()` trigger `depleted` once >50% of `maxPreyCount` died in the current cycle; `tickSpawnPointRecovery()` moves `disabled → recovering → active` after `RECOVERY_DAYS` (21) plus a live nearby-population check (`MIN_RECOVERY_POPULATION = 2`). Entirely pure/testable, no Three.js. This is the one piece of fauna population state with its own persisted snapshot (`SaveSpawnPoint`, see Persistence).

**Predator/prey relationships:** a flat `DAMAGE_TABLE: Partial<Record<AnimalKind, Partial<Record<AnimalKind, number>>>>` (`faunaCombat.ts:29`) plus a separate flat `HUMAN_DAMAGE` table for predator→human bites — no relationship graph, just per-attacker-kind lookup tables with a `DEFAULT_DAMAGE = 8` fallback. `MAX_HP: Record<AnimalKind, number>` (`faunaCombat.ts:9`) is the per-species health-pool table.

**Habitat/roaming ranges:** `AnimalDef.roaming?: [min,max]` (species-specific band from `home`, `AnimalAgent.ts:874-879`) with two named tiers (`SMALL_ROAMING_RANGE = [4,9]`, `LARGE_ROAMING_RANGE = [10,24]`) plus a historic flat `DEFAULT_WANDER_RADIUS = [6,16]` fallback for species without an override; livestock gets its own fixed `LIVESTOCK_WANDER_RADIUS` override passed through the constructor instead of `AnimalDef.roaming`. `ROAM_RADIUS = 50` is a separate, larger hard cap (home-relative, not tied to any streamed-region bound) that every food/water/forage search rejects candidates beyond, regardless of species roaming tier. Deer/stag additionally get a periodic long-range "trip" (`AnimalDef.trips.water`, `WaterTripConfig` — cooldown/stay-duration/search-radius, `AnimalAgent.ts:891-902`) that deliberately exceeds their own `roaming` band.

**Water traversal (fauna-side consumption of `02-world-terrain-water.md`'s terrain-owned answer):** `waterTraversal.ts::classifyWaterTraversal(depth, scale, capability)` is a pure function turning a physical depth (from `terrain/waterSample.ts::sampleLocalWater()`, confirmed unchanged from `02`'s finding) into `'dry' | 'wading' | 'swimming' | null` (null = physically impassable for this species) — `wadeDepthFor(scale)` derives wading depth from the species' own `AnimalDef.scale` rather than a new per-species field, and `AnimalWaterCapability.canSwim`/`waterAdapted` are the only two genuinely independent per-species bits (default: can wade, can also swim at generic cost). `AnimalAgent.isWalkable()` is the actual call site (confirmed via constructor wiring at `AnimalAgent.ts:2135`, `isWalkable: (x, z) => this.isWalkable(x, z)`) — used identically by autonomous wander/food/water search and by mounted-rider movement, so traversability can never diverge between the two (per `waterTraversal.ts`'s own doc). `shouldApplyDrowningDamage(mode, staminaExhausted)` gates a flat `DROWNING_DAMAGE_PER_SEC = 5` — damage applies only while actually `swimming` *and* stamina-exhausted, and stops immediately on reaching shore (no separate drowning countdown).

### Lifecycle: spawn → adult/juvenile → death → corpse decay → removal

**Spawn:** `createFauna.ts`'s `SPAWNS: SpawnSpec[]` (wolf×2/fox×2/deer×4/stag×2/rabbit×3/duck×2/boar×2) places wild-fauna "ring" spawns at a settlement-relative offset band per `SpawnProfile` (`open`/`meadow`/`forest`/`water`/`edge`, `SPAWN_RING_OFFSET`), gated by `clearsRiverChannel()` (river clearance, see Ecosystem consequences) and habitat checks (`isDeerEdgeHabitat`/`sampleForestFactor`/shoreline). Cave/thicket/wolfDen habitat spawners (`SPAWNER_RING_OFFSET = [25,45]`) are placed further out and separately tracked as `PreySpawner`s. Herd species (`HERD_SPECIES`: deer/stag/boar tight, rabbit loose, from `herdCohesion.ts`) spawn 1-2 juveniles alongside an adult per a per-species chance table (`JUVENILE_SPAWN_CHANCE`).

**Adult/juvenile:** `AnimalLifeStage = 'adult' | 'juvenile'` (`AnimalAgent.ts:764`) — a juvenile spawns at `JUVENILE_SCALE_FACTOR` of adult mesh scale and matures after `JUVENILE_MATURITY_SECONDS` (600s, ≈1.25 in-game days), ticked by `AnimalAgent.tickMaturity(dt)` every `update()` call (confirmed call site `AnimalAgent.ts:2962`). A juvenile follows its mother within `MOTHER_FOLLOW_RADIUS = [1,3]`, tighter than the herd's own `HERD_FOLLOW_RADIUS`; `pickHerdLeader()` (`herdCohesion.ts:85`) picks the alive herd member with the lexicographically smallest `animalId` — deterministic, no stored/reassigned leader field, so a dead leader is simply excluded next call.

**Death → corpse decay:** `takeDamage()` → `collapse()` (fires `onDeath` once, regardless of cause) → `health.dead = true`. From there, `advanceCorpseDecay()` runs every tick while `!corpseHeld` (a corpse mid-harvest/bury busy-channel is held): `corpsePhaseFromElapsed(elapsedSeconds)` (`AnimalAgent.ts:202`, pure/exported) is the authoritative **`fresh → rotting (20s) → bones (40s)`** timeline both `02-world-terrain-water.md`'s and `04-npc.md`'s cross-references anticipated — confirmed owned entirely by `AnimalAgent.ts`, not a separate module. `canHarvestMeatFrom()` (`:221`) gates knife-harvest to `fresh`-phase-only, unharvested, unburied corpses. A `rotting` corpse gets lightweight FX (`corpseDecayFx.ts`, distance-gated `CORPSE_FX_DISTANCE = 22`, presentation-only per plan 188's "simulation truth vs. presentation" split) and saps nearby live fauna's stamina (`CORPSE_ROT_INFLUENCE_RADIUS = 5`, `CORPSE_ROT_STAMINA_DRAIN_PER_SEC = 0.03`) — a genuine, if small, ecosystem-consequence hook, reusing the existing stamina resource rather than a new status-effect system. `corpseLingerSeconds(meatHarvested)` returns `HARVESTED_REMAINS_LINGER_SECONDS = 90` (post-knife-harvest) or `CORPSE_LINGER_SECONDS = 60` (natural, unharvested); `readyToRemove()` (`:2467`) is the final gate the caller (`Fauna.update`/`createSettlementRats`) polls every tick to know when to `dispose()`/splice the agent out of its live array — **this removal step is the concrete difference from NPC death, which `04-npc.md` confirmed has no disposal path at all** (a dead NPC stays in `settlement.npcs` permanently); fauna corpses are genuinely removed from the world after their linger window.

**Rabies is a separate infection state layered on top of, and overriding, the normal decision pipeline** (`rabid: boolean`, `AnimalAgent.ts:1702`; `infectWithRabies()`, no incubation — the very next tick uses rabid behavior). Transmission is two-vector: a landed bite (`RABIES_BITE_INFECTION_CHANCE = 0.35`, rolled once per `attack()`, never per-tick) or corpse contact (`applyRabiesCorpseExposure()`, `RABIES_CORPSE_CONTACT_RADIUS = 0.5`, `RABIES_CORPSE_INFECTION_CHANCE = 0.5`, only while the corpse is `rotting` and the corpse itself was rabid — each live/corpse pair rolls at most once, tracked via `rabiesExposedAnimalIds`). A rabid animal bypasses `decideFaunaBehaviour()` entirely (see Behaviour pipeline) and single-mindedly chases the nearest live target within `RABIES_TARGET_DETECT_RANGE = 14`, ignoring human/NPC/fire fear.

### Livestock — house-owned, persisted, distinct life cycle from wild fauna

`settlement/livestock.ts` spawns only 7 `LivestockKind`s (horse/donkey/cow/sheep/chicken/rooster/dog) as **plain `AnimalAgent` instances of the same class wild fauna uses** — livestock is not a parallel type, it's the identical runtime class with `ownerHouseId`/`household` set (`AnimalAgent.ts:1518-1522`: "set only for livestock... `undefined` for wild fauna, which has no owner"). Ownership changes concrete behaviour, confirmed at the call site: `findWaterTarget()` (`AnimalAgent.ts:4250`) tries `findTroughTarget()` (the owning household's `AnimalTrough`/`Household.water`) *before* falling back to a natural shoreline search — same pattern `03-settlements-economy.md` described from the settlement side, now confirmed from the fauna side at the exact method. Per-house rolls (`DOG_OWNERSHIP_CHANCE = 0.35`, species weight table, `LIVESTOCK_TWO_CHANCE`) are deterministic from a per-settlement seed.

**Livestock is the one fauna category with real cross-session persistence**, via a `LivestockRegistry` (`settlement/livestock.ts:95`) that mirrors `HouseholdRegistry`/`NpcStateRegistry`'s "same-manager-lifetime registry, `capture`/`serialize` at save time" shape — but with one structural difference the module's own doc calls out: unlike households/NPC state, **no live object survives a settlement unload today**, so `capture()` must explicitly snapshot the currently-loaded `AnimalAgent[]` array (`livestockToSaveRecord()`) rather than reading a state object that already outlives the agent. `LivestockSaveRecord = AnimalSaveState & {settlementId, animalId, kind, ownerHouseId?}` — `AnimalSaveState` (`AnimalAgent.ts:532`) is a **generic per-individual snapshot contract that exists on the `AnimalAgent` class itself** (`snapshot()`/`hydrate()`, `:2403`/`:2432`) but is only ever invoked for livestock; wild fauna and rats never call it (see Persistence below). `snapshot()` persists position/yaw/health/hunger/thirst/**stamina as a ratio, not a raw scalar** (species can have different `staminaCapacity`, so a raw value wouldn't round-trip — `hydrate()` rescales by the restoring individual's own capacity), production-readiness anchor, and corpse state (`timeSinceDeath`/`meatHarvested`). `SaveData.livestock?: LivestockSaveRecord[]` + `SaveData.removedLivestockIds?: string[]` (tombstones, so a corpse that finished its linger and was disposed before save is never resurrected by deterministic respawn) are both optional/sparse, plan `persistence-001`, confirmed via `saveData.ts:545-555` and its validators (`isLivestockSaveRecord`, `ANIMAL_KINDS`, lines 1280-1324).

### Rats — settlement-local pressure/nuisance, plain `AnimalAgent`, deliberately **not** persisted

`settlement/rats.ts` self-tags `@domain fauna @system settlement-rats` despite living in `src/settlement/` (confirmed exactly as `01`/`03` flagged). `ratPopulationTarget()` (pure, `:49`) computes a target population from `(householdFoodCount + settlementFoodCount) / RAT_FOOD_PER_PRESSURE - dogCount * RAT_DOG_SUPPRESSION`, clamped to `[0, RAT_POPULATION_CAP=5]` — reconciled at most every `RAT_RECONCILE_INTERVAL_DAYS = 0.5`, spawning/despawning one rat at a time (`despawnFarthest()` removes the rat furthest from the observer, so shrinkage reads as "wandered off"). Rats are `new AnimalAgent(ANIMAL_DEFS.rat, ...)` — the same class/constructor livestock and wild fauna use — but explicitly **never `ownerHouseId`-tagged** (own doc: "a rat is wild fauna, never `ownerHouseId`-tagged... ticked/reconciled here instead of persisted"). Confirmed: there is no `RatRegistry`/`SaveData.rats` field anywhere in `saveData.ts` — a settlement's rat population is entirely rebuilt from scratch (starting at 0, growing via the same reconciliation loop) every time that settlement streams back in, regardless of what it was at save time. **Real food loss is real**, though: `maybeEatFood()` routes through the exact same atomic primitives every other food consumer uses (`Household.takeFood()`/`SettlementEconomy.withdrawFood()`), gated by a deterministic hashed per-rat-per-bucket roll (`hash01`, not `Math.random()`) so outcomes don't depend on frame timing or iteration order.

## Behaviour pipeline

### Top-level arbitration is a fixed priority table — structurally parallel to NPC's *sequencing* layer, not its *pressure* layer

`faunaDecision.ts::decideFaunaBehaviour()` is confirmed **genuinely parallel in shape** to `ai/npcDecision.ts`'s top-level `NPC_DECISION_PRIORITY` table (`04-npc.md`'s step 3) — both are a fixed `Record<Kind, number>` priority table (`FAUNA_BEHAVIOUR_PRIORITY`, gaps of 10, `faunaDecision.ts:71-85`) walked in descending-priority order (`BEHAVIOUR_ORDER`, sorted once) with an `isBehaviourValid()` gate per candidate, not a dynamically-scored competition. The 13 `FaunaBehaviourKind`s are: `player-attack`/`-ignore`/`-flee` (90) > `player-flee-prey` (80) > `npc-attack-frenzied` (70) > `npc-attack`/`-ignore`/`-flee` (60) > `fire-avoid` (50) > `frenzy-beeline` (40) > `dog-guard` (35) > `predator-normal` (30) > `prey-normal` (20, always valid — the guaranteed catch-all).

**One important structural divergence this audit found, not anticipated by `01-inventory.md`'s "structurally parallel" framing:** `decideFaunaBehaviour()` **never calls `simulation/scoreActions.ts::pickHighestScore`/`pickActionKind`** — it does its own manual ordered scan (first `isBehaviourValid` match wins). The debug/test-only `scoreFaunaBehaviours()` materializes `ScoredAction<FaunaBehaviourKind>[]` for `?debug=1` inspection but doesn't call `pickHighestScore` on them either (it just returns the pre-filtered valid candidates with their static priority as `score`). This exactly mirrors `ai/npcDecision.ts`'s own top-level table, which `04-npc.md` (Documentation discrepancy area, `NpcAgent.ts:2338`) already confirmed is a similarly fixed, non-scored sequencing layer — **the real runtime consumers of `pickHighestScore` in both domains are three sibling sub-decision modules, not the top-level tables themselves:** `ai/NpcAgent.ts`'s need/weather/heal pressure arbitration (`pickActionKind` over `Needs.ts`/`weatherPressure.ts`/`healingPressure.ts` candidates), `fauna/predatorHumanDecision.ts::decidePredatorHumanIntent()` (predator vs. human attack/flee/ignore, feeds `faunaDecision`'s `playerIntent` input), and `ai/npcAnimalThreat.ts::decideAnimalThreatResponse()` (NPC vs. animal defend/flee). All three build a small `ScoredAction[]` array and call `pickHighestScore` directly — confirmed identical shape across all three call sites.

**Fauna has no equivalent of NPC's three-independent-pressure-producer layer (`Needs.ts`/`decisionModifiers.ts`/`weatherPressure.ts`/`healingPressure.ts` competing for one `pickActionKind` slot).** `FAUNA_BEHAVIOUR_PRIORITY`'s table is entirely about **threat/social override behaviour** (player reaction, NPC threat, fire avoidance, frenzy, dog-guard) — it contains no hunger/thirst/need candidate at all. Hunger- and thirst-driven food/water-seeking is resolved **inside** the two catch-all branches (`predator-normal → updatePredator()`, `prey-normal → updatePrey()`, `AnimalAgent.ts:3152-3165`) via ad hoc internal branching (e.g. `AnimalAgent.ts:4058`: `hungerElevated ? findWaterTarget() ?? findFoodTarget() : findFoodTarget()`), never as a scored candidate contesting against `fire-avoid`/`dog-guard`/etc. This means fauna's "pressure → decision" shape the audit brief hypothesized is genuinely **two-tier and asymmetric**: a fixed-priority threat/social override table on top, with un-arbitrated, hardcoded-order need-seeking logic underneath it — not a single unified pressure-competition system the way NPC's `Needs.ts` layer is.

**Three explicit lifecycle gates bypass the whole table before it's ever reached** (`FaunaDecisionGate = 'dead' | 'mounted' | 'rabid'`, `faunaDecision.ts:18`) — confirmed at the actual call sites in `AnimalAgent.update()`: `dead` returns early at `:2889` (corpse decay only), `mounted` at `:2910` (player-driven movement only), `rabid` at `:2979` (single-minded live-target chase, `updateRabid()`). Only once all three are false does `decideFaunaBehaviour()` run.

**Sub-decision modules mirroring this shape**, each self-documented as deliberately matching `predatorHumanDecision.ts`'s testable-pure-module pattern: `dogGuard.ts::resolveDogGuardTarget()` (own-household wolf defense > nearby-settlement assist > nothing, two flat radius tiers, no scoring — a priority-list, not a scored competition) and `resolveDogPestTarget()` (nearest-rat, no tiers); `preyAlertPerception.ts` (recent-vocalization/live-hunting-target alert relevance, consulted only once the prey's own immediate spatial predator check already found nothing — "keep two concepts separate" per its own doc).

`frenzied` (a wolf-den/quest-related state, set via a `markFrenzied()`-style call at `AnimalAgent.ts:2196`) is confirmed **entirely independent of `rabid`** — both are simple booleans on the same class but drive different, non-overlapping behaviours (`frenzy-beeline` toward a `strategicVillage` vs. rabies' single-minded live-target chase); a frenzied predator still participates in `decideFaunaBehaviour()`'s table (at priority 40, or 70 if also facing an NPC target) rather than bypassing it the way `rabid` does.

## Ecosystem consequences

**Grass forage — confirmed shared identically by wild fauna and livestock**, exactly as `01-inventory.md` claimed: `world/createGrassForagePatches.ts::GrassForageService` (`queryNear`/`consume`/`isAvailable`) is injected into every `AnimalAgent.update()` call (`grassForage?: GrassForageService` parameter) and consumed by `findGrassPatchTarget()` (`AnimalAgent.ts:4102`) — gated purely on `AnimalDef.diet.grass` being present, so a wild deer and a domestic sheep resolve through the exact same code path with no species branch. `consume(id, nowDays)` is atomic ("first-wins... the loser's search simply comes up empty next attempt," per the call site's own comment) — the same live-revalidation-at-claim discipline `04-npc.md` found in `economy/localExchange.ts`'s claim seam. Depletion is a **sparse override record** (`GrassForageOverrides`, `patchId → availableAtDays`), not per-patch object state; patch *placement* stays deterministic and unpersisted, only which ids are currently depleted is (`SaveData.grassForagePatches?: Record<string, number>`, `saveData.ts:556-562`, plan fauna-010 §3/§4).

**River-clearance spawn gating — confirmed from the fauna side, matching `02-world-terrain-water.md`'s finding exactly.** `createFauna.ts::clearsRiverChannel(distanceToWaterEdge, clearance)` (pure, `:210`) is the shared predicate; `SPAWN_RIVER_CLEARANCE = 1.5` gates ordinary wild ring-spawns, `SPAWNER_RIVER_CLEARANCE = 6` (wider, since a cave/thicket/den is a physical prop plus the pack living around it) gates habitat spawner placement — both read `ChunkManager.riverShoreDistance`'s signed distance (negative inside water, `null` = no river nearby = no restriction, confirmed as a pinned test contract). A parallel, fauna-owned road-corridor check exists too: `isNearRoadCorridor()` (`:222`) keeps ordinary wild ring-spawn candidates off road corridors, sharing the same `RoadCorridorSegment` geometry `settlement/roadNetwork.ts` produces (per `02`'s finding) rather than a second road representation.

**Resource yield on death — the knife-harvest core is shared verbatim between the player and Hunter NPCs.** `animalHarvest.ts::harvestAnimalIntoInventory(animal, inventory, acquiredAtDays)` is "the single reusable operation" (its own doc) behind both the player's `[E]` harvest (`app/actions/survivalActions.ts`) and a Hunter NPC's post-kill harvest (confirmed at `ai/NpcAgent.ts:3490`'s `onHuntKill()`, which calls through `SettlementHuntingHooks.harvest` → this same function). It marks the corpse harvested, adds `animalMeat.ts::meatKindForAnimal(kind)` (a 5-entry table: deer/wolf/boar/rabbit/cow → dedicated meat kind, everything else → generic `raw_meat`) to the inventory, and opportunistically adds `hide` if there's room — returning `null` (no mutation at all) if the corpse is no longer harvestable or the inventory has no room, so a race between two actors never double-yields. `harvestedRemains.ts` (bones pile + 1-2 large bones + up to 4 meat-scrap props, species-scaled) is purely decorative post-harvest dressing, itself reusing `items/items.ts::createItemMesh(meatKind)` for the meat-scrap visuals — not a second yield source.

**Livestock production** (`livestockProduction.ts`) is a lazy day-anchor readiness check (`livestockProductionReady(readyAtDays, nowDays)`), not a per-frame timer — correct across a settlement being unloaded/reloaded or a time-skip of any length, matching the "lazy resolve against `nowDays`" idiom `items/timedProcess.ts` already uses for drying. `DropLivestockProductHook` drops a real world item (egg/milk `ItemKind`) that only advances the animal's next cycle once actually collected (`onCollected` callback), so a chicken's cycle can't silently advance while nobody's picking up its eggs.

## Cross-domain seams from the fauna side

### fauna ↔ NPC hunting/combat/threat

**Confirmed, with one correction to `04-npc.md`'s framing.** `04-npc.md`'s "Cross-domain seams confirmed from the NPC side" section groups `ai/npcAnimalThreat.ts`/`ai/npcCombat.ts`/`SettlementHuntingHooks.queryTarget`/`SettlementFoodSourceHooks` together as the seams a hunter's/farmer's food-need branch reads. **From the fauna side: only `SettlementHuntingHooks` (`fauna/huntingHooks.ts`) is fauna-owned.** `SettlementFoodSourceHooks` (`world/foodSources.ts:26`) is entirely `world/`-owned — it resolves world-item/crop food sources (berries, planted/wild crops via `cropLifecycle.ts`/`playerGarden.ts`), has zero import of or dependency on `src/fauna/`, and never touches an `AnimalAgent`. A future `npc.md`/`fauna.md` pair should keep these as two separate, differently-owned hooks rather than a single "hunting/food hooks" bucket — grouping them together (as `04`'s prose does) risks a future reader assuming both live in `fauna/`.

**The actual fauna-owned hunting surface:** `SettlementHuntingHooks` (`huntingHooks.ts:24`) exposes exactly two operations — `queryTarget(x, z, range)` (nearest huntable animal, filtered to `HUNT_PREFERRED_KINDS = [rabbit, deer, stag, boar]` in that preference order, predators/livestock/bear never targetable) and `harvest(target, inventory)` (re-validated knife-harvest, see Ecosystem consequences). `queryTarget` applies a **deterministic, seeded population-protection roll** (`shouldSkipForPopulationProtection()`, `:74`) — if a candidate's spawn point currently has exactly one living animal of its kind nearby, a 50% seeded roll (never `Math.random()`, "a persisted-simulation decision... reproducible for a given world state") can skip it, protecting the last individual of a local population from being hunted to extinction by the same NPC repeatedly. `createHuntingHooks(getFauna, getWorldDays)` binds this to the real `Fauna` instance via a **late-bound accessor** (not a direct reference) because `Fauna` is constructed after every `NpcAgent` in `app/worldBundle.ts` — confirmed the same "hooks object forwarded unchanged, `null` before construction is a normal no-op" pattern `04-npc.md` described for `SettlementFoodSourceHooks`.

**The threat surface fauna exposes to NPC-side code is exactly three read-only accessors on `AnimalAgent`, never decision logic:** `isThreateningHuman(): boolean` (`:2219`), `npcAttackTarget: {npcId, homeId?} | null` (getter, `:2230`), `isHuntingLive: boolean` (getter, `:2240`, true while committed to either a live prey or NPC target). `ai/npcAnimalThreat.ts::senseImmediateAnimalThreat()`/`decideAnimalThreatResponse()` and `dogGuard.ts::resolveDogGuardTarget()` both consume caller-built candidate lists (`ThreateningAnimalCandidate[]`/`DogGuardWolfCandidate[]`) assembled from these three accessors plus `faunaCombat.ts::combatTargetForAnimal()` (a `CombatTargetHandle` wrapping `takeDamage`/`isAlive`/`getPosition`) — confirmed **never a direct import of `AnimalAgent` decision logic from `ai/`**, matching `04-npc.md`'s claim precisely. `ai/npcAnimalThreat.ts::decideAnimalThreatResponse()` is structurally identical to `fauna/predatorHumanDecision.ts::decidePredatorHumanIntent()` (both build `ScoredAction<...>[]`, call `pickHighestScore`, same file-header cross-reference to each other) — this is a genuine "same shape, independently reused" mechanism worth naming explicitly in future docs (see Shared mechanisms).

**Combat itself is genuinely shared, narrow, and bidirectional-in-caller:** `faunaCombat.ts::combatTargetForAnimal()` reuses `shared/HealthState` and routes `applyDamage` straight to `AnimalAgent.takeDamage(amount, 'npc')` — the *same* method the player's own melee/ranged resolution calls (`app/gameLoop.ts:978`/`:1134`: `animal.takeDamage(critResult.damage, 'player')`, going through `combat/criticalHit.ts`'s shared resolver). There is exactly one damage/critical-hit pipeline for player and NPC attacks against fauna; fauna itself never duplicates it.

### fauna ↔ settlements

**Confirmed and materially extended beyond `03-settlements-economy.md`'s brief mention** (see State ownership → Livestock/Rats above for full detail). Summary for the integration table: livestock's `ownerHouseId` changes concrete water/diet-target resolution (household trough before wild forage) and is the one fauna category with real `SaveData` persistence, mirroring the settlement registries' `initial*`/`snapshot*` idiom but with the added wrinkle that no live object survives an unload (an explicit `capture()` snapshot step is required). Rats drain real `Household`/`SettlementEconomy` food through the same atomic primitives every other consumer uses, but are themselves never persisted — a settlement's rat population fully resets to a freshly-reconciled state on every reload.

### fauna ↔ terrain/water

**Confirmed from the fauna side, matching `02-world-terrain-water.md` exactly — no new findings, this audit only verifies the fauna-side call sites.** `terrain/waterSample.ts::sampleLocalWater()` → `AnimalAgent.isWalkable()` (via `waterTraversal.ts::classifyWaterTraversal`) is the single physical-water-presence consumer; river/road spawn-clearance (`clearsRiverChannel`/`isNearRoadCorridor`) reuses `ChunkManager.riverShoreDistance`/`RoadCorridorSegment` rather than a second geometry representation.

### fauna ↔ shared simulation contracts

**Confirmed identical usage to NPC's, at the type level** — `AnimalAgent.ts` imports `ActionLifecycle`/`adoptPlannedAction`/`createActionLifecycle`/`DecisionContext`/`PlannedAction`/`ScoredAction` from `simulation/` (`:25-33`) and builds `PlannedAction<FaunaActionKind>` (`:3255`) through `adoptPlannedAction(this.actionLifecycle, this.pendingAction, next)` (`:3258`) — the exact same generic contract `ai/npcAction.ts::NpcPlannedAction extends PlannedAction<ActionId>` uses, per `04-npc.md`. **The `pickHighestScore`/`ScoredAction` usage nuance documented in Behaviour pipeline above (top-level tables don't call it; sub-decision modules do) applies equally to both domains** — this refines rather than contradicts `04-npc.md`'s claim that the two domains use "identical shape."

### fauna ↔ persistence — the most consequential finding of this audit

**Confirmed and precisely scoped: individual wild-fauna state is intentionally not persisted at all, and this now has three concrete tiers, not a single yes/no answer:**

1. **Persisted:** spawner *lifecycle* only (`SaveSpawnPoint{id, state, deathsThisCycle, disabledAtDay}`, `saveData.ts:165-170`) — deliberately excludes position/type/kind (deterministic from seed/settlement) and any actual animal/runtime state; a restored `active` spawner simply starts its respawn timer from 0. Livestock *individuals* (`SaveData.livestock`/`removedLivestockIds`, full `AnimalSaveState` per individual). Grass-forage patch depletion (`SaveData.grassForagePatches`, sparse overrides, `world/`-owned but consumed identically by wild fauna and livestock).
2. **Not persisted, but deterministically reconstructed identically every session:** wild-fauna ring-spawn population (fixed `SPAWNS` table + seeded placement), and — the more interesting case — **rats**, which despite living in `settlement/` and superficially resembling livestock (owned lifecycle, per-settlement) are explicitly excluded from persistence by their own module doc and reconciled fresh from a live formula every time a settlement (re)loads.
3. **Not persisted, no reconstruction guarantee at all:** a wild animal's individual position/health/hunger/rabies-infection/frenzy state simply ceases to exist on unload — a wolf that was rabid, mid-chase, or juvenile at save time comes back as a fresh deterministic spawn on reload, with no attempt to replay or approximate its prior state. `AnimalSaveState`/`snapshot()`/`hydrate()` exist as a **generic capability on the `AnimalAgent` class itself** (usable by any individual) but are, by policy, only ever invoked by `livestock.ts` — wild fauna's spawn site (`createFauna.ts`) never calls `snapshot()`, and nothing in `createFauna.ts` reads a `SaveData` field for individual animal state.

This confirms and sharpens `01-inventory.md`'s "likely NOT" guess into a fully-verified three-tier picture, and is a materially bigger finding than a single missing-field gap: it means a future feature (e.g. a wolf pack the player has been tracking, a rabies outbreak in progress, a specific named quest animal outside the deterministic `wolfDen`/spawner id scheme) cannot assume any wild individual survives a session boundary today.

**Riding is the one place this boundary is player-visible today:** `SaveData.player.riding` (mount) stores a livestock `animalId` specifically because — per `saveData.ts:44-45`'s own comment — "only livestock kinds have a deterministic id" that survives a reload; a player who somehow mounted a wild animal (not currently possible, `mount?: MountPointConfig` is only configured for livestock kinds in practice) would have no way to reconnect the save reference to a real post-reload individual.

## Shared mechanisms / invariants

- **`terrain/slopeConstraint.ts`** — confirmed reused identically by `PlayerController.update()`, `NpcAgent.steerTo()`, and `AnimalAgent.steerToward()`/movement stepping (`stepWithSlopeAndCollision`, imported at `AnimalAgent.ts:34`) — reconfirms `02-world-terrain-water.md`'s finding from the fauna side with the exact import.
- **`shared/HealthState`/`shared/StaminaState`** — `faunaCombat.ts` re-exports `HealthState`/`createHealthState` directly from `shared/HealthState` (no fauna-specific health type), and `AnimalLife.ts` builds on `shared/StaminaState`'s `drainStamina`/`restoreStamina`/`getStaminaRatio` — the same primitives NPC/player health and stamina use.
- **`ai/npcMovementWatchdog.ts` is imported directly by `fauna/AnimalAgent.ts`** (`createMovementWatchdog`/`tickMovementWatchdog`, `:9-13`) — a genuine, if narrow, **reverse-direction dependency**: unlike every other fauna↔NPC seam in this audit (which flow through an injected hooks object so `ai/` never imports concrete `fauna/` classes), this is fauna importing a concrete `ai/`-owned module directly, with no hook indirection. Worth flagging explicitly in any future `npc.md`/`fauna.md` split, since it's an exception to the otherwise-consistent "hooks object, no direct cross-import" convention this audit and `04-npc.md` both otherwise confirmed.
- **`simulation/{types,scoreActions,actionLifecycle}`** — confirmed reused with identical shape to `ai/`'s usage (see Cross-domain seams above); the one nuance (top-level tables are fixed-priority scans, not `pickHighestScore` consumers) applies to both domains equally and is worth stating once in whichever doc introduces the pattern, rather than re-derived per domain.
- **`ui/agentStatusLabel.ts`** — `AnimalAgent.ts` imports `createAgentLabel`/`createLabelBar`/`applyBarPercent`/`updateAgentLabelDistanceState` (`:36-44`) from the same module presumably backing NPC name/HP-bar labels (not independently verified against `ai/`'s own usage in this audit, since NPC's UI/label code was out of `04-npc.md`'s scope too — flagged as a likely-shared mechanism, not fully confirmed).
- **`world/waterMirror.ts::AGENT_RENDER_LAYER`** — `AnimalAgent.ts` calls `assignRenderLayer` (`:48`) to keep itself out of the water-mirror reflection pass, confirmed matching `02-world-terrain-water.md`'s "layer-gated away from NPC/fauna/grass" finding from the water side.
- **`items/Inventory`/`ItemKind`** — hunting yield (`raw_meat`/species-specific meat/`hide`) and livestock products (egg/milk) both land in the same generic `Inventory`/dropped-item system player and NPC carry use; no fauna-specific item container exists.
- **`AnimalSaveState`/`snapshot()`/`hydrate()`** is a generic per-individual persistence contract that exists once, on the `AnimalAgent` class, but is policy-gated to livestock-only call sites (`livestock.ts`) — worth documenting as "the mechanism exists generically; only one category of caller uses it" rather than "livestock has its own separate persistence code," since a future feature wanting to persist a specific wild individual (a tracked quest animal, say) already has the primitive available and would only need to add a call site, not build new machinery.
- **Non-deterministic `Math.random()` inside wander/food/water candidate search** (`findWaterTarget()`/`findForageTarget()`/`wander()`, confirmed at `AnimalAgent.ts:4256` etc.) — unlike the deterministic-roll discipline `huntingHooks.ts`/`rats.ts` explicitly apply to population-protection and food-drain rolls, ordinary movement-target search uses raw `Math.random()`. This is consistent with fauna individual state never being persisted (per the Persistence finding above, there is nothing for this randomness to desynchronize against across a save/reload), so it does not appear to violate `CLAUDE.md`'s determinism invariant in practice — but it is worth a maintainer's explicit acknowledgement rather than leaving the distinction implicit, since the codebase does apply seeded rolls elsewhere in the very same class for population-sensitive decisions.

## Recommended documentation changes

1. **Create `docs/state/fauna.md`.** The evidence supports this at least as strongly as `04-npc.md` supported `npc.md`: 24 source files (46 with tests, ~11,600 lines), zero current-state documentation today, and a genuinely distinct architecture from both `settlements.md` and a future `npc.md` (monolithic-class-with-13-pure-modules rather than one-coordinator-with-27-delegates; a two-tier fixed-priority/ad-hoc-need-seeking behaviour shape rather than NPC's three-producer pressure competition). Recommended scope: species/`AnimalDef` capability-flag conventions, individual state ownership (and its persistence status — livestock persisted, wild fauna and rats deliberately not, spelled out as the three-tier picture this audit confirmed), the corpse/decay/rabies lifecycle, livestock/rats as the two settlement-adjacent fauna categories with a one-line pointer to `settlements.md`/a future `npc.md` for their *settlement*-side half, the behaviour-pipeline two-tier shape (with an explicit note on how it differs from NPC's), and the hunting/threat/combat seams onto NPC. Cross-reference rather than duplicate `water.md`'s water-traversal ownership and `combat.md`'s shared damage pipeline.
2. **Route NPC↔fauna seams to avoid duplication between a future `npc.md` and `fauna.md`.** Recommend: `fauna.md` documents what fauna *exposes* (the three read-only threat accessors, `SettlementHuntingHooks`'s exact contract including the population-protection roll, `combatTargetForAnimal()`) as its own "surface for other domains" section; `npc.md` documents how the Hunter/Farmer/threat-response *consumes* them, cross-referencing `fauna.md` rather than re-deriving the hook shapes. This mirrors `04-npc.md`'s own recommendation #4 pattern (shared simulation contracts documented once, in the domain with the richest example) — here, fauna is the natural owner of the hook *shape*, NPC of the *consumption logic*.
3. **Explicitly document the three-tier fauna persistence picture** (livestock persisted / wild-fauna-and-rats deterministically-reconstructed-but-unpersisted / no wild-individual-state-survives-at-all) in `fauna.md`, and add a one-line cross-reference from wherever `docs/architecture/ARCHITECTURE.md`'s save-schema section or a future `docs/state/persistence.md` (per `01-inventory.md`'s Stage 2 plan) enumerates `SaveData.livestock` — a reader of the save schema alone would not otherwise learn that wild fauna is a deliberate, explicit exclusion rather than an oversight.
4. **Correct the `SettlementHuntingHooks`/`SettlementFoodSourceHooks` grouping** wherever `04-npc.md`'s content eventually lands in `npc.md` — state plainly that these are two independently-owned hooks (`fauna/` vs. `world/`) that happen to both feed food-need strategy resolution, per Documentation discrepancy #4 above.
5. **Add a `CODE_INDEX.md` entry for the fauna domain** naming `AnimalAgent.ts` as the central coordinator/state owner, `AnimalSpawner.ts` as the population-lifecycle module, and `huntingHooks.ts` as the NPC-facing seam — mirroring the gap `04-npc.md` already found and recommended fixing for `ai/`'s own under-listed "NPC AI internals" section.
6. **Note the `ai/npcMovementWatchdog.ts` reverse-direction import** (fauna importing directly from `ai/`, the one exception to the hooks-only convention) in whichever doc states the general "domains talk through hooks, not direct imports" principle — likely a short callout in `fauna.md`'s own "shared mechanisms" section, since it's the kind of detail a future refactor could accidentally "fix" into a fauna-owned duplicate watchdog without realizing the sharing was deliberate.
7. **`STATE.md`'s §Fauna section should be trimmed once `fauna.md` exists**, following the same pattern `03`/`04` already recommended for §Settlements/NPCs — move plan-ID-narrated history out, keep only a short current-state summary pointing at `fauna.md`.

## Open questions

- Should `settlement/livestock.ts` and `settlement/rats.ts` physically move into `src/fauna/` at some point, or is keeping them in `src/settlement/` (next to the `Household`/`SettlementEconomy` state they read) the right long-term call given they're both already correctly `@domain`-tagged? This mirrors the exact open question `03-settlements-economy.md` and `04-npc.md` both left open for the NPC-state files under `src/settlement/` — recommend a future architectural pass decide the `npcState.ts`/`livestock.ts`/`rats.ts` question together, as one convention, rather than three separate one-off calls.
- This audit did not verify whether `AnimalAgent.ts`'s continued growth (4,861 lines, the single largest file in the domain and comparable in scale to `NpcAgent.ts`'s 4,654) warrants a module-extraction pass analogous to the 2026-09-03/04 NPC refactor `04-npc.md` cited. Given how much of the class is genuinely per-species-data-table (`ANIMAL_DEFS`) rather than behavioural logic, a future maintainer should distinguish "large because of one big data table" from "large because of insufficient extraction" before deciding whether this is a real problem — this audit did not attempt that judgment, only observed the file size.
- Is the `Math.random()`-vs-seeded-roll split noted under Shared mechanisms/invariants (movement-target search unseeded, population-protection/rat-eat rolls seeded) an intentional, documented policy ("only population-affecting/persisted-adjacent decisions need determinism") or an implicit convention that's never been stated as a rule? Recommend whoever writes `fauna.md` ask this explicitly rather than assume — the current code is internally consistent but the boundary isn't written down anywhere this audit found.
- `AnimalDef.mount`'s riding capability and `player/PlayerSkills.ts::ridingSpeedMultiplier` (referenced by `mountedSpeed.test.ts`) sit partly in `fauna/` and partly in `player/` — this audit did not trace the full riding flow (out of scope per the assignment's "do NOT do a full player/items audit" boundary) beyond confirming `AnimalDef.mount`'s presence-based capability flag and that only livestock kinds have deterministic ids for `SaveData.player.riding` to reference. A future `06-player-items.md` audit should confirm the player-side half of this seam.
