## Runtime architecture

Seedvale is a browser 3D sandbox built with **Three.js + WebGL2 + Vite + TypeScript**. The game/simulation layer remains vanilla Three.js; the overlay UI is a hybrid of vanilla DOM modules and Vue 3 + Tailwind v4.

`src/app/createApp.ts` is the composition root. The world systems that are rebuilt together live in `src/app/worldBundle.ts` as `WorldBundle` — terrain/ocean, settlements/fauna, renewable resources/items, player-placed fires/tents/traps/containers/wells/gardens, terrain preparations, caves, drying racks, beehives, work contracts, runtime transport orders, resource-site inventories, grass forage, river water quality, and more. The full field list and rebuild/lifetime invariants are canonical in [ARCHITECTURE.md](./architecture/ARCHITECTURE.md) and `src/app/worldBundle.ts`, not restated here. Fresh boot can return with a few background systems still represented by inert stubs; they are replaced in place when background initialization completes. File-level map: [CODE_INDEX.md](./CODE_INDEX.md).

## Major systems

Each subsection below is a short current-state summary. Domain documents hold the detail; plans and their implementation notes hold the history of *how* a feature was built.

### World / terrain

Procedurally chunked, streamed terrain with instanced vegetation/rocks, tree lifecycle, weather/seasons as deterministic functions of `(seed, elapsedDays)` including a canonical `storm` type with lightning/thunder, mountains, and rivers with their own hydrology/geometry. Inter-settlement road routing is river-aware (plan `world-terrain-023`): the A* search prices every candidate edge against canonical river water, so each road↔river crossing is a deliberate worldgen `ford`/`bridge` record on the route itself (`settlement/roadRiverCrossing.ts`) rather than an accident of elevation; terrain and local-water sampling project a declared ford, and a declared bridge is projected into one deterministic `RoadBridgeSpec` (`settlement/roadNetwork.ts`'s `bridgeSpecOf`/`bridgesNear`, `terrain/roadBridge.ts`'s shared footprint/deck-Y query) with V1 procedural deck+pier presentation instantiated once by its owner chunk (`world/createBridge.ts`, `ChunkManager`), a road-height-shaping suppression inside the open span (never the canonical river carve), and a shared movement-ground query (`ChunkManager.sampleSurfaceGround`/`sampleBridgeDeck`) player/NPC/fauna traversal all read (plan `world-terrain-033`). Procedural landmarks now include the classic set (`monolith`/`stoneCircle`/`smallRuins`/`ruins`/`cemetery`) plus coastal/road/natural variety (`boat`/`shipwreck`/`tower`/`oldTree`/`wagon`, plan world-terrain-027) with dedicated GLBs, stable `landmarkId`s, and generic `interact_landmark` quest hooks. Settlement cemeteries are assignment-driven landmarks (`cemeteryAssignment.ts` / `cemeteryPlacement.ts`): each settlement has exactly one active cemetery (dedicated, or shared between two nearby `SM`s); rare abandoned wilderness cemeteries are a separate low-chance path and never become a settlement's burial destination. Ocean, lakes, day/night, fog and post-processing are implemented. Short-lived environmental blood traces are created directly from player/NPC/animal damage entry points and rendered via one capacity-fixed instanced mesh, resynced to whatever traces are within the streamed-terrain radius; not persisted, carried across an in-session `WorldBundle` rebuild the same way other player-positioned world objects are. Walk-in caves are Cave V2 on the **heightfield representation** (`createCaves()` / `src/world/caves/`, plan `world-terrain-019`): each accepted `CaveTopology` builds one retained `CaveHeightfieldRepresentation` (`floorY`/`ceilY` per node, deterministic base surface minus `mouthCarveDepth`), and that field is the **only production spatial authority** — presentation, terrain mouth, player ground / floor / ceiling (`Caves.queryGround` / `sampleFloor` / `sampleCeiling`), strict occupancy (`Caves.occupancyAt` / `contains`), horizontal wall containment (`Caves.resolveHorizontal`), the hysteretic interior flag (`Caves.queryInterior`, independent `player` audio and `camera` fog channels) and third-person camera space all read it through `caveHeightfieldQuery.ts`, with the representation-neutral hit / occupancy-slack / hysteresis contracts in `caveGroundQuery.ts`. There are no cave wall colliders: `PlayerController` resolves ordinary world colliders first, then `resolveHorizontal` pushes the capsule out of rock and the low rounded fringe along the field's `gap` gradient (identity outdoors, on the hillside above a tunnel and in the open-sky mouth; stateless; no teleport-back). Presentation is the **heightfield mesh**: `caveHeightfieldMesh.ts` / `caveHeightfieldPresentation.ts` assemble the welded floor/ceiling mesh, mouth underside mask and contour-driven rocks synchronously on the main thread, streamed by the unchanged 55/80 m controller through a nearest-first queue (the controller no longer registers anything else on relevance). The cave mouth is a real terrain hole: `createCaves()` registers a per-cave `TerrainCutout` (`caveTerrainCutout.ts`, contour = `mouthOpeningAt`) with `ChunkManager.registerTerrainCutouts()`, which applies it on every chunk mesh build/rebuild (`terrainCutout.ts` marching-squares clip of the indexed chunk grid; survives unload/reload, dig, scorch, prepare; not a persisted modification). The SDF field / column index / collider beads / extraction worker / `sdfCaveMesh.ts` are deleted; `topologyToCaveDefinition` / `CaveVolume` remain catalog/streaming leftovers. The isolated `?caveHeightfieldTest` harness imports the production representation, mesher and spatial helpers (`src/debug/caves/`) without booting `WorldBundle`. Caves come in two production archetypes (plan `world-terrain-020` Stage A): the long-standing `natural` recipe and a longer `adventure` one (`src/world/caves/adventureTopology.ts`) whose folded main route is ~3x the natural exploration length and always carries one readable junction, a dead-end side branch to a side chamber, a deep chamber and a final chamber, addressed by stable role ids. Both recipes share one set of terrain-aware route primitives (`caveRoute.ts` — overburden adaptation, traversable floor grade, total drop, disconnected-passage clearance); `CaveTopology` stays representation-neutral (no archetype/role node kinds) and the archetype is runtime metadata on `Caves.archetypeOf(caveId)`. Assignment is pure and deterministic in `caveArchetype.ts`: existing sites are ordered home-first, the first one whose adventure topology is *actually accepted* becomes the guaranteed home adventure cave (never a relabelled natural cave, never a synthesized site), every other site takes an independent 15% adventure roll, and a rejected adventure attempt falls back to the unchanged natural recipe so no cave is lost. Adventure layouts are priced against an adventure-specific heightfield cell budget before any grid is allocated; the global heightfield config is unchanged. Nothing is persisted — archetype is reproducible from seed + sites + home. Milestone C's fauna half is done (plan `fauna-019`): `Caves.resolveHabitat(caveId, entityHeight)` / `queryGroundIn` / `resolveHorizontalIn` (`src/world/caves/caveHabitat.ts`) resolve a standable interior home chamber and a deterministic entrance route from `CaveTopology`'s segment graph, O(1) per `caveId`, no presentation dependency, no player hysteresis — consumed by fauna's own `AnimalHabitatBinding` (see `fauna.md`). The quests/NPC halves (`quests-progression-008`, `npc-027`) remain open. Plan `world-terrain-020` Stage B adds read-only adventure content anchors (`Caves.contentAnchors` / `contentAnchorsOf`, roles `sideTreasure` / `finalTreasure` / `wagon` / `support` / `crate` / `lantern`) resolved against each cave's own heightfield floor; natural caves expose none. Stages C–E are done: two unlocked cave chests via explicit-Y `WorldGeneratedContainerSpec`, streamed adventure props (wagon/support/lantern), and dark interior `scene.fog` from the camera `queryInterior` channel. Plan `world-terrain-037` materializes adventure `crate` anchors as low-value systemic `WorldGeneratedContainers` (deterministic cheap loot, crate visual) instead of presentation-only props. Plan `world-terrain-022` adds deterministic, presentation-only interior rock/boulder clutter for both archetypes (`caveInteriorRocks.ts`): placements are resolved once per cave (like content anchors) from `CaveTopology` node/segment geometry sampled against the same retained heightfield, steer clear of content-anchor footprints, and render through a handful of shared instanced templates (`buildInstancedProps`) rather than per-rock meshes; gated by `?debugDisableSystems=caveInteriorRocks`.

### World locations / discovery

Coarse world features (lakes, mountain peaks, cemeteries, the abandoned mountain mine, and similar) are classified from deterministic terrain sampling, not authored data — geometry/identity are always a pure function of `(world seed, location id)` and are never persisted. The abandoned mountain-mine landmark (plan `world-terrain-017`) is catalog-owned (`WorldLocationKind` `abandonedMine`, `Caves.abandonedMine()`): `mineId` is independent of `caveId`, binds to an existing eligible `natural`/`adventure` production cave on a coherent massif when possible, otherwise adds one dedicated mountain site after generic archetype assignment so adventure/dungeon guarantees and authored cave quests are not retargeted. Mine gold is world-resource-owned (plan `world-018`): ordinary `ResourceDeposits` fed by landmark-owned definitions with authoritative XYZ + `WorldSpatialContext`, optional explicit finite reserve, and the existing sparse `SaveData.resourceDeposits` remaining override — not a second mining system. Settlement cemeteries are resolved by canonical assignment (`ChunkManager.resolveCemeteryForSettlement`), not nearest-landmark search; abandoned wilderness cemeteries are discovered by a bounded chunk probe. Player discovery/knowledge state and active navigation targets are a separate, real, save-persisted progression layer on top of that catalog; map projection is a pure rendering transform over both, not a third source of truth. Settlement markers follow `LocationKnowledge`, not Fog of War: the home village is confirmed at New Game / restore, and any other village is confirmed on physical arrival inside `VillagePlan.boundary`. Exploring a map cell still does not reveal the settlement sitting on it. Deferred static-world research (plans `quests-progression-047` / `world-030`) is owned by `WorldKnowledgeResearch` (`src/world/locations/worldKnowledgeResearch.ts`): a worker-pool `worldKnowledge` job below tile/mesh that reconstructs corridors inside the worker from a cheap main-thread snapshot, with quest progress and owner-keyed guard/hunter local-knowledge wait/selection (plan `npc-050`) as peer consumers — not a second location registry. Once that research resolves and its authored delay elapses, the ready result transfers into the asking NPC's own authoritative `playerFollowUp` (`ai/npcPlayerFollowUp.ts`, on `NpcAuthoritativeState`) rather than being revealed directly — one reusable "NPC owes the Player something" primitive delivered idempotently through `world/locations/npcPlayerFollowUpDelivery.ts` whether the Player asks again manually or the NPC approaches proactively via the existing idle-duty seam and a narrow non-Vue runtime callback (`ai/npcInitiatedDialogueRequest.ts`).

### Settlements / NPCs

Plan-first villages (`VillagePlan` → `SettlementDef`), streamed settlements. `settlementPlanCache` remains the runtime owner of generated defs; the disposable `settlement-definitions` worldgen cache hydrates that same map across reloads (plan settlements-014). `VillageIdentity.character` (`default` | `closed`) is a generation-time archetype from a dedicated seed salt — home and OUTPOST stay `default`; forest is more likely `closed`. Closed villages reuse the existing palisade ring with higher perimeter coverage, one torch pair per inland road entrance, a stronger guard remainder-weight in `professionStaffing.ts`, a contextual caution bias in existing social evaluators, and a generation-time configured predator-pressure fill around nearby closed sites. MD/LG/XL may carry a settlement-owned satellite pasture outside `VillageBoundary` (`VillagePlan.pasture`, plan settlements-009) with a well, trough, fence marker and local path; SM/OUTPOST do not. Pasture/paddock fence segments clear final local path corridors at planning time and register the same `PropPlacement[]` as settlement OBB colliders (plan settlements-018) — gaps stay open. Pasture is not a `Pasture` entity and does not take livestock ownership from the household. Eligible MD/LG/XL settlements may also roll a horse-vendor paddock (`VillagePlan.paddock`, plan settlements-013) — fenced footprint with an entrance gap, trough, food-only haystack and live vendor horses on livestock origin slots; SM/OUTPOST never do. Horse training is per-`AnimalAgent` progress (derived ordinary/trained/warhorse labels) and survives ownership transfer and save/load. The public square is a planned `VillagePlan.plaza` disk (plan settlements-011), distinct from terrain `clearings.core`: central physical props share `pickPlot()`, LG/XL get a merged paved surface minus reserved footprints, and woodcutters skip plaza-protected trees without a second tree registry. Initial NPC professions are assigned at generation time by `professionStaffing.ts` from adult workforce + food/resource/scale signals; children and reserved home NPCs are not restaffed, and normal settlements no longer grow an extra resource family. After staffing, `professionFamilySurnames.ts` assigns one profession-inspired surname per worldgen household (`family-*`); authored `family-story-*` residents keep their own names, and reserved home identities stay Piotr Leśniewski / Anna Leśniewska and Marek / Kasia Hornblower. `SettlementEconomy` (settlement-owned bulk stock) and `Household` (one family's own wood/water/food/items) are the two resource registries settlements host; both persist and carry across an in-session `WorldBundle` rebuild. Agricultural households with an adult Farmer receive a one-time real seed stock in `Household.items`; loaded Farmers keep using `planFarmWork()`, and unloaded non-home settlements apply a bounded crop-definition catch-up at stream-in (plan settlements-npcs-030). One `seed_*` item is a sowing unit: player, Farmer and aggregate catch-up all consume ×1 seed to produce one `CropPlacement` / one off-screen batch whose logical population and base yield come from `CROP_DEFS` (plan world-023). Cultivated harvest recovers real `seed_*` goods through a shared species `healthySeedRecovery` resolver (plan settlements-npcs-031) into player `Inventory` or `Household.items`; aggregate catch-up applies the same formula as a closed-form net seed change, so a failed/zero yield can still shrink the stock and stop later sowing. NPC work-completion production (stock, item, and mixed `ProductionDef` recipes) commits through one synchronous executor (`src/economy/productionExecutor.ts`) called from existing `npcWork.ts` adapters — not a production manager or tick. Persistent blocked inputs are compact `productionShortages` on the settlement economy (plan settlements-npcs-017), exposed as diagnostic NPC pressure, not a second AI loop. NPC authoritative state — health/stamina/vigor/needs/`physicalInjury`/`injuryRecoveryUpdatedAtDays`/`temporaryConditions`/`helperAssignment`/`activePlan`/`postDeath`/`graveVisits`/`personalInventory` — is physically hosted here (`NpcStateRegistry`) and persists as part of `SaveData.npcStates`, but the decision architecture, work dispatch, combat integration, and social/dialogue behaviour that consume it are canonical in `npc.md`, not documented here. Derived injury severity (plan npc-025) is not persisted. Player temporary conditions (`SaveData.playerConditions`) persist separately from base SPEA. Land ownership (`LandOwnershipRegistry`/`SaveData.ownedLandPlots`) is a separate, simpler player-facing mechanic. Settlement-structure condition/repair (plan settlements-007) is a third settlement-owned registry (`SettlementStructureStateRegistry`, sparse, persists as `SaveData.structureStates`), keyed by stable `VillageBuildingPlan.id`: V1 adapts residential houses only, sharing one quote/begin/contribute/completion transaction (`settlement/structureCondition.ts`, reusing `world/condition.ts`/`world/repair.ts`) between player `[R]` repair (`app/actions/placementActions.ts`) and an NPC's own household-house repair pressure (`ai/NpcAgent.ts`'s `structureRepairHooks`).

### Fauna

Predator/prey/livestock ecosystem built on one shared `AnimalAgent` class — wild fauna, livestock, and rats are the same class distinguished only by ownership/registration. Behaviour is a fixed-priority threat/social-override table on top, with hunger/thirst-seeking resolved ad hoc underneath (structurally different from NPC's unified three-producer pressure competition). Persistence is four-tier plus a sparse exception: livestock persists per individual (an explicit pre-save capture step), spawner lifecycle persists thin, ordinary wild individuals are unpersisted with only the population deterministically reconstructed, settlement rats persist per individual (plus a settlement-owned infestation record for storage damage and nest destruction), and explicitly declared persistent habitat occupants persist as the same `AnimalAgent` snapshot with a fauna-owned slot tombstone. Individual variants (`animalVariants.ts`) start with a deterministic wolf-den alpha (same `AnimalKind`, per-animal multipliers); the quest `markDangerous()` trait composes on the same modifier path. Rats' food-driven carrying capacity is independent of dogs; dogs hunt rats physically and reduce nest-gated infestation replenishment. Player melee/ranged acquisition reads `settlement.rats` alongside livestock and wild fauna. A persistent habitat occupant's home may now be a real walk-in cave (plan `fauna-019`): `AnimalHabitatBinding` (`src/fauna/animalCaveHabitat.ts`) resolves against `Caves.resolveHabitat`, and `AnimalAgent`'s shared ground/containment seam (`snapY()`) prefers that cave's own stateless floor/wall query over surface `sampleHeight` while resident; a committed trip walks the interior↔entrance route before/after its surface leg. The decorative habitat-spawner `cave` type is renamed `rockDen` to stop colliding with real caves (save-compatible: the on-disk id segment is unchanged). `AnimalAgent.update()` is internally split into full-rate sections (corpse/decay, sensing, targeting, decision, and the whole timers/needs/maturity/production/drowning life tick) and two cadence-gated ones — behaviour/movement and presentation — driven by one shared stateless importance policy (`animalUpdateCadence.ts`) used identically by wild fauna and livestock (plan fauna-028). Skipped time is accumulated and flushed in full, the movement step is capped, and combat/threat/flee/hunt/mounted/led/owned/trip/cave/swimming/near-player cases stay at full rate; off-screen animals still age, feed and decide, and camera visibility is not an input. Habitat condition is a derived, lazy read model (`Fauna.getHabitatPressure`, plan fauna-031): one on-demand snapshot of population/mortality/predator/food pressure for a managed spawner, runtime-cached in world time, never persisted and never ticked per frame. Wild inter-animal discovery uses a fauna-owned runtime spatial hash rebuilt once per `Fauna.update()` (`faunaProximity.ts`, plan fauna-042): sensing/targeting visit covering cells instead of the full wild array, livestock stays on the explicit `huntableLivestock` encounter set, and managed-spawner occupancy stays fauna-041 `spawnPointId` membership filled from a reusable count map rather than a per-frame `filter().map()` snapshot.

Death hands cargo off atomically and idempotently to a persistent ground `saddlebags` container (`items/container.ts`'s `pickupPolicy: 'empty-to-item'`, `world/animalPackHandoff.ts`), namespaced `animal-pack:<originSettlementId>:<animalId>`; the corpse itself is unaffected and decays/harvests normally. Arrival inside the canonical return radius clears the episode through the same predicate whether or not a lost-livestock quest is watching, so a live self-return is always reflected as `returned` without player involvement.

### Items / player

`Inventory` / `ItemKind` / a single held-tool slot own item ownership and equip state — `Inventory` itself is generic (player *and* NPC). The player can explicitly give owned items to a living NPC (`giveItemCountToNpc` / `giveItemInstanceToNpc` → `NpcAuthoritativeState.personalInventory`); NPC equipment remains derived from that inventory at action time, with no persistent equipment slots. `ITEM_CATALOG[kind].capabilities` is the single source of truth for every tool-requirement gate; there is no hand-written per-tool check left. Default player look is UBC Peasant/Ranger/Knight (body-armor outfit swap) with UAL1 clips from `ual1_player.glb`; an equipped `arms` pauldron is a skinned overlay on that live skeleton (plan items-player-039). Adventurer is `?player=adventurer`. The mixer drives idle/walk/run/melee, bow stand-ins, sneak crouch, swim, jump, torch/sword idle, camp crouch, and downed death clips when those names exist; camp `lieDown()` stays a procedural tip. The player has the same shared `HealthState` as NPCs/fauna, plus its own survival pools (stamina/vigor/hunger/thirst) and an eight-skill progression system (sneak/survival/traps/defense/archery/riding/medicine/repair, XP-only). Targeted skill use reuses existing gaze `Interactable`s; Repair's first world consumer is player camp equipment (tent/bedroll/platform). Medicine scales medicinal herb `conditionTreatment` potency via `evaluateSkillCompetence(Medicine, Survival support)` (plan items-player-043); Survival awards forage XP and a bounded herb discovery radius. Buildable construction progress (player-placed wells, standing torches, palisades, residential houses, terrain preparations) shares one actor-neutral `contributeWork(id, amount)` seam with NPC work-contract execution — see `player-systems.md`'s Work Contracts section, the single canonical home for that mechanism. Finite systemic treasure (plan world-024) is world content, not quest content: `treasureSites.ts` reconstructs site/chest/key definitions from seed + landmarks; chests are `WorldGeneratedContainers`; lock mutations persist as sparse `unlockedTreasureContainerIds`; matching keys are generic instance-backed `key` items with site-owned ids. Authored one-shot world pickups such as the dark-forest treasure map persist consumption as sparse `consumedWorldPickupIds` (plan quests-progression-036), so rebuild/reload cannot rematerialize a collected source even if the item later leaves inventory. Cave treasure uses the same explicit-Y `WorldGeneratedContainerSpec` seam (adventure chests via `caveTreasureContainerSpecs`, ordinary crates via `caveCrateContainerSpecs`, plan world-terrain-037). ### Quests / progression

`QuestManager` with definitions, objectives, stages and multi-stage world interactions. A stage may keep one `objective` or declare `objectives` with `all`/`any` completion and optional forward transitions to another stage or outcome (plan quests-progression-032); existing single-objective quests are unchanged. Quest NPC references (giver, `talk_to_npc` / `talk_to_npc_choice` targets, relation prerequisites/consequences) use stable `NpcId`; display name is presentation only. Authored names are bound to ids at composition-root materialization from the settlement's deterministic family order. Quest availability prerequisites (player↔NPC relation, prior quest resolved outcome, local settlement reputation/renown) gate whether a `not_offered` quest may be offered; once offered/active, later prerequisite drops do not revoke it. Relation levels (`stranger`/`acquainted`/`friendly`/`trusted`) remain the relation prerequisite vocabulary. Each `QuestDef` has authored `outcomes` with explicit item rewards and consequences (player↔NPC relation, settlement reputation/renown); objective completion is not resolution, and there is no implicit giver/talk-target relation bump or global quest EXP. Report, `talk_to_npc`, `talk_to_npc_choice`, and authored stage `dialogueActions` wait for an explicit player dialogue action from `QuestDialogOverride.actions` — opening NPC dialogue or selecting the help topic does not itself advance or resolve those stages. Stage `dialogueActions` and talk choices may author ordered live-social `reactions` (plan quests-progression-050): first match may change the NPC reply, add consequences, or start a quest-topic cooldown without replacing canonical outcomes. Stage `dialogueActions` are a non-terminal escape hatch: they advance only the current stage (used by `zwiadowca` when a seed never placed a stag in range) and may apply the same `QuestConsequences` seam without resolving the quest. `onInteract` collects explicit quest actions for an NPC across all definitions before falling back to a giver reminder or offer, so one quest's in-progress line cannot hide another quest's required talk. `labelMarker` prefers a currently actionable required talk/action (`talk_to_npc` / `talk_to_npc_choice` / available stage dialogue action) over giver in-progress; reminder plus generic abandon is `…`, not `?`. Each runtime `NpcAgent` gets an initial marker projection even when quest state is clean, so New Game / stream-in / settlement reload do not wait for another quest mutation. `herb` (rare medicinal) is merchant stock at 12 coins as a reachability fallback for `ziola-dla-anny`; mint/yarrow are common renewable world forage (not Kupiec stock). World-problem quests exist end-to-end (bound to a specific `AnimalAgent`/livestock/wolf-den instance via an injected resolver — `QuestManager` never imports fauna to scan it itself). Home **injured cow / Medicine alternative** (`quests-progression-057`) is a third generated def on that same opportunity layer, keyed by household cow `animalId` (`world:injured-cow:<settlementId>:<animalId>`): the giver proposes slaughter, but a branching `any`-mode stage lets the Player instead resolve it by treating the exact bound cow through the ordinary Medicine targeted action. Home **Hunter I–III** (`hunterProfessionQuests.ts`) is a linear profession chain on the home Hunter giver. After `hunter_iii_complete`, **Hunters Brotherhood introduction** (`huntersBrotherhoodIntroduction.ts`, plan quests-progression-048) may materialize a story-exposure invitation when a deterministic two-settlement adult cast resolves; completing it records `hunters_brotherhood_joined` as the only membership fact — no faction record, profession rewrite, or extra SaveData. **Hunting-ground investigation** (`huntersBrotherhoodInvestigation.ts`, plan quests-progression-049) reuses that same binding: it binds to one real bound-settlement deer `thicket` `PreySpawner` deterministically ranked from live `Fauna.getHabitatPressure()` snapshots (condition severity, then max component pressure, then stable `spawnerId`; no candidate when none is currently unhealthy), reuses `interact_spawner` for the field-inspection stage, and captures the pressure snapshot exactly once into a compact quest-local `QuestHabitatPressureObservation` (`QuestProgressEntry.observation`) through a narrow `QuestLifecycleHooks.onInteractSpawnerMatched` hook and `QuestManager.recordObservation()` — never a second fauna/ecology state, never polled per frame. Home **lost treasure expedition** (`quests-progression-027`) binds a real dungeon's own `finalTreasure` anchor plus an ordered `storyFind` trail (abandoned camp → leader pack with the identity-backed `expedition_journal` → final expedition evidence), resolved via `Caves.dungeonChambersOf()`'s stable route order rather than array position; a generated sponsor (trader → miner → other adult) offers it, and a second stakeholder (an adult from a different household, home first then nearest neighbor settlement) is optional — its absence reduces the terminal choice to `journal_to_sponsor` / `keep_journal_and_treasure` rather than inventing one. Exact chronicle ownership is required to continue; the specialist's explicit dialogue choice is a real coin transfer into `personalInventory` or a one-document favour (`chronicle_reference` in a world chest). Distinct paid/favour outcomes reveal the search-area id through existing `LocationKnowledge` without materializing the estate. Stage and terminal `QuestStageEffect`s (`reveal_location`, `transfer_item_instance`, `transfer_animal_ownership`, `discard_carried_container`, `request_world_knowledge`) are applied by `QuestManager` through existing injected seams (plan quests-progression-029 / quests-progression-047); `reward.items`, `consequences`, and `horseRewardAnimalId` remain sugar over the same dispatch. Lost-hunter bow hand-in and bear-cave casket return bind instance/container ids into the def at materialization — `createApp`'s physical resolver only checks world predicates (`requireItemInstanceId` / carried container), not those quest ids. Terminal states include `failed`, `invalidated` (a technical restore/rebuild state, not an outcome) and `abandoned` — a conscious player opt-out on an `active` quest (plan quests-progression-033), distinct from both. Offer *exposure* is capped independently of how many `not_offered` candidates are eligible: `QuestManager.onInteract()` admits at most one `normal`-urgency `not_offered` candidate plus one `urgent` one per giver, selected by a pure, deterministic `rankQuestOfferCandidates()` (urgency, story continuation, relation, authored `QuestOfferPolicy.priority`, then a stable id tie-break) — already-`offered`/`active` quests keep their slot/reminder regardless, and `QuestOfferPolicy.exposure: 'story'` opts an authored linear-history offer out of the cap and out of generic decline entirely. Ordinary giver `active`/`ready_to_report` quests also occupy a derived per-giver capacity of 2 (plan quests-progression-034); `urgency: 'urgent'` / `exposure: 'story'` bypass that active cap, and the cap never hides another giver's required talk, hand-in, or report on the same NPC. `labelMarker` treats a live gather hand-in as `✓` even while the quest is still `active`, outranking a simultaneous `!`; inventory changes dirty markers only when an active gather stage exists. Generic abandon actions stay visible in a single-quest dialogue and move behind titled `QuestDialogTopic`s when several quest contexts share an NPC. A declined offer returns to `not_offered` with a short world-clock cooldown (`QuestProgressEntry.offerSuppressedUntilDay`, reusing the existing `QuestWorldTimeLookup`) instead of reappearing immediately; `list()`/`labelMarker()` only surface a `not_offered` candidate the cap would actually expose, not every eligible one. `QuestAbandonment` (default: allowed, no penalty) drives a generic "give up" `QuestDialogAction` on an `active` giver quest, re-reading live state so a stale callback can't replay its optional `QuestConsequences` twice; a story quest whose `await_quest_outcome` stage resolves through a carried physical item (bear-cave treasure, lost-hunter's bow, suspicious-transport evidence, old-bones' signet, dungeon bandit marked valuable) sets `allowed: false` since a generic opt-out there would strand that carried instance outside any quest tracking. None of this touches the authoritative world problem a quest observes — decline/abandon only change quest-layer bookkeeping. Procedural landmarks carry a stable, save-free derived id and back a `interact_landmark` objective. Quests whose NPC does not yet know the exact place opt into deferred `worldKnowledge` (`request_world_knowledge` / `receive_world_knowledge` / `interact_bound_landmark`): `QuestManager` owns persisted research progress, an injected async resolver owns place lookup, delay uses `getElapsedDays()`, and `{worldKnowledgeClue:id}` expands only after the NPC has revealed the clue (plan quests-progression-047 — pilots `slad-przy-monolicie`, generated `old-place-secret`, chronicle-search ruins). Immediate-known places stay on concrete `interact_landmark`. Quest progress (including `resolvedOutcomeId` after a complete/failed outcome, optional `journal` heard-line stamps, optional `worldKnowledge` research slots, and player↔NPC relations) persists, keyed by stable NPC id (legacy name-keyed relation saves are normalized at composition root); `list()` projects note text from the live def (plan ui-input-021). This player↔NPC relation store is structurally unrelated to the separate NPC↔NPC relationship store — see `npc.md`'s Relationships, social, and dialogue section. LLM quest generation remains unimplemented. Architecture recon (do not replace `QuestManager`; fan-out, generic effects, external resolution): [2026-09-13--quest-system-architecture-recon.md](./reviews/2026-09-13--quest-system-architecture-recon.md).

`ReputationManager` (`src/reputation/`) owns local, per-settlement reputation (five `-100..100` dimensions: trust/competence/benevolence/courage/integrity) and renown (`0..100`) — a settlement-scoped social standing independent of `QuestManager`'s per-NPC relations and of `BadgeManager`'s earned-badge/history record. Changes only through an explicit, already-resolved `SocialConsequence` a caller applies (quest completion or stage dialogue-action selection via `QuestManager`'s seam; a first-time cemetery grave disturbance whose deterministic social-exposure roll succeeds; or a confirmed player kill of a dangerous wild animal — see below) — the manager never infers social knowledge from world/quest state itself. Grave disturbance has no *global* badge: social exposure + settlement reputation/renown are its only global-scope social consequence (its settlement-local counterpart is `BadgeManager`'s `grave_robber` — see below). NPC spontaneous-reaction chance reads local renown (not reputation's dimensions); the Character Screen shows one known settlement at a time (current village when the player is inside one, otherwise last visited / a still-known previous selection, with home as fallback), chosen from `LocationKnowledge` rather than every generated settlement, or "Brak lokalnej reputacji" when none are known. No NPC-by-NPC gossip simulation or decay yet; dangerous-animal-deed renown does lazily cross-settlement-propagate through `SocialNewsLedger` (see below), but that is a narrow, bounded seam, not a general witness/gossip system. See `npc.md`'s Relationships, social, and dialogue section and `persistence.md`'s Reputation/renown row.

`BadgeManager` (`src/badges/badges.ts`) also owns a second, settlement-scoped Settlement Known Deeds namespace (plan quests-progression-059), type-distinct from its global `BadgeId`: `caretaker` (5 known player shovel-burials of an animal corpse attributed to one settlement's local area — never NPC/automatic cleanup of the same corpse), `healer` (5 successful Medicine treatments of that settlement's NPCs or household-owned livestock — never self-treatment or a failed/no-op attempt), and `grave_robber` (the first socially-exposed cemetery grave disturbance for that settlement — a secret/unexposed disturbance never counts). Progress is reported by already-resolved call sites (`survivalActions.ts::startBuryCorpse`, `medicalTreatmentActions.ts::completeMedicalTreatment`, `groundActions.ts`'s grave-exposure branch) through `recordAnimalCorpseBuried` / `recordSuccessfulTreatment` / `recordExposedGraveDisturbance`; `BadgeManager` never imports or owns `ReputationManager` — a newly earned badge's optional one-shot `SocialConsequence` is applied by the caller through the existing `applySocialConsequence` seam (`createApp.ts`'s single `handleSettlementBadgeUnlock` fan-out: toast, consequence, Character Screen refresh). `grave_robber`'s unlock carries no extra consequence, so the same exposure event's existing `GRAVE_DISTURBANCE_EXPOSURE` penalty is not doubled. Earned local badges show under the selected settlement on the Character Screen ("Znany tutaj z"), independent of and never mixed with the global badge list; a not-yet-earned local badge is never revealed. Persisted as optional `SaveData.badges.settlements` (save v49).

Dangerous-animal-deed reputation (plan quests-progression-019, `src/reputation/animalDeeds.ts`) turns one confirmed player kill of a dangerous wild animal into a distance-independent `SocialNewsSignal` — a pure, deterministic resolver, separate from `socialExposure.ts`'s random risk roll. `gameLoop.ts` captures a `PlayerAnimalKillContext` (kind, fauna-owned `AnimalAgent.dangerSignificance`, position) at the moment of death for both melee and ranged kills, and reads `QuestManager.hasSocialOutcomeClaim(animalId)` *before* the lethal hit (not after — `AnimalAgent.collapse()` synchronously advances a bound `kill_target_animal` stage past the point that check can still see it) to suppress the generic deed when a quest already owns that kill's social outcome. Explicit exhaustive species baselines (`deer` is a deliberate zero case; `fox`/`wolf`/`bear` scale by `dangerSignificance`, so an alpha wolf or quest-marked dangerous individual yields more than a normal one of the same species) feed the resolver; distance attenuation itself (`reputationFactor` zeroes out by 1500m, `renownFactor` — reaching further — by `MAX_ANIMAL_DEED_INFLUENCE_DISTANCE` at 3000m) is applied later, per settlement, not baked into the signal. No cooldowns or kill counters in V1.

Lazy social-news propagation & reputation catch-up (plan quests-progression-022, `src/reputation/SocialNewsLedger.ts`) replaced a synchronous "scan every settlement within 3km at kill time" model — `onPlayerAnimalKill` in `createApp.ts` used to call `settlementsWithinDistance()` against `SettlementsManager.peekDef()`, which is not a cheap cache read: a miss runs the full `generateSettlementDef()` pipeline, so a cold-cache kill could synchronously materialize hundreds of settlement definitions and freeze the main thread. The kill path now only ever enqueues a small `SocialNewsEvent` (`SocialNewsLedger.enqueue`) and catches up `SettlementsManager.getLoaded()` (already-built settlements only, no grid scan, no `peekDef` for unknown cells) through `catchUpSettlements()`. `SettlementsManager` also fires a narrow `onSettlementAvailable(id, x, z)` callback once a settlement (home or a streamed-in neighbor) actually finishes building; `createApp.ts` wires this to the same lazy catch-up, so a settlement that streams in later still resolves any still-pending event within its 7-day TTL (`ANIMAL_DEED_NEWS_TTL_DAYS`), without ever generating an unknown `SettlementDef`. A settlement that catches up an event becomes a knowledge carrier: reputation dimensions are always computed from distance to the event's real origin (never reset by relaying), while renown can relay through an existing carrier at a fixed `SOCIAL_NEWS_RELAY_FACTOR` (`0.75`) decay per hop — deterministic best-source selection, never summed across multiple carriers. The ledger is app/session-owned (a sibling of `ReputationManager`, not part of `WorldBundle`), so an in-session `rebuildWorldBundle()` keeps pending news; only New Game resets it. Bounded queue (`MAX_PENDING_SOCIAL_NEWS_EVENTS = 256`, oldest dropped first) and TTL-based expiry (`prune()`, run on enqueue/catch-up, never per-frame) keep it small; `LocationKnowledge` (player discovery) is never consulted. Persisted as optional `SaveData.socialNews` (save v40).

### Persistence

IndexedDB-backed (`src/persistence/`), named save slots (up to 8). `SaveData` is a serialization format, not a runtime authority: each domain owns its state and serializes it once per save; restore is construction, not a two-phase hydrate-then-apply pass. A real migration pipeline validates on both write and read, and a write-time integrity guard refuses to overwrite an existing slot whose current record fails to parse. Still not a full simulation snapshot — ordinary wild individual fauna and NPC/animal execution state (phase/pending-action/pathfinding/combat-intent/carried work inventory) are deliberately excluded from every save; settlement rats, infestation `{ storageDamaged, nestDestroyed }`, and sparse persistent habitat occupants persist. NPC personal belongings persist as part of `npcStates`. `Continue` is closer to, but still not equivalent to, serializing the complete living world.

- Ordinary boot always goes through the Start Screen (`src/main.ts` → `src/ui/createStartScreen.ts`), including a confirmed-empty save list: zero rows opens the New Game form (player name, save name, seed) instead of creating a world, and deleting the last save returns to that same state. Only a storage-read failure bypasses the screen. The player name is per-save `WorldConfig.player.name`, passed into `createApp()` as an explicit New Game option — not a global profile.

## Important shared concepts

Prefer extending existing shared mechanisms instead of creating parallel systems.

- `WorldBundle` — lifetime/rebuild boundary for the world systems ([ARCHITECTURE.md](./architecture/ARCHITECTURE.md)).
- `HealthState` — shared health/damage/death (`src/shared/HealthState.ts`) used by fauna, NPCs and the player.
- `StaminaState` — shared physical-effort capacity (`src/shared/StaminaState.ts`) used by fauna and NPCs.
- `VigorState` — NPC daily physiological budget (`src/shared/VigorState.ts`); collapse gates sleep through the existing NPC FSM. Not used by fauna.
- `PlayerNeeds` — player stamina/vigor/hunger/thirst pools (`src/player/PlayerNeeds.ts`), reusing `StaminaState`/`VigorState`. A shared `PhysicalEffortIntensity` (`light`/`moderate`/`heavy`) seam costs real elapsed busy-action time in stamina/vigor for physical work, decoupled for compressed work (well construction, terrain-prep time-skip).
- `WaterSource` — shared well/lake/river/ocean drink/fill abstraction (`src/world/WaterSource.ts`); future polluted/treated sources should reuse it. `WaterQuality` is `safe` / `unsafe` / `undrinkable`: well is always `safe`, ocean always `undrinkable`, lake always `unsafe` (drinkable with a warning), and river is resolved per pickup point via `WorldBundle.riverWaterQuality` (`riverWaterQualityResolver.ts`) — not a blanket `safe`. A player-built well can additionally require a carried `rope` to draw water, or carry an uncovered-well direct-drink risk — see [player-systems.md](./state/player-systems.md) and [water.md](./state/water.md).
- Shared simulation contracts — `PlannedAction`, `ActionLifecycle`, `DecisionContext`, `pickHighestScore` in `src/simulation/`. NPC + fauna adapters; the richest worked example (three independent pressure producers competing through one arbitration) is documented in [npc.md](./state/npc.md); fauna cross-links rather than repeating it.
- Buildable `contributeWork(id, amount)` — the actor-neutral seam every player-built object (wells, standing torches, palisades, residential houses, terrain preparations) shares with NPC work-contract execution: clamp to remaining work, credit only accepted work, progress lives on the object's own entry and is never duplicated onto the contract. Canonical home: [player-systems.md](./state/player-systems.md)'s Work Contracts section.
- `SettlementEconomy` — settlement-owned bulk stock (`src/economy/`). Not player `Inventory`. Persisted (`SaveData.settlementEconomies`, required) and carried across an in-session `WorldBundle` rebuild. `food` is a concrete `ItemKind` `Inventory` (mirroring `Household.items`), not part of the scalar bulk stock. Source-attribution ledger, exact-once realization and entitlement accrual (plan settlements-004) live in `src/economy/sourceLedger.ts`, embedded per-economy and persisted as `SettlementEconomySnapshot.sourceAccounting` (optional/sparse — never reconstructed from stock, inventory, resource-site inventories or `history()`). Attribution starts only at delivery (`oreTransportDemand.ts::creditDeliveredOreToStock`, given order-carried `economicSourceId` provenance), never at mining time.
- `Household` — one family's own wood/water stock plus concrete food/misc items (`src/settlement/household.ts`), sitting between NPC carrying and `SettlementEconomy`. Persisted (`SaveData.households`, sparse/optional) and carried across an in-session `WorldBundle` rebuild the same way `SettlementEconomy` already was.
- `SettlementStructureStateRegistry` — settlement-structure condition/repair state (`src/settlement/structureStateRegistry.ts`, plan settlements-007), keyed by stable `VillageBuildingPlan.id`; sparse/optional (`SaveData.structureStates`) and carried across an in-session `WorldBundle` rebuild the same way `Household`/`SettlementEconomy` already are. Shares one quote/begin/contribute/completion transaction (`src/settlement/structureCondition.ts`) between player and NPC repair — never a second repair implementation per actor.
- `NpcAgent` / `AnimalAgent` — central behaviour integration points. `NpcAgent` also carries a small generic `Inventory` as a brief hold between extracting a world resource and delivering it (not persisted — see [npc.md](./state/npc.md)).
- `Inventory` / `ItemKind` / `HeldTool` — item ownership + single held-tool slot; `Inventory` itself is generic (player + NPC). `src/items/primaryWeapons.ts` owns explicit persisted primary melee/ranged choices (`primaryMeleeWeapon` / `primaryRangedWeapon` in `SaveData`) behind the HUD shortcut buttons. Runtime Combat Mode (`src/player/playerCombatMode.ts`, plan ui-input-018) tracks whether that configured primary is currently drawn; it is not persisted and starts inactive on load/new game. `[X]` sheathes when active and redraws `lastActiveWeapon` (melee-first fallback) when inactive. HUD melee/ranged buttons become contextual sheathe/switch actions while drawn.
- `TreeLifecycle` / `harvestWorldTree*` — tree growth + multi-stage chop (`src/world/treeLifecycle.ts`, `treeHarvest.ts`), plus deterministic branch gathering with its own regeneration cooldown.
- `QuestManager` — quest progress, outcomes and player↔NPC relations.
- `ReputationManager` (`src/reputation/`) — per-settlement reputation (five `-100..100` dimensions) and renown (`0..100`); independent of `QuestManager`, changed only via an explicit `SocialConsequence` a caller applies. Cemetery grave disturbance uses `socialExposure.ts` for a one-shot day/night + Sneak roll before that consequence; a dangerous-animal kill uses `animalDeeds.ts`'s deterministic species-baseline + distance resolver instead (plan quests-progression-019).
- `ChunkManager` — terrain sampling, streaming and environment-facing world queries; one shared terrain material (`buildChunkGeometry.ts`) with shader-injected bare-ground dirt colour detail from `src/assets/sharedSurfaceDiffuseTextures.ts` (async 1K JPG, influence 0 until loaded).
- `TerrainVisualHorizon` (`src/terrain/terrainVisualHorizon.ts`, plan `world-terrain-035`) — the shared exterior presentation contract: a pure `fadeStart`/`opaqueAt` distance pair derived only from `chunkSize`/`loadRadius` (never `unloadRadius` hysteresis), stored on `WorldBundle.terrainVisualHorizon` and recomputed on every rebuild. `weatherVisuals.ts::capOutdoorFogToTerrainHorizon` caps outdoor `scene.fog` by it (day/night → weather → horizon cap → cave-interior override, applied in `gameLoop.ts::applyDayNight`) so terrain-dependent meshes (settlement buildings, the distant cave mouth proxy) fade out before unsupported streamed terrain can be exposed. Presentation-only — never affects simulation, streaming or persistence. The distant cave mouth proxy (`createCaveMouthProxy`, plan world-terrain-026) uses its own fog-enabled `createCaveMouthProxyMaterial()` to participate in this cap, while full cave-interior presentation keeps its separate fog-exempt materials unchanged.
- `createCaves` / Cave V2 — streamed walk-in interiors (`src/world/caves/`); the retained `CaveHeightfieldRepresentation` is the single spatial authority (`world-terrain-019`): presentation mesh assembled on the main thread with a real terrain mouth cutout owned by `ChunkManager`; a cheap dark mouth proxy (`createCaveMouthProxy`, plan world-terrain-026) covers that cutout whenever the full presentation is inactive — presentation-only, same `mouthOpeningAt` contour, no spatial authority; `queryGround` / `sampleFloor` / `sampleCeiling` (player ground, neutral hit + underground-miss hysteresis in `caveGroundQuery.ts`), `occupancyAt` / `contains` / `spatialContextAt` (strict, stateless — camera boom, swim eligibility, torch; `spatialContextAt` is the shared `surface | cave:<id>` identity for player interaction/combat filtering, plan world-027), `resolveHorizontal` (entity-neutral wall containment used by `PlayerController` after ordinary colliders) and `queryInterior` (hysteretic interior flag with independent `player` / `camera` confirmation slots) all read it via `caveHeightfieldQuery.ts`. No cave colliders, no SDF. Shared cave surface material adds triplanar rock diffuse colour detail from the same `sharedSurfaceDiffuseTextures` module (plan 021 — browser verification pending). Camera mouth-exit from a portal or surface-clipped hood origin; stable-interior boom never falls back to the outdoor heightfield and shortens instead of parking in the mouth throat. Browser verification of the containment / camera migration pending by the User. The `?caveHeightfieldTest` harness is debug-only and imports the production helpers. Two archetypes (`world-terrain-020` Stage A) plus `dungeon` (`world-terrain-024`): `natural`, the longer `adventure` recipe, and the still-larger branched `dungeon` recipe. Assignment (home adventure guarantee, further dungeon guarantee when an existing site accepts, 15% adventure roll, independent 5% dungeon roll, dungeon→adventure→natural fallback) is pure in `caves/caveArchetype.ts` and exposed as `Caves.archetypeOf`. Dungeon caves expose a read-only stable chamber view via `Caves.dungeonChambersOf` (role-based node ids, not `nodes[]` position) and, when accepted, exactly one deterministic shallow underground pool via `Caves.undergroundPoolOf` (`world-terrain-025`: real heightfield basin, streamed local water presentation, shared `WaterSource` `{ kind: 'lake', quality: 'unsafe' }`, shoreline approach contract — no swim/drowning path). Dungeon animals are not implemented yet.
- `WorldLocationCatalog` / `LocationKnowledge` / `NavigationTargets` — concrete named world locations, player discovery state and active travel targets. See [state/world-locations.md](./state/world-locations.md).
- `Place` / schedule-related NPC work — foundation for daily routines.
- The persistent worldgen cache (`worldgenCacheDb.ts`, `(seed, namespace, version, fingerprint) → payload`) is a structurally separate, disposable versioning concept from `SaveData.version` — never a correctness dependency. See [persistence.md](./state/persistence.md#worldgen-cache) for the mechanism and its current namespaces.
- **Asset anchors** — `src/assets/assetAnchors.ts`; convention in [docs/assets/ANCHORS.md](./assets/ANCHORS.md).

Before adding a new abstraction, check whether one of these already owns the responsibility.

## Current architectural seams / active refactors

- **World visual overhaul** — plants done in part; clouds (weather-driven variety plus local ground fog) and sky are implemented; distant mountains remain.
- **UI** — Vue migration is incremental, browser verification pending across most of it. Do not assume every future UI belongs in Vue; extend the existing facade + store pattern when migrating.
- **NPC daily routine** — Place + executable schedule + vigor are implemented; the household resource layer is implemented (see [settlements.md](./state/settlements.md)). Vigor collapse and a critical need interrupt a schedule-driven action already in flight; ordinary schedule/time-of-day changes still do not. NPC execution state (phase/pending action/pathfinding/combat intent/carried inventory) resets on every `WorldBundle` reconstruction, including an in-session settlement unload/reload — only authoritative state (health/needs/plan/etc.) carries over; do not treat in-session rebuild continuity as full execution-state persistence. Social Places beyond a settlement's own campfire remain an intentional gap.

## Not implemented / intentionally deferred

- Player melee/ranged cannot damage an NPC — only animals are hit-test candidates today; an `[E]` on an NPC opens dialogue instead. See [combat.md](./state/combat.md).
- Fauna's own outgoing attacks use a flat per-attacker-kind damage table rather than the shared melee/ranged/critical/defense pipeline — see [combat.md](./state/combat.md) and [fauna.md](./state/fauna.md).
- Player HP is not persisted — every Continue/Load fully heals the player, while NPC and livestock HP both persist. See [persistence.md](./state/persistence.md#known-persistence-limitations).
- Individual ordinary wild fauna are never persisted (only the population is deterministically reconstructed); explicitly declared persistent habitat occupants are the sparse exception. Rats persist per individual plus a settlement infestation record. See [fauna.md](./state/fauna.md#persistence-classes).
- NPC/animal execution state (pending action, pathfinding, combat intent, carried inventory) is never persisted and resets on every reconstruction.
- Social Places beyond a settlement's own campfire; conversation partner selection/ranking by personality/traits/role/relationship; group conversations; social interaction memory entries.
- LLM/AI-generated quests.
- Inter-settlement trade and player crafting.
- Full combat system for the player — see [state/combat.md](./state/combat.md) for exactly what exists vs. what's missing.
- Weapon repair/broken lifecycle, general tool durability (shovel/pickaxe), bow durability/sharpness, arrow recovery, 3D projectile visuals.
- Cube-sphere / fully spherical world architecture.
- Distant background mountains.
- Full Vue migration of all existing UI.
