## 1. Cel

Wprowadzić wspólny, deterministyczny system walki NPC, który wykorzystuje istniejące mechanizmy combat zamiast tworzyć równoległy system.

Pierwszym użytkownikiem będzie **NPC vs animal**, przede wszystkim jako fundament pod przyszły system myśliwego.

Architektura od początku musi obsługiwać również **NPC vs NPC**, ponieważ później będzie wykorzystywana m.in. przez bandytów.

Plan nie definiuje powodów rozpoczęcia walki ani zachowania konkretnych profesji. Combat jest mechanizmem wykonawczym używanym przez systemy NPC.

## 2. Granica odpowiedzialności

Przepływ ma pozostać rozdzielony:

```text
NPC needs/problems/goals/pressures
        ↓
NPC decision
        ↓
combat intent
        ↓
NPC Combat
        ↓
attack / defense / damage
```

NPC Combat nie decyduje samodzielnie, dlaczego NPC walczy ani kogo powinien zaatakować. Przyszłe systemy, np. Hunter, animal defense i bandits, dostarczą intencję oraz target.

Combat nie może wymagać kamery, inputu gracza, player target selection ani obecności `gameLoop` do działania NPC.

## 3. Combatant contract

Wprowadzić minimalny wspólny kontrakt dla uczestnika walki, jeżeli obecne typy nie zapewniają już odpowiedniego seam-u.

Kontrakt powinien wystarczyć do wspólnego pipeline'u dla:

```text
NPC ↔ animal
NPC ↔ NPC
NPC ↔ player
animal ↔ NPC
```

Pierwsza implementacja aktywnie obsługuje NPC → animal oraz obronę NPC przed obrażeniami.

Nie tworzyć rozbudowanej hierarchii combatantów ani dużej abstrakcji bez potrzeby. Wspólny kontrakt powinien obejmować tylko dane i operacje faktycznie potrzebne do combat.

## 4. Combat lifecycle

Dodać minimalny stan/lifecycle combat NPC zintegrowany z istniejącym `NpcAgent` i `ActionLifecycle`.

NPC powinien móc:

- wejść w combat action na podstawie otrzymanej intencji,
- posiadać aktualny combat target,
- przerwać zwykłą pracę/rutynę na rzecz combat,
- wykonać atak,
- reagować na otrzymane obrażenia,
- zakończyć combat,
- umrzeć.

Nie tworzyć osobnego globalnego `NpcCombatManager` ani niezależnego combat loop.

## 5. Target

Combat target powinien być niezależny od konkretnego typu celu.

V1:

```text
NPC → animal
```

Architektura musi jednak nie zakładać, że targetem zawsze jest zwierzę. Późniejsze NPC vs NPC nie powinno wymagać przebudowy target modelu.

Nie tworzyć osobnego target managera dla każdego typu jednostki.

## 6. Melee

NPC korzysta z istniejącego melee pipeline'u i centralnego `ITEM_CATALOG`.

Wykorzystać istniejące:

- `MeleeConfig`,
- damage/range/arc/timing,
- attack lifecycle,
- istniejące mechanizmy trafienia,
- istniejące critical-hit resolution, jeżeli jest częścią wspólnego pipeline'u.

Nie tworzyć równoległych `NpcMeleeConfig`, `NpcWeaponDamage` ani `NpcAttackTiming`.

Wspólne mechanizmy combat powinny należeć do neutralnej warstwy `src/combat/`, a nie do `playerMelee.ts`. Jeśli obecny playerowy kod zawiera logikę potrzebną również NPC, należy wydzielić tylko konkretny wspólny mechanizm bez szerokiego refaktoru.

NPC korzysta z istniejącego carried state jako źródła wyposażenia potrzebnego podczas aktywności takich jak przyszłe polowanie. Nie tworzyć w tym planie pełnego NPC equipment/storage systemu.

## 7. Ranged

Ranged combat jest częścią tego planu jako kolejny etap implementacji.

Plan 162 należy domknąć/rozszerzyć tak, aby istniejący ranged pipeline mógł być używany przez NPC, przede wszystkim przez przyszłego myśliwego.

Docelowy wspólny przepływ:

```text
RangedConfig
    ↓
ranged attack lifecycle
    ↓
projectile
    ↓
hit resolution
    ↓
damage / critical
    ↓
target
```

Player i NPC mają być różnymi źródłami ataku, a nie dwoma niezależnymi systemami łuku.

Nie tworzyć `NpcBowSystem` ani osobnego projectile pipeline.

## 8. Defense

NPC korzysta z istniejącego systemu defense.

Wykorzystać i w razie potrzeby uogólnić istniejące:

- `DefenseConfig`,
- `resolveDefense()`,
- deterministyczny defense roll,
- reguły kierunku ataku.

Defense powinien być gotowy na:

```text
animal → NPC
NPC → NPC
player → NPC
```

Pierwszy aktywny przypadek poza samym resolverem będzie związany z przyszłą obroną NPC przed zwierzętami.

Nie tworzyć drugiego defense resolvera dla NPC.

## 9. Damage i śmierć

Wykorzystać istniejący `HealthState` i istniejący lifecycle śmierci NPC.

Przepływ:

```text
attack
  ↓
defense
  ↓
damage
  ↓
HealthState
  ↓
death
```

NPC może umrzeć.

Nie implementować w tym planie revive, respawn ani osobnego downed state NPC.

## 10. Healing / opatrunki

Opatrunki nie są częścią samego combat lifecycle.

Combat powinien jedynie pozostawić NPC w stanie, który może zostać obsłużony przez istniejący NPC decision/action flow.

Docelowo:

```text
combat → injured
           ↓
NPC decision/action
           ↓
existing consumable/healing mechanism
           ↓
HealthState restored
```

NPC może wykorzystać dostępny opatrunek, jeżeli taki posiada, ale nie zakładamy używania go podczas aktywnej walki.

Nie tworzyć `NpcHealingSystem`. Szczegółowa decyzja, kiedy NPC leczy się i jaki priorytet ma opatrunek, pozostaje poza NPC Combat.

## 11. Carried state

Combat powinien wykorzystywać istniejący `NpcAgent.inventory` / carried state.

Przykładowy przyszły flow myśliwego:

```text
home storage
    ↓
takes necessary equipment
    ↓
carried state
    ↓
hunt
    ↓
NPC Combat
```

Pozostałe wyposażenie pozostaje w storage i jest poza zakresem tego planu.

Nie tworzyć pełnego NPC equipment systemu ani nowych mechanizmów storage.

## 13. Przyszli użytkownicy

NPC Combat ma stanowić wspólny fundament dla:

```text
Hunter
  → NPC Combat → animal

Animal defense
  → NPC Combat → animal

Bandit
  → NPC Combat → NPC
```

Przyszłe plany powinny dostarczać decyzję/intencję oraz kontekst, zamiast implementować własne systemy ataku.

## 14. Miejsca w kodzie

Dokładne pliki należy potwierdzić podczas implementacji, ale obecny audit wskazuje przede wszystkim:

## 15. Reuse / architektura

Przed dodaniem nowego mechanizmu należy sprawdzić, czy istniejący system może zostać rozszerzony.

W szczególności:

- `ITEM_CATALOG` pozostaje źródłem statystyk broni,
- `MeleeConfig` pozostaje wspólną konfiguracją melee,
- `RangedConfig` pozostaje wspólną konfiguracją ranged,
- `DefenseConfig`/`resolveDefense()` pozostają wspólnym mechanizmem defense,
- `HealthState` pozostaje źródłem zdrowia,
- NPC `ActionLifecycle` pozostaje właścicielem lifecycle akcji,
- projectile system z planu 162 pozostaje wspólnym mechanizmem ranged.

Unikać:

- `NpcCombatManager`,
- `NpcMeleeSystem`,
- `NpcBowSystem`,
- osobnego NPC damage system,
- osobnego NPC health system,
- osobnych target managerów.

## 16. Zależności

### ~~150 — combat mode / defense

Dostarcza istniejące mechanizmy player combat/defense, które należy uogólnić tylko tam, gdzie jest to potrzebne.

### ~~162 — bows, arrows, ranged combat and critical hits

Dostarcza istniejący ranged/projectile pipeline. W ramach NPC Combat należy go domknąć pod użycie przez NPC.

### Przyszłe zależności funkcjonalne

NPC Combat będzie fundamentem dla przyszłych planów:

- Hunter,
- Animal Defense,
- Bandits.

Nie są one dependency tego planu, ponieważ dostarczają zachowanie/intent, a nie fundament techniczny.

## 17. Performance i symulacja

NPC Combat nie może być player-centric ani wymagać pełnej renderowanej reprezentacji NPC.

Należy zachować możliwość późniejszego użycia w hybrydowej symulacji:

- brak per-frame globalnego target scan,
- brak zależności od kamery/player input,
- bounded/local target queries,
- deterministyczne resolvery,
- wykorzystanie istniejących action/update frequency mechanizmów NPC.

Nie przenosić combat do Web Workera bez konkretnej potrzeby wynikającej z kosztu CPU.

## 18. Acceptance criteria

Po implementacji technicznie możliwy jest następujący flow:

```text
NPC
 ↓
otrzymuje combat intent + target
 ↓
wchodzi w combat action
 ↓
wykorzystuje broń z carried state
 ↓
wykonuje melee attack
 ↓
target otrzymuje damage
 ↓
target może zastosować defense
 ↓
NPC może otrzymać damage
 ↓
NPC może umrzeć
```

Po etapie ranged:

```text
NPC
 ↓
bow + arrows z carried state
 ↓
ranged attack
 ↓
istniejący projectile pipeline
 ↓
target
```

Architektura pozwala później dodać NPC vs NPC bez tworzenia drugiego combat systemu.

## 20. Implementation summary (2026-08-21, melee; ranged added same day)

**Melee (implemented):**

- `src/combat/meleeAttack.ts` — pulled the neutral windUp→hitWindow→recovery
  timer + `resolveMeleeHits`/`yawToward` out of `player/playerMelee.ts` (which
  now wraps `createMeleeAttackLifecycle()` and re-exports these instead of
  owning a second copy). Player-only stamina gating, gap-close/lunge and
  target acquisition (`pickCombatTarget`/`rankCombatTargets`) stayed in
  `playerMelee.ts` as the notes recommended.
- `src/combat/combatIntent.ts` — `CombatTargetHandle` (`ref` + `getPosition`/
  `isAlive`/`applyDamage`) and `CombatIntent { target }`. Small, data-only;
  no `Combatant` hierarchy, no target manager. A caller that already holds
  the concrete entity (an `AnimalAgent`, a future `NpcAgent`, the player)
  builds the handle; combat only ever sees this narrow surface.
- `src/ai/npcCombat.ts` — NPC-only glue: `resolveNpcMeleeWeapon`/
  `resolveNpcDefenseConfig` scan `NpcAgent.carried` (the existing generic
  `Inventory`, plan 131) for the first melee/defense-capable `ITEM_CATALOG`
  kind, deterministic catalog-key order; `applyNpcMeleeHit` (critical roll +
  `target.applyDamage`); `resolveIncomingNpcDamage` (defense roll for
  `animal → NPC` / `NPC → NPC` / `player → NPC`, all one shape).
- `NpcAgent` gained a `'combat'` `Phase` (and `CurrentActivityKind`),
  `beginCombat(intent)`/`cancelCombat()`/private `endCombat()`/private
  `die()`, and a `combat` case in `update()`'s existing switch — driven by
  the same per-agent `update()` cadence every other phase uses, no second
  loop, no `NpcCombatManager`. `beginCombat()` fails fast (no side effect)
  when the target is already invalid or the NPC has no melee-capable
  carried item. In range: swings using the shared lifecycle, resolves the
  hit once via `resolveMeleeHits` against the *live* target position
  (re-fetched every tick, never cached), applies it via `applyNpcMeleeHit`.
  Out of range: reuses the existing `steerTo()` walk (no new pathfinding).
  Vigor collapse or an invalidated target ends combat and returns to
  `choose` — the existing decision flow re-derives what happens next.
- Incoming damage: `NpcAgent.applyIncomingCombatDamage()` runs the defense
  resolver before `takeDamage()`. `AnimalAgent.takeDamage()`'s `source` union
  widened to `'npc' | 'player'` (same provocation/retaliation reaction for
  both) and `faunaCombat.ts` gained `combatTargetForAnimal()` — the concrete
  `CombatTargetHandle` a caller uses to point NPC Combat at a live animal.
- Death: `NpcAgent.takeDamage()`/`applyIncomingCombatDamage()` call a new
  private `die()` (tips the mesh, stops the mixer, hides HP/stamina/vigor
  bars, cancels any active action/combat) the moment `HealthState.dead`
  flips; `update()` no-ops for a dead NPC from the next tick on. No corpse
  timer/removal, no revive/respawn/downed state, no loot — matches §9/§13's
  explicit scope boundary. This is the first thing that can actually kill an
  `NpcAgent`; there was no prior death consequence path at all (`takeDamage`
  existed but had zero call sites before this plan).
- Deterministic attack identity: `NpcAgent.combatAttackAttempt` /
  `defenseAttempt` are per-agent monotonic counters (mirrors
  `PlayerController.nextDefenseAttempt`), never frame number/array
  index/object identity.
- A yaw-convention seam worth flagging for future combat work:
  `NpcAgent.mesh.rotation.y` follows `steerTo`'s facing convention
  (`atan2(dirX, dirZ)`, forward = `(sin, cos)`), the mirror image of the
  shared combat forward convention every pure resolver uses (`resolveMeleeHits`/
  `isAttackFromDefensibleDirection`/`yawToward`, forward = `(-sin, -cos)`).
  `resolveIncomingNpcDamage` converts by rotating `+π`; outgoing attacks sidestep
  the issue entirely by computing a fresh `yawToward()` at the hit edge instead
  of reusing `mesh.rotation.y`. See the test in `npcCombat.test.ts` that locks
  this conversion in.

**Ranged (implemented):**

`CombatIntent` gained an explicit `mode: 'melee' | 'ranged'` — the caller
decides the weapon type; `beginCombat()` never silently falls back from one
to the other when the requested one isn't carried (mirrors melee's own "no
config → cannot start" rule). The concrete gap identified before starting
this stage: plan 162's ranged pipeline (`RangedConfig`, `player/playerRanged.ts`,
`combat/projectile.ts`, `combat/rangedAttack.ts`) was real and reusable, but
its *state* (the draw/release/recovery timer, and the live `activeProjectiles`
array) lived entirely inside `player/playerRanged.ts` and `app/gameLoop.ts`'s
local closures — no seam for a non-player shooter. Two small additions closed
that gap without touching any of the reusable pieces:

- `src/combat/rangedLifecycle.ts` — the draw→release→recovery timer, pulled
  out of `player/playerRanged.ts` the same way `combat/meleeAttack.ts` pulled
  melee's timer out of `player/playerMelee.ts` (§ above). `playerRanged.ts`
  now wraps `createRangedAttackLifecycle()` and only layers player stamina
  gating on top — `RangedConfig`, `combat/projectile.ts` (`advanceProjectile`/
  `sweptProjectileHit`/`Projectile`), and `combat/rangedAttack.ts`
  (`rangedAccuracy`/`rangedDeviationRoll`/`resolveRangedDirection`) are
  reused completely unchanged.
- Projectile *ownership*, not a shared registry: instead of generalizing
  `gameLoop.ts`'s player-position-keyed `activeProjectiles` array into a
  world-level pool (which would have been exactly the kind of "global
  projectile manager" the plan forbids), each `NpcAgent` owns at most one
  in-flight `combatProjectile` on itself — mirrors how `combatAttack` is
  already a per-agent field, not a shared one. An NPC won't draw a second
  shot while its current arrow is still travelling (a deliberate V1
  simplification vs. the player's multi-arrow array — documented in the
  field's own doc comment).
- `src/ai/npcCombat.ts` gained `resolveNpcRangedWeapon`/`resolveNpcAmmoKind`
  (mirrors `resolveNpcMeleeWeapon`, catalog-key-order carried-bow lookup,
  ammo checked separately since a bow can resolve with zero arrows) and
  `applyNpcRangedHit` (same critical-roll/`applyDamage` shape as
  `applyNpcMeleeHit`, reading damage/crit off the already-spawned
  `Projectile`).
- `NpcAgent`'s `combat` phase split into `tickMeleeCombat()`/
  `tickRangedCombat()` (both private, called from the same `case 'combat'`
  branch on `intent.mode`) — approach if out of the bow's range, draw when
  in range and idle (spends `staminaCost` up front, same as melee), spawn a
  `Projectile` at `fireReady`, advance/collide it every tick against the
  target's *live* position (re-fetched every tick, matches melee), apply the
  hit via `applyNpcRangedHit`, end combat as `'failed'` if the NPC runs out
  of carried ammo entirely (no point staying in a combat that can never fire
  again). `archery` skill has no NPC equivalent yet, so accuracy uses the
  bow's own base value (`rangedAccuracy(config, 0)`) — same "smallest
  existing-compatible value" choice `applyIncomingCombatDamage` already made
  for defense skill.
- A second instance of the yaw-convention seam flagged in the melee summary:
  the ranged fire path's `aimYaw` fallback (when `yawToward()` returns `null`,
  i.e. target exactly on the NPC's own position) originally fed
  `mesh.rotation.y` straight into `resolveRangedDirection()` — wrong
  convention, same bug shape as the melee/incoming-damage case. Fixed before
  landing: the fallback now converts via `+ Math.PI`, same as
  `resolveIncomingNpcDamage`.
