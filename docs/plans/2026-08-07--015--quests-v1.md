# Plan: Questy v1 (minimalny fetch/delivery)

**Status:** `verification needed`
**Created:** 2026-08-07
**Scope:** [ROADMAP.md](../ROADMAP.md) v0.4+ (questy), nadbudowa nad [npc-interactions.md](./2026-08-07--011--npc-interactions.md) (dialog system)

## Kontekst

Roadmap: „proste questy → potem generator (opcjonalnie LLM)”. To pierwszy, minimalny krok — nie generator, nie quest log pełny jak w RPG. Cel: udowodnić pipeline (quest state, accept/complete przez dialog, integracja z save) na jednym typie questa, zanim dołożymy więcej.

## Stan obecny (dla kontekstu)

- Dialog gracz↔NPC już działa: proximity prompt `[E]`, modal z imieniem + losową kwestią (`src/ui/createNpcDialog.ts`, `NpcAgent.getDialogueLine()`) — patrz [npc-interactions.md](./2026-08-07--011--npc-interactions.md) (`done`).
- Dialog jest **jednostronny** — NPC mówi linijkę, gracz nie ma wyborów (`npc-interactions.md` explicite to wykluczał z v1: „Drzewo dialogowe / wybory gracza” poza zakresem).
- **Brak inventory/przedmiotów** w projekcie w ogóle (sprawdzone: brak `Inventory`/`pickup`/`carry` w `src/`). Klasyczny „przynieś 5 drewna” quest wymagałby budowania systemu przedmiotów od zera — zbyt duży zakres na v1.
- `SaveData` ([src/persistence/saveData.ts](../../src/persistence/saveData.ts)) dziś zapisuje tylko `config` + pozycję gracza — **nic** o stanie NPC/questów. Dodanie quest state = nowe pole + bump `version` + backward-compat dla starych save'ów.

## Decyzja: typ questa v1 — „zanieś wiadomość” (relay), nie fizyczny przedmiot

Zamiast przedmiotu do noszenia (wymaga inventory), quest v1 to **relay**: NPC A prosi gracza, żeby przekazał wiadomość NPC B; gracz idzie porozmawiać z NPC B (`[E]`, istniejący dialog); wraca do NPC A i dostaje potwierdzenie/podziękowanie. Zero nowych assetów, zero inventory — czysto stan + wykorzystanie istniejącego interact/dialog na dwóch NPC.

To celowa uproszczona interpretacja „fetch/delivery” — zaimplementowana jako pierwsze podejście; jeśli po testach w przeglądarce okaże się niesatysfakcjonująca, można zamiast tego poczekać z questami do prostego inventory.

## Cel v1

1. **Jeden hardcoded quest** (jeden giver, jeden target, jedna wiadomość) — udowodnić pipeline, nie zbudować content pipeline.
2. **Accept/decline w dialogu** — jedyne rozszerzenie jednostronnego dialogu: gdy NPC ma questa do zaoferowania, dialog pokazuje dwie opcje zamiast tylko „zamknij”.
3. **Quest state machine**: `not_offered → offered → active → ready_to_report → complete`.
4. **Wizualny feedback**: rozszerzenie `npc-label` sufiksem — „!” dla givera z ofertą/aktywnym questem, „?” dla givera ready-to-report i dla targetu z aktywnym questem.

## Zakres

### 1. Quest data + state

```ts
// src/quests/quests.ts (nowy)
export type QuestState = 'not_offered' | 'offered' | 'active' | 'ready_to_report' | 'complete'

export type QuestDef = {
  id: string
  giverName: string   // musi się zgadzać z CharacterDef/NPC_NAMES
  targetName: string
  offerLine: string
  activeReminderLine: string   // linijka giver-a dopóki quest active
  targetLine: string           // co mówi target NPC, gdy gracz go odwiedzi z aktywnym questem
  reportLine: string           // podziękowanie po powrocie do givera
}
```

Stan trzymany osobno od `QuestDef` (np. `Map<questId, QuestState>`), żeby dane questa zostały statyczne/serializable.

### 2. Dialog: accept/decline

Rozszerzenie `createNpcDialog.ts` (obecnie: tekst + zamknięcie): gdy otwierany dialog trafia na NPC z `offered` questem, pokazać dwa przyciski/hotkeye (np. `[E] Przyjmij` / `[Esc] Odmów` — reużyć istniejące klawisze zamiast nowych, żeby nie kolidować z resztą bindów w `Keyboard.ts`). Odmowa nie blokuje ponownej oferty przy następnej rozmowie (na razie brak trwałego „nie, dzięki”).

### 3. Wiring w `NpcAgent`/`createApp.ts`

- `NpcAgent` (lub osobny `QuestManager` w `createApp.ts`) sprawdza przy otwarciu dialogu: czy ten NPC jest giver/target aktywnego/oferowanego questa, i dobiera linijkę z `QuestDef` zamiast (albo obok) zwykłej `getDialogueLine()`.
- Target NPC musi rozpoznać, że gracz ma aktywny quest wskazujący na niego — najprościej: globalny/przekazany `QuestManager` z metodą `onInteract(npcName): string | null` zwracającą nadpisanie linijki dialogowej.

### 4. Wizualny marker stanu questa

Najlżejsza wersja: dopisać do istniejącego `npc-label` (CSS2D, `${name} · ${need}`) sufiks typu `!` / `?` gdy NPC ma coś związanego z questem — unika budowania nowego systemu ikon na v1. Ładniejsza wersja (ikonka nad głową, osobny sprite) — do rozważenia, jeśli tekstowy sufiks okaże się nieczytelny w testach.

### 5. Integracja z save

**Decyzja:** pominięte w v1 (patrz Poza zakresem) — `QuestManager` żyje tylko w pamięci `createApp.ts`, quest resetuje się po Continue/reload. `SaveData.version` zostaje `1`, bez zmian w `saveData.ts`.

## Rozszerzenie po pierwszym teście w przeglądarce

Po potwierdzeniu, że pipeline działa (`!`/`?` markery, accept/decline), użytkownik dograł trzy rzeczy w tej samej sesji — nie osobny plan, bo to naturalne dopięcie tego samego stanu questa:

1. **Licznik `exp`** — `QuestManager.getExp()`, `+10` przy `complete`. Wyświetlany w HUD (`Hud.setExp`, `src/ui/createHud.ts`).
2. **Panel questów w GUI** (środek ekranu, `[L]` toggle / `Esc` zamknij) — `src/ui/createQuestLog.ts`, lista questów + filtr Wszystkie/W trakcie/Zakończone (`QuestManager.list()`).
3. **Relation/sympathy per NPC** — `QuestManager.getRelation(name)`, `+1` dla givera i targetu przy `complete`. Widoczne w panelu questów per wiersz (`♥ Imię N`), na razie bez wpływu na dialog/AI — czysty licznik.

Wszystko żyje w pamięci `QuestManager` (patrz decyzja o pominięciu save w v1) — reset po Continue/reload tak jak sam quest.

## Poza zakresem v1

- Wiele questów naraz (jeden hardcoded quest wystarczy do sprawdzenia pipeline'u) — quest log UI **jest** w zakresie (patrz wyżej), ale renderuje listę o długości 1.
- Prawdziwe przedmioty/inventory (klasyczne „przynieś X sztuk Y”) — osobny, większy plan, dopiero gdy inventory zaistnieje.
- Generator questów (LLM/OpenRouter, wspomniany w ROADMAP jako „potem”) — to dopiero po tym, gdy ręczny pipeline działa.
- Nagrody (przedmioty/waluta) — na v1 nagrodą jest tylko linijka podziękowania, brak systemu nagród.
- Rozgałęzienia dialogowe poza binarnym accept/decline.
- **Persystencja quest state w save** — zdecydowane: poza v1. Quest state żyje tylko w pamięci na czas sesji; Continue/reload resetuje go do `not_offered`. `SaveData.version` bez zmian.
