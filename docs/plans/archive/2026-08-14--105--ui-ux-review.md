## 6. Kryteria oceny

- **UX:** hierarchia, czytelność, discoverability, feedback, modalność, ile UI zasłania świat 3D, różnica mobile vs desktop.
- **Visual:** typografia, spacing, radius, kolory, kontrast, ikony, panele, z-index. Szukać bliźniaczych elementów o różnych stylach.
- **Mobile:** touch targets ≥44px, joystick vs E vs pauza vs minimapa, safe area, landscape A55, czy modale są używalne.
- **A11y (rozsądny zakres):** kontrast, focus, keyboard, informacja nie tylko kolorem. Semantyka HTML / aria — poza zakresem (skreślone w prompcie).
- **Vue/CSS:** duplikacja, hardcoded values, brakujące wspólne komponenty; co CSS (joystick, canvas minimapy, CSS2D), co Tailwind, czy cienka warstwa tokenów wystarczy.
- **shadcn-vue:** nie zakładać migracji wszystkiego. HUD/game chrome zostaje custom; panele/formularze mogą użyć primitive (Button, Dialog, Input). Nie drugi system obok store + facades.

## Character Screen — UI Refactor Plan

### Cel

Dodać ekran **Character** opisujący bohatera/gracza oraz uporządkować prezentację jego aktualnego stanu w ramach refaktoru UI.

Pierwsza wersja pokazuje:

- HP
- Hunger
- Thirst
- Vigor
- Dirtiness

### Zakres

#### 1. Character screen

Dodać osobny ekran/panel "Character" zgodny z istniejącą architekturą UI.

Dla każdej wartości pokazać:

- nazwę
- aktualną wartość
- maksymalną wartość, jeśli dotyczy
- wizualny stan krytyczny/niski

#### 2. Player state

Character UI ma korzystać z istniejącego stanu gracza.

Nie tworzyć osobnych wartości potrzeb przechowywanych w UI.

Preferowany przepływ:

"Player state → Needs/Health → Character UI"

Jeżeli istniejące systemy NPC mogą zostać bezpiecznie wykorzystane również przez Playera, należy je współdzielić zamiast tworzyć równoległą implementację.

#### 3. Needs

Pierwszy zestaw potrzeb:

- "Hunger"
- "Thirst"
- "Vigor"
- "Stamina" (?) 
- "Dirtiness" (nowe, dodać w osobnym planie) 

"HP" pozostaje częścią systemu zdrowia, a nie potrzeb.

"Dirtiness" traktować jako stan/need, który w przyszłości może wpływać na zachowanie, higienę, komfort i relacje z NPC. Nie dodawać w tej sesji. 

#### 4. UI architecture

Character powinien być przygotowany na późniejsze rozszerzenia:

- Traits
- Skills
- Equipment
- Relationships
- Injuries
- Fatigue
- inne informacje o bohaterze

UI ma być warstwą prezentacji, a nie źródłem prawdy dla stanu gracza.

#### 5. Multiplayer readiness

Architektura nie powinna zakładać, że UI może bezpośrednio modyfikować statystyki.

Stan Character powinien być możliwy do późniejszego przeniesienia do modelu server-authoritative:

"Server/Simulation → Player State → Character UI"

Nie implementować jeszcze multiplayera ani server-side simulation.

### Poza zakresem

- pełny system Player AI
- nowe zachowania gracza
- multiplayer
- server migration
- rozbudowany system equipment
- nowe questy
- nowe mechaniki związane z higieną
