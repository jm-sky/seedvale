# Plan: Natural Crop Lifecycle — Implementation Notes

**Created:** 2026-08-20  
**Status:** `verification needed` 🔍 — implemented 2026-08-20, see plan §11 "Implementation summary" for what actually shipped and where it deviated from these notes (natural crop cycle is periodic rather than one-shot, see plan §11 for why).  
**Priority:** medium · **Effort:** M  
**Depends on:** ~~140~~ ~~126~~  

## Review summary

Plan `172` is directionally correct and fits Seedvale's existing deterministic/lazy lifecycle architecture. The main implementation risk is not the lifecycle itself, but accidentally conflating three different concepts already present in the codebase:

1. **natural world pickups** generated by `src/terrain/chunkItems.ts`,
2. **settlement garden crop pickups** currently created by `src/items/createItemSpawners.ts`,
3. **future planted crops** owned by plan `126`.

The implementation should establish one reusable crop lifecycle model, but it should not turn the existing renewable settlement pickup system into a per-plant simulation system or create a second world resource manager.

`docs/STATE.md` confirms that tree lifecycle already uses explicit stages, deterministic procedural defaults, sparse overrides and lazy world-time resolution. It also confirms that vegetation is chunk-scoped for simulation/lifecycle and region-batched only for rendering. fileciteturn13file0L2-L2

The current plan is therefore **implementable, but needs the boundaries below made explicit before coding**.

## 1. Most important correction: identify the actual current crop source

The plan says that natural edible plants currently appear as ready static objects. In the current code, `chunkItems.ts` does **not** generate carrot, potato or cabbage. Its natural flora pool currently generates mushroom, flower, branch, cone, herb, berries and nuts; it returns deterministic `ItemPlacement` records with stable chunk-local IDs. fileciteturn15file0L2-L2

Carrot/potato/cabbage currently come from `createItemSpawners.ts` as renewable garden-pad pickups. That code deliberately uses the existing generic `ItemSpawnPoint`/respawn contract, with one pickup of each crop kind per garden pad. fileciteturn14file0L2-L2

Therefore the agent must first determine which of these is the intended target:

- If `172` means **wild natural crops**, add a new deterministic natural-crop placement pool alongside the existing flora pool in `chunkItems.ts`.
- If `172` means **garden crops**, replace/extend the garden pickup representation with persistent crop instances, while keeping the generic item spawner for genuinely renewable pickup resources.
- Do not silently reinterpret `berries`/`nuts` as crops; they are already part of the natural-food item pool from plan `159`.

The implementation notes below assume that `172` introduces lifecycle-bearing **crop entities/placements**, while preserving existing generic item spawners for non-lifecycle pickups.

## 2. Do not copy TreeLifecycle literally

`TreeLifecycle` is the architectural reference, not necessarily the module to modify heavily.

The existing tree model contains tree-specific concepts such as species preferences, size class, living height, chop stages, stump visuals and harvest yields. `172` should reuse the same *shape of solution* rather than forcing crops into tree types. fileciteturn17file0L2-L2

Recommended crop core types:

```ts
export type CropGrowthStage = 'young' | 'mature' | 'spoiled'

export type CropPresence = {
  id: string
  x: number
  z: number
  cropId: CropId
  initialStage: CropGrowthStage
  stageStartedAt: number
}

export type CropStateOverride = {
  stage: CropGrowthStage
  stageStartedAt: number
}
```

Prefer `stageStartedAt` over storing an accumulating age. This makes time skipping, unload/load and deterministic resolution straightforward.

Do not store `currentStage` as authoritative state for procedural crops unless it is an override. The resolved stage should be derived from world time when needed.

## 3. Data definitions should be immutable and independent of item definitions

Avoid putting crop growth timings directly into `ITEM_DEFS` unless the existing item catalogue is explicitly intended to become the crop-definition source.

A crop definition represents a **world plant**, while `ItemKind` represents an inventory/pickup product. They are related but not identical.

Recommended shape:

```ts
export type CropDefinition = {
  id: CropId
  matureAfterDays: number
  spoilAfterDays: number
  harvestItem: ItemKind
  spoiledItem?: ItemKind
  visual: CropVisualDefinition
}
```

Use IDs such as `carrot`, `potato`, `cabbage` consistently with existing `ItemKind` values where possible, but keep the lifecycle abstraction separate from inventory semantics.

Avoid an open-ended stringly-typed `species/type` field if the existing `ItemKind` union can provide compile-time safety.

## 4. Resolve lifecycle with elapsed time, not incremental ticks

The key function should be pure and cheap:

```ts
resolveCropStage(crop, worldDays): CropGrowthStage
```

Conceptually:

```text
elapsed = worldDays - stageStartedAt

elapsed < matureAfterDays
  → young

elapsed < matureAfterDays + spoilAfterDays
  → mature

otherwise
  → spoiled
```

The exact interpretation of `stageStartedAt` must be documented. If `matureAfterDays` and `spoilAfterDays` are durations, do not accidentally interpret the latter as an absolute world-day timestamp.

A single pure resolver should be used by:

- harvesting,
- visual rebuild,
- interaction targeting,
- persistence restoration,
- tests,
- plan `126` planted crops.

Do not have renderer logic independently calculate crop age.

## 5. Natural spawn must remain deterministic

The current natural item generation is worker-safe and deterministic: `computeChunkItems()` uses seeded RNG streams and stable IDs based on chunk coordinates/local indices. fileciteturn15file0L2-L2

Crop generation should follow the same pattern.

Recommended placement record:

```ts
export type CropPlacement = {
  id: string
  x: number
  z: number
  cropId: CropId
  initialStage: CropGrowthStage
  stageStartedAt: number
}
```

However, be careful with `stageStartedAt`: if it is generated directly from an arbitrary random number at world generation time, the same world seed must always produce the same value. Prefer deriving it from the stable placement seed or deriving an initial age/stage from a deterministic random roll.

Do not use `Date.now()`, frame time or load time.

## 6. Consider a procedural baseline instead of saving every natural crop

The existing `chunkItems.ts` deliberately uses stable procedural IDs so collected state can be represented by sparse `collectedItemIds` rather than serializing every generated pickup. fileciteturn15file0L2-L2

Natural crops should aim for the same architecture:

```text
procedural crop placement
        +
procedural initial lifecycle state
        +
small sparse override/removed set
        ↓
resolved crop state
```

This is preferable to serializing every crop in every loaded chunk.

A natural crop that simply progresses from young → mature → spoiled should not need a save entry at all if its state can be deterministically reconstructed from seed + position + world time.

A save override is needed only when gameplay changes the procedural baseline, e.g.:

- harvested/removed crop,
- player-planted crop,
- another persistent world interaction that changes its lifecycle anchor.

This distinction is particularly important for future multiplayer scalability.

## 7. Do not make `stageStartedAt` a persistence requirement for every natural crop

The plan currently lists:

```text
id + crop type + position + stageStartedAt / minimal override
```

For natural procedural crops, this can be too much state.

Prefer:

```text
procedural crop:
  id + deterministic initial state

persistent override:
  id + override state

player-planted crop:
  explicit plantedAt/stageStartedAt
```

The exact serialization should follow the existing save architecture rather than introducing a crop-specific save store.

## 8. Chunk lifecycle ownership

Keep crop simulation chunk-scoped just like tree lifecycle.

The chunk manager should own the lifecycle of loaded crop representations:

```text
chunk generated
  → deterministic crop placements
  → resolve stage for current world time
  → create/update visual representation

chunk unloaded
  → remove visual/runtime representation
  → retain only sparse persistent state globally
```

Do not add `CropManager` to `WorldBundle` merely to keep track of every crop in the world.

This follows the existing architecture where tree lifecycle remains chunk-scoped while region batching is a rendering concern. `docs/STATE.md` explicitly describes this separation. fileciteturn13file0L2-L2

## 9. Rendering: prefer stage buckets, not per-crop Object3D logic

The existing vegetation renderer already uses `InstancedMesh` buckets and region-level batching. fileciteturn13file0L2-L2

For crops, use the simplest compatible representation:

```text
cropId + stage
    ↓
visual bucket
    ↓
instanced mesh
```

Avoid creating one Three.js object per crop unless the current crop representation genuinely requires it.

If the visual difference can be achieved through scale/variant/material parameters, use that rather than introducing three GLBs per crop.

The important contract is that visual state is derived from the resolved lifecycle stage, not that every stage must have a unique asset.

## 10. Beware the existing garden spawner semantics

`createItemSpawners.ts` currently creates a pickup mesh immediately and respawns it after a fixed `CROP_RESPAWN_TIME = 90`. That is intentionally a **renewable pickup source**, not a plant lifecycle. fileciteturn14file0L2-L2

Do not implement `172` by simply changing `respawnTime` or adding a `stage` field to `ItemSpawnPoint`.

That would mix:

```text
renewable pickup source
```

with:

```text
individual living crop
```

and would make future planting/NPC farming much harder.

If garden crops are in scope, the garden should instead provide crop placement anchors/slots and those slots should instantiate lifecycle-bearing crops. The existing item spawner can remain for other garden pickups that are explicitly renewable resource sources.

## 11. Harvest should use existing interaction and inventory paths

The plan correctly says not to create a new interaction system.

The implementation should expose the crop as an existing interactable/gather target and only change the validation/yield decision:

```text
interact with crop
  → resolveCropStage(now)
  → young: reject / no mature yield
  → mature: give harvestItem, remove/override crop
  → spoiled: give spoiledItem if defined, otherwise no normal yield
```

Do not duplicate inventory capacity, pickup, label or interaction code.

The result of a harvest should enter the same inventory/item flow used by other gathered resources.

## 12. Define spoiled semantics explicitly before coding

The plan currently allows either:

```text
spoiled → no normal harvest
```

or:

```text
spoiled → special product
```

That is good flexibility, but the implementation should define a deterministic contract:

- `harvestItem` is available only in `mature`;
- `spoiledItem` is optional;
- if `spoiledItem` is absent, interaction removes/marks the crop without an inventory yield, or leaves it as the existing world object according to the chosen gameplay rule;
- never silently give `harvestItem` from `spoiled`.

For v1, keeping `spoiledItem` optional is preferable to inventing new organic-matter inventory items solely for this plan.

## 13. Initial stage distribution should be deterministic and gameplay-oriented

The plan says initial stage may be selected procedurally. Make the rule explicit.

A good v1 approach is a weighted deterministic roll, for example:

```text
young  40%
mature 50%
spoiled 10%
```

The exact numbers are gameplay tuning, not an architectural requirement.

More important:

- no chunk should contain only mature crops;
- the distribution must be seed-stable;
- stage age within a stage should also be deterministic;
- avoid all crops changing stage simultaneously after a world reload.

A stage-only roll without a deterministic age/offset will produce visible synchronization artifacts.

## 14. Do not update crop stages every frame

The renderer does not need a simulation tick for every crop.

Resolve on:

- spawn/load,
- chunk rebuild,
- world-time transition that can affect loaded crops,
- interaction/harvest,
- explicit visual refresh.

If the world clock advances continuously, do not scan every crop each frame just to discover that its stage has not changed.

A cheap alternative is to keep the next transition day for loaded crops and refresh only when world time crosses it. Even then, avoid a global crop scheduler unless profiling shows it is necessary.

## 15. World time integration

Use the same world-time source used by `TreeLifecycle` / `DayNightState.elapsedDays`.

Do not introduce:

- crop-local timers,
- `setInterval`,
- real-time milliseconds,
- a second elapsed-day counter.

This also guarantees correct behavior after time skips and reloads.

## 16. Plan 126 contract should be stronger

The relationship with plan `126` is one of the strongest parts of `172` and should be treated as an implementation contract:

```text
CropDefinition
CropGrowthStage
resolveCropStage()
visual stage mapping
harvest rules
```

must be reusable by planted crops.

Plan `126` should supply the initial lifecycle anchor for a planted crop rather than creating its own growth implementation.

In particular, avoid having:

```text
NaturalCropLifecycle
PlantedCropLifecycle
```

as two independent implementations.

The difference should be **where the initial crop state comes from**, not how the crop grows.

## 17. Plan 126 should not be pulled into this implementation unnecessarily

Do not implement seeds, planting interaction, inventory seed consumption or player placement as part of `172`.

The only required compatibility work is making the lifecycle API usable by `126`.

If `126` currently assumes that planting directly creates a mature item, update the shared lifecycle boundary rather than importing all of plan `126` into `172`.

## 18. Suggested module boundaries

Prefer a small module structure such as:

```text
src/world/cropLifecycle.ts
  types
  definitions
  resolveCropStage
  lifecycle helpers

src/terrain/chunkCrops.ts
  deterministic natural crop placement

src/terrain/... existing chunk manager / vegetation renderer
  crop loading/unloading and visual integration
```

Do not create a manager class unless the existing chunk architecture genuinely requires one.

If `cropLifecycle.ts` becomes small enough, definitions and resolver can remain together. Avoid creating five tiny files for a simple three-stage system.

## 19. IDs must be stable and distinguish crop instances from item pickups

Do not reuse the generic item-spawner IDs such as `spawner:${index}` for natural crop instances.

Use a deterministic world/chunk namespace, e.g.:

```text
crop:${cx}:${cz}:${localIndex}
```

or an equivalent existing ID convention.

This matters because collected item IDs and crop overrides have different semantics.

A harvested crop should be represented by a crop override/removal state, not by adding its ID to `collectedItemIds` unless the existing persistence architecture deliberately treats it as an item placement.

## 20. Save/load and rebuild must preserve gameplay mutations

The plan explicitly requires chunk unload/load and save/load continuity.

The important test is not merely that a procedural crop reaches the same stage after reload. Test both:

```text
natural crop
→ mature
→ harvested
→ chunk unload
→ chunk load
```

and:

```text
natural crop
→ player harvest
→ save
→ reload
```

The crop must not respawn because the deterministic generator still says it exists.

This is where sparse overrides/removal state becomes necessary.

## 21. Avoid changing generic `ItemPlacement` unnecessarily

`ItemPlacement` currently has the simple contract:

```ts
id + x + z + kind
```

and is deliberately worker-safe. fileciteturn15file0L2-L2

Do not turn this type into a giant union containing crop lifecycle state if crops are conceptually different world entities.

Prefer a separate `CropPlacement`/`CropPresence` type and integrate it with the chunk result pipeline in the smallest possible way.

This preserves the current clean separation between static pickup generation and lifecycle-bearing world objects.

## 22. Testing strategy

Add focused pure tests first. They should cover:

- young before mature threshold,
- exact mature boundary,
- mature harvest window,
- exact spoiled boundary,
- no negative elapsed-time bugs,
- deterministic stage resolution,
- different crop definitions using the same resolver,
- deterministic initial-stage generation,
- stable crop IDs.

Then test persistence/rebuild behavior at the chunk integration level.

Do not rely exclusively on browser testing for lifecycle arithmetic.

## 23. Browser verification should include time acceleration

The manual verification should avoid waiting real-time for full crop growth.

Use the existing debug/world-time mechanism to advance the world through:

```text
young → mature → spoiled
```

Then verify the visual representation and interaction at each stage.

Also test a chunk boundary because crop lifecycle is intended to survive unload/load.

## 24. Potential issue with `spoiled` persistence

A procedural crop that reaches `spoiled` does not necessarily need a persisted `spoiled` override: if the stage is fully derived from world time, reload will resolve it again.

Only persist a change if the player/world interaction changes the baseline.

This keeps save data small and avoids the common mistake of turning every naturally generated entity into persistent simulation state.

## 25. Recommended implementation order

1. Inspect current `TreeLifecycle` resolution and its callers; reuse its world-time conventions.
2. Define `CropGrowthStage`, `CropDefinition`, `CropPresence` and sparse override shape.
3. Implement pure `resolveCropStage()` and unit tests.
4. Add data-driven definitions for carrot/potato/cabbage.
5. Add deterministic crop placement only at the actual intended source (natural terrain vs garden slots); do not modify both blindly.
6. Integrate chunk load/unload and visual stage selection.
7. Integrate existing harvest interaction/inventory flow.
8. Add sparse removal/override persistence.
9. Expose the lifecycle API needed by plan `126` without implementing planting.
10. Run technical checks and browser verification.

## 26. Things the agent should explicitly avoid

- `CropManager` / `PlantManager` singleton.
- Per-frame crop updates.
- Real-time timers.
- A second world clock.
- Separate planted-crop lifecycle logic.
- Duplicated inventory/harvest interaction.
- Serializing every procedural crop.
- Reusing `collectedItemIds` for unrelated crop state without checking persistence semantics.
- Three separate heavy GLBs per crop unless assets require it.
- A broad refactor of `TreeLifecycle` merely to make the code look more generic.
- Introducing a Worker solely for crop lifecycle resolution.
- Turning `ItemSpawnPoint` into a general-purpose living-entity abstraction.

## 27. Acceptance criteria refinement

The existing plan's acceptance criteria should be interpreted as:

- **Deterministic:** same seed + same world time + same persistent overrides produce the same crop state.
- **Lazy:** no crop simulation loop exists.
- **Persistent:** harvested/otherwise mutated crops stay changed after chunk unload/load and save/load.
- **Shared:** planted crops can call the same lifecycle resolver in plan `126`.
- **Data-driven:** adding a crop definition does not require another lifecycle branch.
- **Renderer-safe:** crop count does not introduce one `Object3D` and one update operation per crop unless the existing renderer proves that necessary.
- **Architecturally local:** no new global manager or parallel interaction system.

## Final assessment

**Recommendation: proceed, with the scope clarification in §1 treated as mandatory.**

The lifecycle design itself is a good fit for Seedvale and should be kept small. The highest-risk mistake is implementing it as an extension of the existing renewable garden `ItemSpawnPoint` system or assuming that `chunkItems.ts` already contains carrot/potato/cabbage natural placements. The current code shows those are different mechanisms. fileciteturn14file0L2-L2 fileciteturn15file0L2-L2

The safest architecture is a small, pure crop lifecycle module plus deterministic crop placement and sparse persistent overrides, integrated into the existing chunk/render/interaction paths. That gives plan `126` a reusable growth mechanism without creating a second crop system.
