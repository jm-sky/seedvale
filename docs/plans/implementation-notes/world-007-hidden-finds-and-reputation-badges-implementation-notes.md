# Implementation Notes: Hidden Finds & Reputation Badges\n\n## Source-of-truth recon\n\nExisting hidden treasure is a small settlement-specific implementation, not a generic world system.\n\n### Existing hidden treasure\n\n- src/settlement/hiddenTreasure.ts owns marker geometry and hit testing. hiddenTreasureMarkerPositions() derives X/Z positions; hiddenTreasureDigHit() resolves the nearest marker within HIDDEN_TREASURE_DIG_TOLERANCE.\n- DIG_RADIUS comes from src/terrain/dig.ts.\n- src/settlement/props.ts exposes SettlementLandmarks.hiddenTreasureMarkers and currently creates the decorative marker flowers for the home settlement. They have no Interactable/collider.\n- src/app/actions/groundActions.ts is the authoritative shovel-dig path. startDigAt() completes applyDigAt() and then calls checkHiddenTreasureDig().\n- Current treasure progress is an in-memory hiddenTreasureDigCount. Current reward is only granted after HIDDEN_TREASURE_MARKER_COUNT hits.\n- Current reward uses Math.random() for 200–300 coins and one of three swords, so reward selection is currently not deterministic.\n- Current reward is placed through bundle.placedContainers.place('chest', ...). Instance-backed swords require createAcquiredInstance().\n- src/persistence/saveData.ts has only SaveWorldFlags.hiddenTreasureFound for the current treasure.\n- src/app/saveState.ts serializes worldFlags.\n\n### Important discrepancy\n\nComments/docstrings in hiddenTreasure.ts, props.ts and groundActions.ts describe 3 markers, while the current exported HIDDEN_TREASURE_MARKER_COUNT is 4. Treat the current code as authoritative and remove stale comments during migration.\n\n## Digging seam\n\nKeep src/app/actions/groundActions.ts:startDigAt() as the only shovel-dig action. The important completion order is applyDigAt() followed by hidden-find resolution and Quick Actions sync.\n\nDo not add a new shovel action or an Interactable for graves.\n\nsrc/app/interactables.ts contains DIG_REACH and aimed/gaze interaction plumbing, but Hidden Finds should remain a consequence of normal ground digging. The current treasure deliberately follows this pattern.\n\nsrc/terrain/dig.ts owns DIG_RADIUS, DIG_DURATION_SEC, getDigProfileAt() and soil/rock eligibility.\n\n## Landmark ownership\n\nsrc/settlement/props.ts is the main current landmark materialization seam. SettlementLandmarks already carries many world-space landmark positions and currently contains the legacy hiddenTreasureMarkers field.\n\nsrc/settlement/createSettlement.ts returns Settlement with id, size, center, landmarks, economy and households. Settlement.size is the existing VillageSize model and should be reused for loot scaling.\n\nProcedural landmark constructors are exposed through props.ts, including createCemetery, createCemeteryPlot, createGraveStone, createMonolith, createStoneCircle and createSmallRuins. Trace the actual VillageLandmarkPlan/VillagePlan placement path before implementing cemetery spots; do not assume a visual constructor owns authoritative landmark state.\n\n## Settlement lookup\n\nThe plan requires loot to depend on the nearest settlement. Reuse an existing bounded/spatial settlement lookup if one exists. Do not scan all settlements on every shovel completion if the loaded/local world already provides a suitable lookup.\n\nDo not introduce a generic wealth field just for this feature. Prefer Settlement.size or an existing development metric.\n\n## Determinism\n\nsrc/world/parseSeed.ts already provides createSeededRandom(). src/settlement/settlementGenerator.ts provides cellSeed(). Reuse these conventions instead of adding another RNG/hash implementation.\n\nHidden Find existence, positions and loot selection must not use Math.random() during normal gameplay. Stable identity should include existing stable landmark identity plus spot index where applicable.\n\nGenerated positions/results should be derived; persistent state should only record what cannot be safely re-derived, primarily resolved spot IDs.\n\n## Hidden Find ownership\n\nKeep authoritative state outside Three.js meshes. Prefer four responsibilities:\n\n1. static profile/definition for landmark kind;\n2. deterministic generation of candidate spots and their outcomes;\n3. sparse resolved-state storage;\n4. resolver taking dig position plus world context and returning the result.\n\nDo not make Object3D.userData authoritative.\n\n## Cemetery\n\nThe cemetery is the multi-spot exception.\n\n- Use the real cemetery grave layout/count as input.\n- Generate multiple potential dig spots from that layout.\n- Each spot gets its own deterministic outcome.\n- A spot resolves once.\n- Not every grave/spot needs loot.\n- Total possible loot must be bounded.\n\nDo not implement one global cemetery loot container/pool.\n\nDo not blindly assume 1 grave = 1 dig spot; inspect the actual cemetery generator and choose the smallest sensible mapping.\n\n## Ordinary landmark finds\n\nAgreed interpretation:\n\n- stone circle 25% = one roll for the whole landmark;\n- monolith/pillar 10% = one roll for the whole landmark;\n- if successful, choose one deterministic dig position;\n- multiple visual/sample positions must not create multiple treasures.\n\nThis differs intentionally from cemetery multi-spot behaviour.\n\n## Existing item mechanisms\n\nReuse src/items/items.ts ItemKind/ITEM_DEFS, src/items/itemCatalog.ts, src/items/Inventory.ts, src/items/trade.ts createAcquiredInstance(), and src/world/createPlacedContainers.ts where appropriate.\n\nDo not create another loot or inventory system. The old chest reward is a reference, not a requirement for every Hidden Find.\n\n## Reputation / relations\n\nQuestManager owns persistent relations and exposes player standing/relation export/import. Before implementing, inspect getPlayerStanding(), relation mutation methods and the NPC social lookup path.\n\nApply cemetery penalty at the gameplay event boundary where a dig is confirmed as a grave disturbance. Empty result still causes the penalty. Ordinary Hidden Finds elsewhere do not automatically cause reputation loss.\n\nDo not create a parallel global reputation system.\n\n## Badges / achievements\n\nFocused recon found no obvious generic Badge/Achievement subsystem in the inspected entry points. First confirm with a narrow repository search; if none exists, create a small standalone domain model with explicit ownership rather than embedding badges into QuestManager.\n\nKeep standing and badges separate:\n\n- standing = current social value;\n- badge = persistent historical fact.\n\nUpdate badge progress from discrete gameplay events such as grave disturbed, Hidden Find discovered and rare relic found. Never evaluate achievements every frame.\n\n## Persistence\n\nSave schema is canonical v1 with no migration layer.\n\nAdding persistent Hidden Find state requires coordinated changes to src/persistence/saveData.ts validation/type and src/app/saveState.ts assembly, plus the load/restore path in src/app/createApp.ts or the relevant WorldBundle setup.\n\nCurrent worldFlags.hiddenTreasureFound is too coarse for independent cemetery spots. Find all consumers before replacing/removing it.\n\nPrefer sparse resolved IDs. Do not persist deterministic positions/results.\n\n## UI\n\nVue UI is mounted by src/ui-vue/App.vue and state is centralized in src/ui-vue/store.ts. Existing player screens include CharacterScreen.vue, SkillsScreen.vue, InventoryScreen.vue and QuestLogScreen.vue.\n\nFollow the existing screen + store/facade pattern. Inspect how Character/Skills are opened from current navigation and add Badges to that existing player-facing surface rather than creating a second UI state mechanism.\n\n## Recommended implementation order\n\n1. Focused recon of actual cemetery generation and grave positions/count.\n2. Trace every current hiddenTreasure consumer and remove home-settlement-only assumptions.\n3. Introduce generic Hidden Find definitions, deterministic generation and resolution.\n4. Migrate the existing treasure as the first profile.\n5. Add cemetery multi-spot generation.\n6. Add settlement-size loot scaling.\n7. Add stone circle and monolith profiles.\n8. Add sparse persistence for resolved IDs.\n9. Reuse existing player standing for cemetery disturbance.\n10. Add Badge/Achievement state and event-driven progress.\n11. Persist badges/progress.\n12. Add Vue presentation.\n13. Run technical checks.\n14. Leave visual/gameplay verification to the user.\n\n## Avoid\n\n- no grave Interactable or Dig Grave prompt;\n- no visible dig markers;\n- no second shovel/dig pipeline;\n- no single global cemetery loot;\n- no Math.random() for persistent find outcomes;\n- no authoritative state in Three.js meshes;\n- no duplicated settlement wealth metric;\n- no second reputation system;\n- no automatic reputation penalty for ordinary landmark finds;\n- no hidden achievement conditions exposed before discovery.\n\n## Primary files\n\n- src/settlement/hiddenTreasure.ts\n- src/app/actions/groundActions.ts\n- src/app/interactables.ts\n- src/terrain/dig.ts\n- src/settlement/props.ts\n- src/settlement/createSettlement.ts\n- src/settlement/settlementGenerator.ts\n- src/world/parseSeed.ts\n- src/quests/QuestManager.ts\n- src/persistence/saveData.ts\n- src/app/saveState.ts\n- src/app/createApp.ts\n- src/ui-vue/store.ts\n- src/ui-vue/App.vue\n- src/ui-vue/screens/CharacterScreen.vue\n- src/ui-vue/screens/SkillsScreen.vue\n- src/items/items.ts\n- src/items/itemCatalog.ts\n- src/items/Inventory.ts\n- src/items/trade.ts\n- src/world/createPlacedContainers.ts\n\n## Useful tests\n\nPrefer pure/unit tests for deterministic dig-spot generation, point-to-spot hit resolution, seeded outcomes, cemetery spot count, settlement-size loot profiles, single-find landmark probability and resolved-spot idempotency.\n\nDo not use unit tests to claim Three.js visual correctness. Browser/manual verification remains the user's responsibility.\n\nRepository is the source of truth; these notes describe current seams and known constraints, not planned abstractions that already exist.
