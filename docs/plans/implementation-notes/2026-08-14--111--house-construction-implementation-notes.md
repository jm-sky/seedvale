- `pickHouseDefinition` is size-aware: outposts stay on cottages; MD+ mix in 6×6 / 8×6 farmsteads.
- `src/settlement/houseBuilder.ts` resolves parts through the existing `ConstructionCatalog` / `loadGltf` cache. No second asset registry.
- Static repeats become per-house `InstancedMesh` buckets; after placement, `createHouseStaticBatch()` merges identical geometry+material across houses into settlement-owned InstancedMeshes. Doors stay interactive.
- Door: `door → hingePivot → doorLeaf`. `door_1_flat` hinge offset is **x = -0.51 m** (review 011). `setOpen` interpolates only `hingePivot.rotation.y`. Settlement `update` opens the door when the observer is near the entrance point.

Native MegaKit metres — no `prepareProp` height-fit. `landmarks.houses` now carries `definitionId` + `footprintRadius` (`houseId` === `definitionId` for assembled houses). Colliders / Places / households / livestock / night lamps unchanged in ownership.
- `houseCatalog.ts` is kept: Asset Browser entries, lamp-mount tests, and GLB fallback if MegaKit templates fail to load.

## 2026-08-25 — collider alignment / scale cleanup

- `HOUSE_ASSEMBLY_SCALE` changed from `1.1` to `1`. The lamp/chest/furniture `invHouseScale` compensations in `props.ts`/`houseLighting.ts` derive from `hut.scale.x` at runtime (not a hardcoded `1.1`), so they keep working unchanged — they now simply divide by `1`.
- Added `openingLocalPose(def, opening)` in `houseBuilder.ts` as the single source of truth for a door/window opening's local pose. `buildHouse()` (frame/fill placement, door root), `buildHouseDoorCollidersLocal()` (closed-door collider) and `derivedInteractionPoints()` (door/entrance points) now all read this one function instead of three independent `matchingWallPlacement` + `wallLocalTransform` computations that happened to agree.
- `DOOR_1_FLAT_HINGE_OFFSET_X = -0.51` is unchanged — still applied only to the hinge, relative to `openingLocalPose`, so the closed door leaf stays centred on the same opening pose the collider now explicitly shares.
- **Browser testing found a real, pre-existing gap** (not introduced by the above): a door's whole 2 m wall module is fully skipped by `buildHouseWallCollidersLocal` (so the frame/leaf can render there), but the closed-door disk (`HOUSE_DOOR_COLLIDER_RADIUS = 0.45`) only covers ~0.45 m around the center — leaving ~0.55 m of totally uncollided space on each side, wide enough for the player (radius 0.35 m) to walk in beside a closed door instead of through it. Fixed with `buildHouseDoorJambCollidersLocal()` — two always-present frame/jamb circles flanking every door opening, present regardless of open/closed state (only the leaf disk toggles). Wired into `buildHouseCollidersWorld`.
- **First jamb-radius attempt was wrong** — `HOUSE_DOOR_JAMB_OFFSET = 0.75` / `HOUSE_DOOR_JAMB_RADIUS = 0.5`, derived by summing raw collider radii to "just touch" the door disk and the neighboring wall collider. That ignored that `resolvePosition` (`world/collision.ts`) adds the *querying entity's own* collision radius (player = 0.35 m) to every collider it tests — so the effective blocked span was much wider than the raw circles suggested, and ended up sealing almost the entire ~1 m doorway shut (browser-confirmed: "gap of ~5 cm"). Recalculated properly, solving for the effective (radius + entity-radius-inclusive) span instead of the raw one: `HOUSE_DOOR_JAMB_OFFSET = 1.05`, `HOUSE_DOOR_JAMB_RADIUS = 0.15` — inner edge ≈0.55 m (half the real `door_1_flat` leaf width, 1.118 m) so the visual doorway stays walkable, outer edge ≈1.55 m so the jamb alone (not relying on a same-side neighbor wall module, which doesn't exist when a door sits at a wall's end next to a corner post, as in `TEST_HOUSE_01`) fully closes the gap to the module edge. Added a regression test (`houseBuilder.test.ts`) that specifically guards the walkable corridor width via `resolvePosition`, not just "some point near the door is blocked" (the earlier regression test would not have caught the over-sized-jamb bug, since a too-small gap still "blocks a point beside the doorway").
- Found but **not fixed** (documented as a loose end, not concretely demonstrated as broken today): house corner posts (`def.corners`, e.g. `corner_exterior_wood`) have no dedicated collider at all — `buildHouseWallCollidersLocal` only iterates `def.walls`. In the common case this is masked by a neighboring wall module's own player-radius-inclusive reach (`0.95 + 0.35 = 1.3` > the `1.0 m` distance from a wall-module center to its own corner), but that's incidental, not a real invariant, and doesn't hold if the corner-adjacent module is itself a skipped door module with no fallback wall collider (which is exactly the case the jamb fix above patches for `TEST_HOUSE_01`, since its jamb's reach happens to also cover the adjacent corner).
- Added a `?debugColliders=1` overlay (`debug/colliderDebugView.ts` + `debug/debugMode.ts`'s `isColliderDebugMode()`) — renders every nearby `Collider` as a translucent orange cylinder, updated once per frame in `gameLoop.ts` from `bundle.chunkManager.collidersNear` (read live, not cached, per the `WorldBundle` rebuild invariant). This overlay is what surfaced the over-sized first-attempt jambs visually ("big circles that surround the wall").
