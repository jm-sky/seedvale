# Landmark Quests — implementation notes

## Review scope

Reviewed against the current `main` codebase, `docs/plans/README.md`, `docs/STATE.md`, and the plan `2026-08-16--132--landmark-quests.md`.

The plan is still `planned`; no implementation for landmark quests exists yet. The existing foundations are real and usable: stable landmark IDs, world-driven quest lifecycle, injected animal resolvers, and the existing `[E]` interaction pipeline.

## Current architecture

### Composition / ownership

- `src/app/createApp.ts` is the composition root.
- `src/app/worldBundle.ts` owns/rebuilds the main world systems (`ChunkManager`, settlements, fauna, etc.). Keep injected callbacks indirect through `bundle` so they survive `rebuildWorldBundle()`.
- `QuestManager` is intentionally world-agnostic. It already uses dependency injection for fauna lookup and dangerous-animal mutation instead of importing fauna directly.
- `src/app/interactables.ts` builds a fresh per-frame `Interactable[]` from current world systems.
- `src/interaction/Interactable.ts` is the common adapter type consumed by target selection / `[E]` interaction.
- `src/interaction/resolveInteraction.ts` dispatches world-object interaction to `QuestManager.onInteractObjective()` where appropriate.

### Landmarks

`src/terrain/chunkEnvironment.ts` owns deterministic environment placement. The four proper landmarks are:

- `monolith`
- `stoneCircle`
- `smallRuins`
- `cemetery`

`EnvironmentPlacement.id` is already generated by:

`deriveLandmarkId(seed, cx, cz, kind, ordinal)`

and currently has the form:

`kind:cx:cz:ordinal:seed(base36)`

The ID is deterministic and is not persisted. Existing tests in `src/terrain/chunkEnvironment.test.ts` already cover determinism and uniqueness across seed/chunk/kind/ordinal.

Important: the ID is currently only data on the placement. There is no landmark lookup API, runtime landmark registry, quest consumer, or `Interactable` variant for landmarks.

### Quest system

`src/quests/quests.ts` defines `QuestObjective` and the static `QUESTS` definitions. Existing objective types include world interactions (`interact_well`, `interact_tree`, `interact_spawner`, fauna objectives, etc.). There is no landmark objective yet.

`src/quests/QuestManager.ts` owns quest state and progression. `onInteractObjective(ref)` is the correct extension point for landmark progress. `ObjectiveRef` is the world-to-quest event adapter and is deliberately independent of Three.js/world generation.

The existing fauna pattern is the best model:

- `AnimalTargetResolver` is injected into `QuestManager`.
- `createApp.ts` supplies the resolver because it owns the world bundle.
- `QuestManager` stores the stable bound ID and never imports the underlying world system.

Landmarks should follow the same dependency direction.

### Interaction

`buildInteractables()` currently exposes NPCs, animals, trees, spawners, houses, wells, fires, items, deposits, etc. There is no environment-landmark query yet.

`resolveInteraction()` already handles `animal`, `house`, `spawner`, `tree`, and `well`, forwarding quest-relevant interactions to `QuestManager`. A landmark case should be another small branch, not a new interaction system.

## What is already implemented vs what is missing

### Already implemented

- Deterministic procedural landmark generation.
- Four landmark kinds from plan 049.
- Stable `EnvironmentPlacement.id` from plan 110.
- Existing quest stages, relation gates, rewards/effects and terminal lifecycle states.
- Existing injected world-target resolver pattern for fauna.
- Existing per-frame interaction adapter and `[E]` target selection.
- Existing quest progress dispatch through `QuestManager.onInteractObjective()`.
- Persistence of active quest state through existing `QuestState`/save data.

### Missing for plan 132

- Landmark lookup/access API.
- Landmark-specific `QuestObjective` / `ObjectiveRef`.
- Landmark binding at quest activation (the important dynamic-binding problem described below).
- Landmark exposure through `Interactable` / target selection.
- Landmark progress dispatch.
- Actual landmark-driven quest definitions.
- End-to-end world consequence using an existing world-state hook, if a suitable one exists.
- Tests for lookup, objective matching, persistence/reload and interaction.

## Key architectural issue: static `QuestDef` vs runtime landmark ID

Do not blindly implement the plan as a static quest definition containing a hardcoded `landmarkId`.

`QUESTS` is static data, while the actual procedural landmark ID depends on the current world seed and a concrete chunk. A definition such as:

```ts
{ type: 'interact_landmark', landmarkId: 'smallRuins:...' }
```

would either only work for one world or force hardcoded world coordinates/IDs, which the plan explicitly rejects.

Use the existing fauna binding pattern instead:

1. Quest definition describes the kind/selection rule needed to find a landmark.
2. When the stage becomes active, the world layer resolves a concrete existing landmark near the relevant NPC/settlement/problem.
3. `QuestManager` stores that concrete `landmarkId` in runtime state, analogous to `animalTargets`.
4. The active objective then matches only that exact ID.

The public objective can still be the plan's small shape (`interact_landmark` + concrete ID), but the runtime binding must be handled separately from static `QUESTS` data. Prefer a small selector/binding mechanism rather than making `QuestDef` itself mutable.

Do not add a second persisted landmark state just to solve this. The active quest's existing `QuestState` is the persistence boundary.

## Landmark lookup recommendation

There are two distinct needs and they should not be conflated:

### A. Nearby runtime interaction

For `[E]`, use landmark placements belonging to currently loaded chunks. Extend the existing chunk/environment ownership with a small query such as `getNearbyLandmarks(playerPos, range)` or an equivalent accessor.

This is not a global registry: loaded chunk data is already runtime world state. The result should be the existing `EnvironmentPlacement` data, including `id`, `kind`, `x`, and `z`.

Avoid scanning every `Object3D` in the Three.js scene.

### B. Deterministic quest resolution

Quest binding must work without requiring the target chunk to remain loaded. The current ID format already contains enough address information (`kind`, `cx`, `cz`, `ordinal`, `seed`) to identify the candidate.

However, do not assume that parsing the ID alone reconstructs the final placement. Landmark placement also depends on terrain/biome/village context in `computeChunkEnvironment()` (height, slope, biome bias and cemetery village-fringe rules). The resolver must validate/reconstruct the deterministic placement rather than treating the encoded ID as proof that the landmark actually exists.

Keep the search bounded to a relevant area (for example the NPC/settlement region), never scan the whole procedural world.

If the existing terrain generator cannot cheaply reconstruct an unloaded landmark, prefer a deterministic bounded resolver over a global cache. Do not introduce a persistent `Map<landmarkId, ...>` as a workaround.

## Recommended implementation shape

### 1. Terrain/environment API

Start in `src/terrain/chunkEnvironment.ts` and/or the existing `ChunkManager` environment ownership.

Add the smallest reusable resolver/accessor possible. It should:

- use the existing `deriveLandmarkId()`;
- return `EnvironmentPlacement`-level data, not `THREE.Object3D`;
- distinguish the four proper landmark kinds from decorative environment objects;
- validate the requested ID against the deterministic generation rules;
- support unloaded chunks for quest resolution;
- avoid a world-wide registry.

Also expose nearby loaded placements for interaction if `ChunkManager` does not already retain/query environment placement data.

### 2. Quest types

In `src/quests/quests.ts`:

- add `interact_landmark` to `QuestObjective`;
- keep it generic, not one objective per landmark kind;
- extend `ObjectiveRef` in `QuestManager.ts` with an exact `landmarkId` reference.

Suggested shape:

```ts
{ type: 'interact_landmark', landmarkId: string }
```

and:

```ts
{ type: 'interact_landmark', landmarkId: string }
```

for the interaction/progress reference as well.

The important invariant is exact-ID matching: interacting with another ruin/monolith must not advance the quest.

### 3. Runtime landmark binding

Mirror `animalTargets` in `QuestManager` with a small `questId -> landmarkId` binding if needed by the final design.

Do not persist a separate binding map. The concrete landmark ID must either be encoded into the active quest's persisted state through the existing quest representation or be deterministically re-derived from the quest/world context on load.

Be especially careful here: unlike animal IDs, landmark IDs are stable across unload/reload, so there is no reason to invalidate an active landmark quest merely because its chunk was unloaded.

### 4. Resolver injection

Introduce a narrow injected resolver from the app/world layer, for example conceptually:

```ts
resolveLandmarkTarget(selector, origin) => landmarkId | undefined
```

Keep `QuestManager` unaware of:

- `ChunkManager`;
- terrain generation;
- Three.js;
- chunk streaming;
- `Object3D`.

`createApp.ts` should provide the resolver through the existing `bundle` indirection, just like `resolveAnimalTarget`.

### 5. Interaction adapter

Extend `src/interaction/Interactable.ts` with a landmark variant containing only the data interaction code needs:

- `kind: 'landmark'`;
- position;
- stable `id`;
- landmark kind / display label if useful.

In `buildInteractables()` add nearby loaded landmarks using the same `GAZE_RANGE`/target-selection pipeline. Do not create a separate proximity system.

In `resolveInteraction.ts`, forward:

```ts
questManager.onInteractObjective({
  type: 'interact_landmark',
  landmarkId: target.id,
})
```

and fall back to a simple landmark flavor/examine line when no quest consumes it.

Keep the interaction generic; the active quest determines whether it has gameplay significance.

### 6. Quest definitions

Do not generate a quest for every procedural landmark.

Start with 2–3 hand-authored quests whose premise is an existing NPC/settlement problem. The landmark should solve or advance a real problem, not be the reason for the problem merely because it exists.

Prefer the existing quest infrastructure:

- `availability` for relation gates;
- `effects` for relation/EXP;
- multi-stage `QuestStage` where returning to an NPC is needed;
- existing world flags/hooks only where they already have the correct semantics.

Avoid adding a generic `landmarkVisited` flag.

## Selecting the first quests

Before adding definitions, inspect the current NPC/world-problem code and choose problems with a natural physical location.

Good candidates:

- `smallRuins`: missing object/information or investigation problem.
- `stoneCircle`: disappearance / last-known-location investigation.
- `monolith`: exploration or warning tied to an NPC's concern.
- `cemetery`: settlement/NPC problem where investigating a burial place has social consequences.

The plan's examples are patterns, not mandatory content. Do not invent a parallel lore system just to justify landmark quests.

At least two quests should work end-to-end. Prefer different landmark kinds if the existing world state supports it.

## Persistence and lifecycle

The current save schema already persists quest progress. No new save field should be introduced just for landmarks.

Important cases:

- **Chunk unload/reload:** landmark ID remains unchanged; quest stays active.
- **Save/load:** active landmark target must resolve to the same deterministic ID.
- **Different seed:** old quest state belongs to the saved world seed, so never use hardcoded world coordinates/IDs that assume a specific seed.
- **Missing/invalid target:** do not silently complete the objective. Use the existing quest lifecycle semantics; for a truly impossible binding, fail/invalidate only if that matches the meaning of the existing lifecycle.
- **Double interaction:** `onInteractObjective()` should advance at most once because only the active stage can match; ensure the interaction code does not dispatch the same event twice.
- **Wrong landmark:** same-kind but different-ID landmark must not complete the objective.
- **Multiple nearby landmarks:** normal target selection must determine one target using the existing gaze/range logic; do not add quest-specific selection rules.

Unlike wild fauna, a landmark does not need the plan 110 "unstable runtime entity" invalidation rule. Its identity is explicitly deterministic.

## Performance considerations

Landmarks are rare, so interaction lookup should be cheap.

Preferred path:

- query only loaded chunks near the player for `[E]` candidates;
- avoid scanning all chunks or all scene objects every frame;
- reuse the existing per-frame `Interactable[]` and `withinRange()` filtering;
- avoid generating new terrain/landmark data every frame;
- quest binding may perform a bounded deterministic search once on quest activation, not every frame;
- do not add a worker solely for landmark lookup unless profiling shows a real CPU cost.

The existing performance direction strongly favors bounded/lazy work and avoiding a second world-state cache.

## Main implementation risks

1. **Static quest definitions hardcoding procedural IDs.** Avoid by binding a real landmark at runtime through an injected world resolver.
2. **Resolver accidentally becoming a second world generator.** Reuse `chunkEnvironment` rules and deterministic IDs; keep one source of truth.
3. **Global landmark registry creeping in.** Loaded chunk data is acceptable; a world-wide persistent `Map` is not.
4. **Interaction becoming quest-specific.** Landmark interaction should be a normal world interaction and only report progress to `QuestManager` when a matching active objective exists.
5. **QuestManager coupling to terrain/chunks.** Keep the same injection boundary already used for fauna.
6. **Invented world state.** Prefer existing NPC/settlement problems, flags and relation effects. Do not add `LandmarkState` merely to remember that a landmark was visited.
7. **Expensive unloaded lookup.** Keep quest target search bounded to a relevant region and perform it only when binding/rebinding, not per frame.

## Recommended implementation order

1. Verify how `ChunkManager` currently retains finalized environment placements and add the minimal nearby-landmark accessor if necessary.
2. Design and test a deterministic `landmarkId -> placement` resolver without introducing a registry.
3. Add `interact_landmark` objective/ref and exact-ID matching in `QuestManager`.
4. Add runtime binding for a concrete landmark when the quest stage becomes active, following the existing animal-target pattern.
5. Add the landmark `Interactable` and `resolveInteraction()` branch using the existing target-selection pipeline.
6. Choose 2–3 real NPC/settlement problems and add the smallest hand-authored landmark quests that fit them.
7. Add focused unit tests, then technical verification.
8. Perform browser verification of travel, interaction, unload/reload and save/load.

Do not implement new landmark types, a discovery/map-marker system, a global registry, LLM-generated quest definitions, or a new world-state subsystem as part of this plan.
