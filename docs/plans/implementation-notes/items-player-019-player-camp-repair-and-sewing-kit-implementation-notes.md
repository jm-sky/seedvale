# Implementation Notes: items-player-019 — Player camp repair and sewing kit

## Dependency preflight

`items-player-019` depends on three unfinished contracts and must be implemented against their **actual post-implementation APIs**, not by recreating them locally:

- `items-player-018` — camp inspection, tent/bedroll/platform condition and factor-based shelter/degradation semantics,
- `items-player-021` — `Repair` skill plus shared skill-evaluation / targeted-skill action seam,
- `world-021` — persistent `RepairProgress`, actor-neutral work contribution, material commitment and repair completion semantics.

On current `main` all three remain `planned`. Current code therefore still has the pre-018/pre-021 shape: six player skills, no `RepairProgress`, and `PlacedTent = { id, x, z, yaw }` with ids generated by `createPlacedTents.place()`.

Before coding 019, reconfirm those three dependencies. Where their implemented API differs from the plan, follow current code ownership and preserve the contracts below rather than introducing adapters that duplicate them.

## Core architecture after dependencies

019 should be a thin camp-domain consumer of shared mechanisms:

```text
camp object owner
  owns condition + optional RepairProgress

camp repair domain
  resolves quote: target condition, materials, capability, work, effort

items-player-021
  supplies Repair competence / targeted contextual action plumbing

world-021
  supplies RepairProgress + accepted-work semantics

player adapter
  validates Inventory/capability, commits materials, starts/resumes Busy work bout,
  contributes work, awards Repair XP for useful work
```

Do not restore the old immediate-repair model where Busy completion directly adds condition. Busy is only a **work bout** against persistent target-owned repair progress.

## Repair episode semantics to inherit from `world-021`

Do not create a camp-specific `RepairProgress` type or parallel helper set. Reuse the shared type/helpers from `world-021` (planned home: `src/world/repair.ts`) and its invariants:

- progress belongs to the world target/component, never the player,
- materials are committed atomically when the repair episode starts,
- interruption preserves `completedWork` and committed materials,
- subsequent work bouts contribute accepted work to the same episode,
- completion atomically sets authoritative condition to `targetCondition`, clears progress and resets degradation anchor,
- normal degradation is frozen for the component while repair is active,
- no explicit cancel/refund path in v1.

Camp object mutation owners should expose operations equivalent to:

```text
resolve/checkpoint condition
start repair from authoritative quote
contribute repair work
complete repair when required work is reached
```

App/UI code must not mutate `RepairProgress` or condition records directly.

## Camp repair quote ownership

Keep one small pure camp-domain resolver, e.g. `src/items/campRepair.ts`, but its job is **camp-specific policy**, not shared repair lifecycle.

It should define/resolve for `tent | bedroll | platform`:

- legal target condition (`100` for player v1),
- material kind/count as a deterministic function of damage restored,
- required item capability,
- required work,
- physical effort,
- Repair skill contribution and optional Survival support if the post-021 skill-evaluation seam supports it naturally.

Reuse the shared `MaterialRequirement` type used by construction/`world-021`; do not add another `{ kind, count }` repair type.

UI preview and authoritative start validation must call the same resolver. Vue renders values only.

The old notes' `baseRepairPoints 25 / 34 / 17`, `repairMaterialMultiplier(survival)` and `survivalDurationMultiplier()` are **not canonical anymore**. They may only be consulted as balance reference if useful. The current plan explicitly makes `Repair` the primary competence and required work/material cost damage-dependent.

## Repair skill integration

After `items-player-021`, use its real `Repair` skill and skill-evaluation seam. Do not implement another skill formula inside camp UI/actions.

Required semantics:

- `Repair` is primary,
- `Survival` is optional context/support only,
- no RNG,
- no mandatory global weighted-average formula,
- if the post-021 API has no clean support-skill seam, omit Survival influence in v1 rather than inventing one.

Repair XP must use existing `awardSkillXp()` conventions and be tied to meaningful accepted/completed repair work. Never award XP for preview, targeting, failed start, starting an episode with zero contribution, or cancelling before useful work. Design cadence so repeated resume/cancel cannot farm XP.

## Targeted/contextual interaction integration

019 should integrate with both existing camp inspection from `items-player-018` and the targeted-skill foundation from `items-player-021` without making two repair implementations.

Preferred shape:

```text
normal camp inspection → repair/continue action
selected Repair + gaze target → resolves the same camp repair action
                                      ↓
                              same domain quote/start/resume path
```

`Interactable` remains a thin target adapter. Do not add repair state, material formulas or skill difficulty fields to the generic interaction model.

Use existing `FlavorDialog`/contextual action view models. Do not create `TentRepairModal`, `BedrollRepairModal` or `PlatformRepairModal`.

## Condition/degradation integration from `items-player-018`

Always resolve/checkpoint the target's authoritative condition using the actual post-018 condition API before:

- generating the authoritative start quote,
- starting repair,
- packing a tent.

Do not hard-code today's pre-018 sleeping-utility `sheltered: boolean` contract. 018 replaces it with factor-based shelter protection and adds tent condition/degradation.

During active repair, follow `world-021` freeze semantics rather than continuing weather degradation in parallel.

Condition `0` remains repairable and does not imply automatic destruction.

## Tent must become instance-backed

This remains required because condition must survive world ↔ inventory transitions.

Current relevant files:

- `src/items/itemInstances.ts`
- `src/items/Inventory.ts`
- `src/items/trade.ts`
- `src/items/tradeCatalog.ts`
- `src/items/createPlacedTents.ts`
- `src/app/actions/placementActions.ts`
- `src/app/actions/restActions.ts`
- `src/app/createApp.ts`

Current `itemInstances.ts` centrally owns instance classification, cloning and id generation. Add a tent instance carrying `condition` and include `tent` in the central instance-backed classification. Extend every clone/save/restore boundary that currently only knows durability/sharpness/liquid fields.

Do **not** reuse `clamp01()` for tent condition; camp condition is `0..100`.

`Inventory` already provides `addInstance()`, `removeInstance()`, `getInstances()`, `countInstances()` and `canAddInstance()` semantics; use these instead of a parallel portable-tent store.

Audit every old stack caller when `tent` becomes instance-backed. Current main still has stack-oriented tent checks/removal in placement/rest/Quick Actions paths; after migration there must be one representation only.

## Stable physical tent identity

Prefer the same physical id across:

```text
TentItemInstance.id ↔ PlacedTent.id
```

Current `createPlacedTents.place()` generates `tent:${Date.now()}:...`, so the post-018 placement API will need to accept the carried instance/id (or otherwise preserve one stable identity) rather than manufacturing a second identity.

Placement:

1. choose a concrete carried tent instance,
2. Busy/placement flow may start,
3. on successful placement re-resolve the instance by id,
4. transfer its id + condition into world-owned tent state.

Packing:

1. block if an active repair episode exists,
2. resolve/checkpoint current condition to `now`,
3. construct the carried instance with the same id/condition,
4. verify `inventory.canAddInstance(instance)`,
5. only then remove the world tent and add the instance.

Packed tents should not continue weather degradation and should not carry the world degradation anchor. Redeploy initializes the anchor to current elapsed world time.

## Legacy stacked-tent migration

Use the existing persistence migration/restore pipeline; do not normalize this opportunistically from gameplay code.

Required invariant:

```text
legacy count N tents
→ N fresh TentItemInstances(condition = 100)
→ stack count removed
```

After restore there must never be both stack-count tents and tent instances.

Use the repository's existing migration id convention. Avoid runtime `Date.now()` inside deterministic save migration if existing migration helpers provide deterministic ids.

## Sewing kit and capability

Extend the central item capability mechanism only:

```text
ItemCapability += textile_repair
CAPABILITY_NEED_LABEL.textile_repair
```

Repair gates through:

```ts
inventory.hasCapability('textile_repair')
```

not through `kind === 'sewing_kit'`.

Add `sewing_kit` to the normal item registries (`ItemKind` / `ITEM_DEFS`, `ITEM_CATALOG`) as a stackable reusable utility item:

- weight `0.4 kg`,
- non-holdable,
- no durability in this plan,
- capability `textile_repair`,
- use the actual size enum (`SM` is the current equivalent of plan-level `S` unless neighboring utility items justify `XS`).

Merchant acquisition should reuse normal merchant stock/pricing. Price is `18 coin`. No crafting/world-spawn/quest-reward path in 019.

Platform repair continues to require the existing `wood_chopping` capability rather than a concrete axe kind.

## Material transaction and revalidation

At repair episode start, authoritative order should match `world-021`:

```text
relookup target
→ resolve/checkpoint current condition
→ derive fresh quote
→ validate no active repair / condition < target
→ validate Repair action availability
→ validate capability
→ validate all materials
→ atomically consume/commit materials
→ create RepairProgress
```

Failure before commit means no materials consumed and no repair state.

Once an episode exists, do not consume materials again on resume.

At each work bout start/resume revalidate at least target existence, active repair and actor/tool capability. Do not keep mutable target references across Busy Action; retain stable ids and relookup.

## Busy Action / physical effort

Reuse the existing Busy Action and physical-effort helpers, but treat each Busy Action as a contribution interval rather than the whole repair.

Effort policy from the plan:

```text
bedroll  → light
tent     → light
platform → moderate
```

On interruption, contribute the accepted elapsed useful work according to the actual shared Busy/work pattern introduced/used by `world-021`. Do not implement "consume/mutate only in onComplete" as the old notes suggested; partial useful work is now intentionally persistent.

Do not persist Busy Action state itself.

## Camp object mutation seams

After `items-player-018`, tent, bedroll and platform owners need explicit mutation methods for condition/repair lifecycle. Avoid mutating objects returned from `.list()`/snapshot getters as an implicit side effect.

Each object owner should remain responsible for:

- resolving/checkpointing condition,
- exposing current repair state,
- starting a validated repair episode after the app layer commits materials,
- accepting repair work,
- completing atomically and resetting degradation anchor.

If `world-021` establishes reusable naming/signatures for its well-roof consumer, mirror that pattern where it fits instead of inventing camp-only terminology.

## Packing and other conflicting operations

A tent with active `RepairProgress` cannot be packed in v1. Give explicit feedback and leave world state unchanged.

Likewise, any operation that would delete/replace a bedroll/platform while repair is active must either be blocked or explicitly preserve the same authoritative repair owner. Prefer blocking in 019; do not migrate active repair episodes into inventory.

Full-camp setup from `items-player-018` must not auto-repair damaged components and must not discard their condition.

## Selling damaged tents

Tent selling becomes instance-aware once tents are migrated. Reuse the existing instance sell-price/order path in `src/items/trade.ts` rather than making merchant-only tent logic.

Extend the current condition-aware instance pricing/ordering carefully for tent `condition 0..100`; keep trap-specific broken/usage semantics unchanged.

Selling multiple tents must choose deterministically. A worn-first ordering is suitable if it remains consistent with the repository's existing instance-selection conventions.

## High-value tests / regressions

Prioritize cross-system tests that prove the new ownership boundaries:

- legacy stacked tent save → only tent instances after restore,
- merchant purchase → fresh tent instance at `condition = 100`,
- damaged tent pack/redeploy/save-load preserves physical id + condition,
- inventory-full packing leaves world tent untouched,
- active tent repair blocks packing,
- Quick Actions/placement still recognize instance-backed tents,
- clone/save conversion preserves tent condition,
- preview and authoritative start use the same repair quote logic,
- failed start consumes no materials and creates no progress,
- interruption preserves committed materials + partial accepted work,
- resume does not consume materials again,
- degradation is frozen during active repair and resumes from completion anchor,
- completion updates condition exactly once and clears progress,
- missing target/tool at resume contributes no further work,
- Repair XP cannot be farmed by start/cancel/resume loops,
- damaged-tent sell price is monotonic and instance selection deterministic.

## Recommended implementation order

1. Reconfirm implemented APIs of `items-player-018`, `items-player-021`, `world-021`.
2. Add sewing kit/capability.
3. Migrate tent to item-instance lifecycle + persistence/migration + pack/redeploy identity continuity.
4. Add pure camp repair quote definitions/resolver using shared material/skill contracts.
5. Add explicit repair lifecycle methods to tent/bedroll/platform owners, reusing `RepairProgress` helpers.
6. Wire inspection + targeted Repair actions to one shared start/resume path.
7. Wire Busy work contributions, physical effort and Repair XP.
8. Extend instance-aware damaged-tent trading.
9. Add boundary/regression tests.
