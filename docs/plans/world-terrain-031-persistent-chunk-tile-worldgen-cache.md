# Plan: Persistent chunk tile worldgen cache

**Created:** 2026-09-14
**Status:** `verification needed` 🔍
**Type:** optimization
**Priority:** high · **Effort:** L
**Depends on:** none
**Domain:** `world-terrain`
**Subdomains:** `chunks` `terrain` `vegetation`
**Tags:** `worldgen` `cache` `worker` `chunks` `performance`
**Roadmap:** -
**Model:** Opus, Sonnet

## Goal

Persist canonical worker-generated `ChunkTileResult` so same-seed reloads/rebuilds and revisits can skip repeated terrain-grid and deterministic placement generation.

Cache only deterministic base worldgen output. Player/runtime terrain deltas, lifecycle state and Three.js presentation remain outside it.

## Recon

`src/terrain/chunkHeightmapProtocol.ts` already defines the correct data-only boundary:

```ts
ChunkTileResult = ChunkTileData & {
  vegetation
  items
  environment
  crops
}
```

`ChunkTileData` is apron-inclusive typed arrays for heights/floor heights/biome/body scale/continentalness/ridge/moisture/road tint.

`ChunkTileParams` already contains exact deterministic generation inputs: seed/coords/size/resolution/config plus nearby roads, clearings, regional smoothing, rivers, cemetery inputs and authored expedition ruins.

`ChunkMeshDataCache` is a separate downstream, session-only byte-bounded cache. Keep it; persistent tile reuse and mesh-data reuse are different stages.

Player terrain changes are sparse save/runtime deltas through `modifyTerrain(..., 'player')`; cave/system modifications are deterministic replay. Neither belongs in the cached worker result.

Reuse `worldgenCacheDb.ts`; no new DB/store or `SaveData` field.

## Cache contract

Add `src/terrain/chunkTileWorldgenCache.ts` (or equivalent terrain-owned adapter).

Namespace: `chunk-tiles`, explicit version.

Sub-key: `chunk:<cx>:<cz>`.

Payload: existing `ChunkTileResult`, structured-cloned with typed arrays intact.

Do not persist `ChunkRecord`, meshes/materials, colliders, grass/mesh presentation data, player modifications, tree/crop lifecycle overrides or resource depletion.

## Per-record fingerprint

This namespace cannot rely only on one small world-level fingerprint because per-chunk road/river/clearing/cemetery inputs affect output.

Compute a stable hash from the exact `ChunkTileParams` used for that worker request:

```text
key = seed / chunk-tiles / version / chunk:<cx>:<cz>
fingerprint = stableHash(ChunkTileParams)
```

Stable-hash plain deterministic data with stable object-key ordering. Algorithm changes inside `computeChunkTile` or vegetation/items/environment/crop generation require namespace-version bump even if params are unchanged.

## Lookup integration

Integrate at `ChunkManager.ensureLoaded()` immediately after exact params are built and before `requestChunkTile()`:

```text
paramsFor(coord,...)
→ fingerprint
→ persistent lookup
   ├─ hit → normal finalize pipeline
   └─ miss → requestChunkTile worker
            → remember canonical result
            → normal finalize pipeline
```

Do not put IndexedDB inside the worker and do not create a second chunk finalization path.

Chunk loading is already async, so persistent lookup fits that seam without changing gameplay APIs.

## Direct-record lookup

The current generic `listCacheRecords()` reads all records for a seed/namespace. That is unsuitable for potentially hundreds of large chunk records.

Extend `worldgenCacheDb.ts` with the smallest reusable direct primary-key lookup (`getCacheRecord` or equivalent `(seed, namespace, version, subKey)`) and use it per requested chunk.

Reuse the existing key/store. Do not create another store/index unless measured need proves it necessary.

## Critical immutability rule

Never queue a live mutable `ChunkRecord.tile` and clone it seconds later after runtime terrain code may have mutated its typed arrays.

On worker miss, snapshot/persist the canonical `ChunkTileResult` **before runtime modifications/finalization can mutate it**.

A cache hit must likewise become runtime-owned data that may be modified without mutating any retained cache authority.

This boundary is required for save isolation: digging/building in save A must never contaminate the deterministic cache later reused by save B.

## Validation and fallback

A cached record is disposable. Validate required typed arrays, expected apron grid length `(resolution + 2)^2`, and required placement arrays. Invalid data is a miss and is regenerated by the normal worker path.

No cache migrations.

## Bounds / eviction

Do not hydrate the namespace into RAM.

Choose a conservative per-seed cap after estimating actual tile payload size. Count-based `enforceCacheCap()` is acceptable for V1 only if record sizes are sufficiently uniform; otherwise make the smallest reusable cleanup extension needed. Do not build a generic quota manager.

Avoid a write transaction on every cache hit just to touch `lastAccessedAt`; batch access metadata if needed.

`Clear cache` continues to work through generic per-seed cache deletion.

## System interactions

- Changed roads/rivers/clearings/cemetery inputs naturally change the per-record fingerprint.
- Cave mouth/system terrain modifications are replayed after cached/fresh tile retrieval exactly as today; do not bake them into the base payload.
- Tree/crop/resource lifecycle/depletion/removal overrides stay authoritative over deterministic cached placements.
- Same-seed saves share only base worldgen data, never mutable deltas.

## Instrumentation

Add bounded debug/perf counters using existing infrastructure where practical: persistent tile hits/misses/invalid records, read time and worker generations avoided. No per-frame logging/new observability framework.

## Non-goals

- Persistent `ChunkMeshData` or GPU cache.
- Persistent grass worker output in this plan.
- Runtime/player modification caching.
- Replacing the worker pool.
- Pre-generating chunks to warm cache.
- Loading all cached chunks into memory.
- Terrain algorithm changes.

## Tests

Cover:

1. `ChunkTileResult` typed-array/placement round-trip;
2. direct chunk lookup without namespace-wide hydrate;
3. exact params hit avoids worker generation;
4. changed road/river/clearing/cemetery/global config misses;
5. version mismatch misses;
6. malformed array lengths/types regenerate safely;
7. cached and fresh base results are deeply equivalent;
8. later player terrain mutation cannot corrupt persistent record;
9. cave/system replay is identical on cached/fresh tiles;
10. lifecycle/depletion overrides apply identically;
11. clear/eviction returns to worker generation;
12. IndexedDB failure falls back to worker;
13. stale async result from previous world cannot attach to current activation.

## Implementation

Implemented on `main`.

- `src/persistence/worldgenCacheDb.ts` — two generic seams, both keeping the
  module's "never throw into gameplay" rule: `getCacheRecord()` (direct
  primary-key read, no `by_seed` hydrate) and `deleteCacheRecords()`
  (exact-key eviction in one transaction). `listCacheRecords()` /
  `enforceCacheCap()` are unchanged and stay the small namespaces' path.
- `src/terrain/chunkTileWorldgenCache.ts` — the `chunk-tiles` namespace:
  `chunk:<cx>:<cz>` records holding the unchanged `ChunkTileResult`,
  `chunkTileFingerprint()` over the whole `ChunkTileParams` (so any new
  deterministic param field invalidates by itself), structural validation
  against `(resolution + 2)²`, `cloneChunkTileForRuntime()`, a best-effort
  read/write pair and bounded hit/miss/invalid/write/eviction counters.
- Bounds: a per-seed **byte** budget (128 MiB) tracked in a small `meta`
  manifest record read through the same direct lookup; over budget, the
  least-recently-used tiles are dropped by exact key. A cache hit updates
  recency in memory only and never opens a write transaction.
- `src/terrain/chunkManager.ts` — `acquireCanonicalTile()` sits between
  `paramsFor()` and `requestChunkTile()` inside `ensureLoaded()`: a hit skips
  the worker, a miss runs it and schedules the fire-and-forget write. Both
  paths converge on the single existing `rec.tile = … → waitForFinalizeSlot()`
  finalize pipeline, always through a runtime clone, so the canonical object a
  pending IndexedDB write holds is never mutated by `attachChunkMesh()`.
  Record identity is re-checked after the cache read and after the worker
  result, and the failure/cleanup paths are identity-checked too, so an unload
  or rebuild under the same key can neither start a pointless worker job nor
  let a stale result attach to a replacement `ChunkRecord`.

Terrain modifications, terrain cutouts, tree/crop lifecycle, planted crops,
collected item ids, resource depletion, mesh data and grass stay downstream and
are not cached; `ChunkMeshDataCache` remains a separate session-local LRU.

Verified: `pnpm test` (503 files), `npx tsc --noEmit`, `pnpm run lint:fix`,
`pnpm run build`. Browser cold/warm traversal comparison is the user's.
