## Problem

Plan `world-013` significantly reduced the procedural lake/peak scan cost used by `WorldLocationCatalog`, but manual verification still shows a visible freeze when buying the **Near Map (`map_near`)**.

Near Map covers only `0–20 km`, so the remaining multi-second hitch is unlikely to come from the coarse terrain scan alone.

Current recon points to the cemetery lookup path:

```text
merchant purchase
→ applyLocationMap('map_near')
→ landmarksInRange(0, 20 km)
→ cemeteryCandidates()
→ cemeteryForSettlement()
→ ChunkManager.findLandmarkNear('cemetery', ...)
```

For loaded chunks `findLandmarkNear()` reuses the existing tile. For unloaded chunks it falls back to synchronous procedural work on the main thread:

```text
paramsFor(...)
→ computeChunkTile(...)
→ computeChunkEnvironment(...)
→ search landmark
```

A single cemetery query can inspect several settlements, and each settlement lookup can inspect multiple chunk coordinates. The cache added in `world-013` removes repeated work after the first lookup, but it does not remove the cold-path cost paid during the first Near Map purchase.

The implementation benchmark for `world-013` intentionally isolated the terrain scan with empty caves/settlements, so this real settlement/cemetery path was not represented in that benchmark.

## Goal

Remove the remaining main-thread freeze from cold World Location discovery queries, starting with Near Map purchase.

World Location queries must not require full synchronous generation of many unloaded chunks merely to resolve deterministic landmark placement.

The fix must preserve one source of truth for landmark placement: a location resolved before a chunk is streamed must match the physical landmark later generated by the normal world pipeline.

## Scope

### 1. Confirm the cold-path hotspot

Instrument the real Near Map flow enough to measure:

- total location-query time,
- `cemeteryCandidates()` time,
- `findLandmarkNear()` calls,
- inspected chunk coordinates,
- loaded-tile hits,
- unloaded-chunk fallbacks,
- time spent in fallback `computeChunkTile()` / `computeChunkEnvironment()`,
- existing lake/peak classification and extraction timings.

Keep diagnostics opt-in and without normal console spam.

The purpose is to confirm the source of the hitch before changing architecture, not to build a general profiler framework.

### 2. Remove unnecessary full synchronous chunk generation from landmark lookup

Remove or significantly reduce the full unloaded-chunk generation fallback used by World Location landmark queries.

The implementation may refactor `findLandmarkNear()` or introduce a lower shared resolver, depending on current code dependencies found during implementation notes/recon.

Do not make merchant- or map-specific shortcuts.

### 3. Preserve deterministic landmark placement as one source of truth

Do not introduce a separate approximate `WorldLocation` cemetery generator.

If the current placement logic is embedded too deeply in full chunk/environment generation, extract or reuse the minimal shared deterministic mechanism needed by both:

```text
normal streamed chunk generation
and
lightweight unloaded landmark lookup
```

For the same seed/config/chunk, both paths must resolve the same landmark identity and position.

### 4. Reuse existing terrain/world mechanisms

If landmark placement requires terrain information, reuse existing pure samplers or shared placement logic instead of duplicating world-generation rules.

Avoid materializing full terrain/vegetation/item/render data when the lookup only needs enough information to decide landmark placement.

Do not create a second cache/system when an existing world-generation seam can be shared.

### 5. Keep existing WorldLocationCatalog cache and lifecycle

Keep the cemetery cache introduced by `world-013` unless current code recon proves it obsolete.

Its role remains reuse across overlapping Near/Guard/Far queries. This plan should primarily reduce the cost of a cache miss.

Existing world-rebuild invalidation semantics must remain correct across seed/config changes.

### 6. Preserve gameplay semantics

Do not change:

- Near Map range (`0–20 km`),
- Far Map range (`60–200 km`),
- merchant reveal counts,
- guard reveal behaviour,
- `LocationKnowledge`,
- discovery source semantics,
- cemetery frequency or placement rules,
- `WorldLocation.id`,
- map/navigation presentation.

This is a fix to the implementation path, not a gameplay rebalance.

### 7. Do not move the whole WorldLocationCatalog to a Worker by default

Do not introduce a worker for the entire World Location system as the first solution.

`world-013` already introduced a lightweight cached coarse terrain scan. If the remaining hitch is caused by synchronous full chunk generation during cemetery lookup, remove that cost at its source.

Worker offload remains a follow-up only if profiling after this fix still shows a meaningful CPU-heavy long task.

## Acceptance criteria

- Cold Near Map purchase does not synchronously perform full `computeChunkTile()` generation for a series of unloaded chunks on the UI event path.
- Buying Near Map no longer causes a visible gameplay freeze.
- A landmark resolved before chunk streaming has the same id/position as the physical landmark later generated by the normal chunk pipeline.
- Near/Guard/Far discovery results remain deterministic and independent of query order.
- Existing discovery/reveal semantics remain unchanged.
- No parallel landmark-generation system is introduced.

## Tests

Add or extend automated tests covering the architectural contract rather than wall-clock timings:

1. unloaded lightweight lookup matches the normal generated landmark result for the same seed/config/chunk,
2. absence of a landmark is also consistent between both paths,
3. deterministic id/position parity is preserved,
4. unloaded landmark lookup no longer requires full `computeChunkTile()` generation where the new lightweight/shared path applies,
5. loaded chunks still reuse existing tile/environment data where appropriate,
6. cache miss and cache hit return the same result,
7. rebuild/invalidation does not leak results from the previous world,
8. Near/Guard/Far query order does not change results.

Do not add wall-clock performance thresholds to Vitest.

## Implementation status

Implemented as scoped: cemetery-only extraction, no worker, no new cache/system.

- `src/terrain/chunkEnvironment.ts`: cemetery RNG/gating/identity extracted verbatim into `resolveCemeteryPlacement(coord, params, terrain: CemeteryTerrainSampler)` — a pure function taking only the two terrain accessors cemetery acceptance actually needs (`heightAt`/`roadTintAt`). `computeChunkEnvironment()` now calls it with a `CemeteryTerrainSampler` backed by its own apron-grid `sample()`; identical RNG draw order, so no behavior change for the full-generation path (covered by existing + new parity tests).
- `src/terrain/chunkHeightmap.ts`: `computeChunkTile()`'s per-texel loop body (raw sample + regional smoothing + road/clearing corridor + river carving) extracted into `computeChunkTexel()`. New `createLocalTerrainSampler(coord, params)` resolves `heightAt`/`roadTintAt` at arbitrary world points by evaluating only the handful of apron-grid texels a query's bilinear interpolation actually touches (cached per texel index), instead of allocating a full `(resolution + 2)²` grid.
- `src/terrain/chunkManager.ts`: `findLandmarkNear()`'s unloaded-chunk fallback extracted into pure, exported `resolveUnloadedLandmark(kind, coord, params)`. For `kind === 'cemetery'` it calls `createLocalTerrainSampler` + `resolveCemeteryPlacement` — no `computeChunkTile()`/`computeChunkEnvironment()` call, no vegetation/full-environment generation. Every other landmark kind (`monolith`/`stoneCircle`/`smallRuins`) keeps the original full-generation fallback unchanged — out of scope per the plan (not on this cold path today).
- River segments: unchanged, pre-existing behavior — both the loaded and unloaded paths still resolve via `paramsFor(coord, [])` (no river carving) for the unloaded fallback, same as before this plan. Documented explicitly in `resolveUnloadedLandmark`'s doc comment as a deliberate, unchanged tradeoff (real hydrology on the query path would reintroduce the cost this plan removes).
- Diagnostics: reused the existing `getMonitor().recordHitch('PROPS', ms, label)` mechanism (already used elsewhere in `chunkManager.ts` for chunk-generation phases) instead of adding a new counters/diagnostics subsystem — zero cost when the perf monitor is disabled (the common case), and distinguishes loaded / unloaded-lightweight / unloaded-full-fallback / miss in the existing perf tooling by label.
- Tests added: `chunkHeightmap.test.ts` (`createLocalTerrainSampler` parity against a full `computeChunkTile()`-backed sampler — plain terrain, roads, clearings/regional, and query-order independence), `chunkEnvironment.test.ts` (`resolveCemeteryPlacement` parity across many seeds — both full-tile-backed and lightweight-sampler-backed — asserting both acceptance and rejection outcomes actually occur, plus exact-field parity against `computeChunkEnvironment`'s own cemetery result), `chunkManager.test.ts` (`resolveUnloadedLandmark` — a `vi.spyOn(chunkHeightmap, 'computeChunkTile')` proves the cemetery path never calls it while the monolith path still does; determinism/order-independence across chunks).
- `pnpm test`, `npx tsc --noEmit`, `pnpm run lint:fix`, and `pnpm run build` all pass.
- Not done (left to the user per the plan): browser Performance trace before/after on a cold Near Map purchase, and the Guard/Far Map regression pass.
