# Implementation Notes: Vegetation and Prop Instancing

**Plan:** [2026-08-12--087--vegetation-and-prop-instancing.md](./2026-08-12--087--vegetation-and-prop-instancing.md)

## Status (2026-08-13)

**Implemented + technically verified** (`tsc`/`lint`/`test`/`build` green after every phase):

- **Phase 1** — `src/render/instancedProps.ts`: `buildInstancedProps(templates, placements, name)` buckets by `(speciesIndex, primitiveIndex)`. `flattenPropTemplate` (memoized per template root in a `WeakMap`) composes each mesh's ancestor-chain matrix excluding the root's own transform (that part is folded into the per-instance matrix instead). The instance matrix itself is built by a scratch `Object3D` that reproduces `cloneProp`/`clonePropWithYaw` + `placeOnGround` step for step, per the plan's §2.1 — not a re-derived formula. `removeByKey` is a swap-remove that keeps every primitive bucket's instance index in sync. `instancedProps.test.ts` proves matrix equivalence against the real `clonePropWithYaw` + `placeOnGround` path (tolerance ~1e-6, limited by the `Float32Array`-backed `instanceMatrix` buffer, not by the math) plus a swap-remove test.
- **Phase 2** — `foliageWind.ts`'s `BEGIN_VERTEX_WIND` gained a `#ifdef USE_INSTANCING` branch (`propMatrix = modelMatrix * instanceMatrix`) so amplitude/phase are per-instance instead of shared by every instance in a bucket. `WIND_CACHE_KEY` bumped to `v2` (new shader text, new program cache entry). `loadGltf.ts`'s `disposeObject3D` now calls `InstancedMesh.dispose()` (frees the `instanceMatrix` GPU buffer, which neither `geometry.dispose()` nor `material.dispose()` touches) — safe for plain meshes since `isInstancedMesh` is `undefined` there. New `loadGltf.test.ts` (didn't exist before).
- **Phase 3** — `chunkManager.ts`: bush/cactus/reed placements split out of the tree-only `buildPlacementGroup` path into `buildInstancedProps` calls, one per kind present in a chunk (`ChunkRecord.vegetationInstances: InstancedPropGroup[]`). Trees stayed on the old clone-per-instance path in this phase — deliberate, per the plan, to prove both paths coexist in one chunk before touching tree lifecycle.
- **Phase 4** — Living trees (`resolved.visual === 'living'`) instanced too, keyed by `treeId` (`ChunkRecord.treeInstances: InstancedPropGroup`, `removeByKey`). Non-living stage meshes (limbed/felled/stump) stay individual `Object3D`s in a new `ChunkRecord.vegetationExtras` group (replaces the old `rec.vegetation`). `treeLifecycle.ts` gained `getPresence(id): TreePresence | null` (`byId.get(id) ?? null`) because an instanced tree carries no per-object `userData` for `refreshTreeVisual` to read identity off of anymore. `refreshTreeVisual` reworked: `treeInstances.removeByKey(treeId)` first; if that returns `false`, find-and-remove in `vegetationExtras` as before. The rebuilt visual always lands in `vegetationExtras` regardless of whether the new stage is living again (stump → sapling regrowth) — a deliberate simplification from the plan (§2.3 point 2): re-inserting into an already-built instance buffer is more machinery for a rare runtime-refresh path, versus the bulk case (initial chunk load) which is what actually needed instancing. `ChunkRecord.treeYaw: Map<treeId, rotationY>` fills the one gap `TreePresence` doesn't cover (position/species/size/stage are all on `TreePresence` already).
- **Phase 5** — `tile.environment` split the same way as phase 3: `largeRock`/`rockCluster`/`fallenLog` (GLB, no runtime state) instanced via `buildInstancedProps` (`ChunkRecord.environmentInstances: InstancedPropGroup[]`); `campfire`/`monolith`/`stoneCircle`/`smallRuins` (procedural, unique geometry per placement) stay on the old `buildPlacementGroup` path in `rec.environment`. `speciesIndex: 0` for every environment instance is not a new simplification — today's code already always clones template index 0 for these kinds (`EnvironmentPlacement` has no `speciesIndex` field).

`cloneProp`/`clonePropWithYaw` (tree path) and `clonePropWithYaw` (rock/cluster/log path) are now unused in `chunkManager.ts` and were dropped from its imports.

## Browser/visual verification

- Informal only: user reported "chodzę po mapie i działa" (walking around, no visible breakage) after phase 3. No structured seed/GUI-metrics check from the plan's §5 has been run.
- **Phase 0 (baseline measurement) was never done** — no before/after `Draw calls`/`Triangles (rendered)`/`Geometries (GPU)` numbers exist for this plan. The phase ordering in the plan puts phase 0 first specifically so there's a number to compare against; skipping it means the expected win (fewer draw calls in dense forest / near environment clusters) is architecturally sound but not measured.
- Risks called out in the plan as needing a browser check, still open: **R2** (wind phase differs between neighboring trees — visual only, can't be asserted from a unit test), **R3/R4** (triangle count change from losing per-object frustum culling; any `nature/*` material still `transparent` would show wrong blend order inside a bucket — `hardenFoliageAlpha` already converts matching foliage materials at GLB-load time, so risk is believed low but unconfirmed).

## Remaining (not done)

- **Phase 6 (Should)** — settlement tree/bush cluster instancing (`landmarks.trees[].mesh`). Deliberately deferred: bounded to one settlement (a few dozen objects, not the thousands phases 3–5 covered across ~49 loaded chunks), and `landmarks.trees[].mesh` is read by `places.ts` (`workplaceFor` woodcutter targeting) and `createSettlement.ts` — reworking it means redoing phase 4's removeByKey/lifecycle-refresh complexity on a different data structure, with NPC systems holding references. Low ROI relative to phase 7.
- **Phase 7 (Nice to have) — chosen as next.** LOD via `InstancedMesh.count` narrowing for distant chunks, same pattern already proven on grass (`grass.ts`'s `setLodFraction`). Recovers the triangle-count regression risk (R3) that phases 3–5 introduced by trading per-object frustum culling for bucket-level culling — and unlike phase 6, this applies continuously across every loaded chunk, not one fixed location. Needs: a count-fraction API on `InstancedPropGroup` (or a wrapper), wired into `chunkManager.ts`'s existing per-chunk distance calculation (same one `syncGrassForRecord` already uses).
- **Phase 8 (Nice to have)** — raising vegetation density/radius now that headroom may exist. Explicitly out of scope for this plan (a separate visual decision, not an optimization).
